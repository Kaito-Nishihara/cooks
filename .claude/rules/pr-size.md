# PR の大きさの規約

Claude が本リポジトリで PR を作るときの、1 つの PR の大きさのルール。
修正量が多い PR は、レビューできない。
多くなるときは、複数の PR に分ける。

## 目安

- 実装の差分は、1 つの PR につき 400 行程度までとする。
- テストを含めた差分は、800 行程度までとする。
- 作り直したファイル(`api/`、`generated/`、ロックファイル)は、数えない。
- 数え方は `git diff --stat <base>...HEAD` の、足した行と消した行の合計とする。

## 分ける時点

- 実装を始める前に、差分の見込みを立てる。目安を超えそうなら、最初から分けて進める。
- 書いた後で超えていたら、PR を出す前に分ける。出した後に気付いたら、閉じて分け直す。
- 「分けないと受け入れ条件を確かめられない」を理由に、1 つにまとめない。受け入れ条件のテストは、それを通せる PR に置く。

## 分け方

依存の少ない順に、下から積む。サービスの機能は、次の順で分けられる。

1. 共通のライブラリ(`service-common`)に足す部品
2. ドメイン(集約、値オブジェクト)と、そのテスト
3. テーブル(Flyway)と、基盤(リポジトリの実装)
4. ユースケースと入口と、API のテスト。入口が複数あるときは、入口ごとに分ける

画面は、共通の部品、1 つの画面、の順で分ける。
仕様書だけの変更は、実装の PR に混ぜず、別の PR にする。

## 分けた PR の決まり

- どの PR も、それだけでビルドとテストが通る。
- 分けた PR は、1 つずつ `main` に入れる。前の PR が `main` にマージされてから、次の PR を出す。
- どの PR も、base は `main` にする。前の PR のブランチを base にしない。base を付け替える前にマージすると、変更が `main` ではなく前のブランチに入るためである(#62 から #70 で起きた)。
- 前の PR のマージを待つ間に、次の作業を書き始めてよい。そのときは前のブランチから切り、PR を出す前に `main` を取り込む。
- PR の本文の先頭に、分けた全体のうちの何番目かと、前の PR の番号を書く。
- 対応する Issue を閉じる `Closes #番号` は、最後の PR にだけ書く。ほかの PR には `Refs #番号` と書く。
- 報告には、PR ごとの行数と、次に出す PR を書く。
