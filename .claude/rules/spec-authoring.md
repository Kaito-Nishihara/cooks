# 仕様書の規約

Claude が本リポジトリで仕様書を作成、更新するときのルール。
対象は `docs/` 配下の Markdown である。
読者は、実装する Claude と、内容を承認する利用者の二者である。
文章は [writing-style.md](writing-style.md) に従う。

## 文書の種類と置き場

| 種類 | 置き場 | 書くこと |
|---|---|---|
| 要件定義 | `docs/requirements.md` | 何を作るか、何を作らないか。受け入れ条件。全体の技術構成 |
| 機能の仕様書 | `docs/design/<機能名>.md` | 1 つの機能の画面、API、データ、エラー、受け入れ条件の詳細 |
| 決定の記録 | `docs/decisions/<連番4桁>-<題>.md` | 技術や設計の選択を 1 件。選んだ案、却下した案、理由 |
| 図 | `docs/architecture.html` と、各文書の中の mermaid | 構成と流れ |

ファイル名は英小文字とハイフンにする。例: `docs/design/recipe-edit.md`、`docs/decisions/0003-session-cookie.md`
題名(`#` の見出し)は日本語で書く。

要件定義を正本とする。
機能の仕様書は要件定義を詳しくするもので、矛盾させない。
要件定義と食い違う設計が要るときは、先に要件定義を直し、利用者の承認を得る。

## 書く時点

- 機能の仕様書は、その機能の実装を始める前に書き、利用者の承認を得てから実装する。
- 決定の記録は、選択をしたその作業の中で書く。後からまとめて書かない。理由を忘れるためである。
- 実装の途中で仕様を変えたときは、コードより先に仕様書を直す。
- 構成(サービス、通信の向き、データの持ち主)を変えたときは、`docs/architecture.html` も同じ作業の中で直す。

## 機能の仕様書の構成

上から次の順で書く。該当がない節も消さず、「なし」と書く。

1. **目的**: この機能で利用者ができるようになること。2〜3 行
2. **範囲**: やること、やらないこと
3. **画面**: パス、表示する項目、操作、状態(読み込み中、空、エラー)
4. **API**: メソッドとパス、受け持つサービス、必要な役割、入力、出力、エラーの `code` と HTTP の状態
5. **データ**: テーブルと項目、制約、持ち主のサービス
6. **サービスの間のやり取り**: 呼び出す相手、相手が応答しないときの動き
7. **受け入れ条件**: 下の規約に従う
8. **未決事項**: 決まっていないことと、いつ誰が決めるか

## 決定の記録の構成

1. **状況**: 何を決める必要があったか
2. **決めたこと**: 選んだ案を 1 文で
3. **理由**
4. **却下した案**: 案ごとに、却下した理由を 1〜2 行
5. **影響**: この決定で変わること、後で見直す条件

決めたことを後で覆すときは、古い記録を書き換えず、新しい記録を足して古いほうに「0007 で置き換えた」と書く。

## 受け入れ条件

- 確かめられる形で書く。「使いやすい」「適切に」のような、合否を判定できない語を使わない。
- 1 つの条件に、操作と期待する結果を 1 組だけ書く。
- 具体的な値を書く。例: 「2 人分で 250g の材料を 4 人分にすると 500g と表示される」
- 失敗する場合も書く。権限がない、入力が不正、相手のサービスが応答しない、の 3 つは必ず検討する。
- 条件ごとに識別子を付ける。形は `AC-<機能>-<連番2桁>` とする。例: `AC-EDIT-03`
- テストの名前かコメントに、対応する識別子を書く。どの条件がテストされていないかを検索できるようにするためである。

## 書かないこと

- コードを読めば分かる実装の詳細(クラス名の一覧、関数の引数)
- 作業の経過(「最初は A を試したが」)。経過は書かず、結論と理由を書く。却下した案は決定の記録に書く
- 決まっていないことを、決まったかのように書くこと。未決事項の節に書く
- 確かめていない性能や上限の数字。見込みは「見込み」と書く

## 図

- 流れは mermaid のシーケンス図、状態の移り変わりは状態遷移図で書く。
- 図には、本文で説明していない情報を載せない。図だけを見て実装すると本文の決まりを落とすためである。
- 図の直前に、その図で何を読み取ってほしいかを 1 文で書く。

## 文書を足したとき

1. `docs-site/mkdocs.yml` の `nav` に 1 行足す。
2. `docs/index.md` の文書の一覧に 1 行足す。
3. `docker compose -f docs-site/compose.yaml up -d` でサイトを起動し、`docker compose -f docs-site/compose.yaml logs docs` に警告が出ていないことを確かめる。
4. 足したページが表示され、リンクが切れていないことを確かめる。

## 承認

仕様書を書いたら、実装に進む前に利用者へ次を伝える。

- 自分で決めて書いたこと
- 要件定義から変えたこと、足したこと
- 未決事項

利用者が承認していない仕様書をもとに実装を始めない。
