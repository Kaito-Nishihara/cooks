# React 画面実装スキル

## 置き場所

| 種類 | 置き場所 |
|---|---|
| 画面 | `src/client/routes/<name>.tsx` |
| 再利用コンポーネント | `src/client/components/` |
| API 呼び出し | `src/client/api/<resource>.ts` |
| 業務ロジック | `src/domain/`(Worker と共有) |

画面はクライアント側のルーティングで切り替える。
Worker はどのパスに対しても同じ HTML を返す。

## 計算はブラウザでやる

Workers 無料プランの CPU 制約から、次の計算は**画面側で実行する**。

- 栄養値の算出(`src/domain/nutrition/`)
- レシピ提案のスコア計算と除外判定(`src/domain/suggestion/`)

成分表(`public/data/foods.json`)は静的アセットとして配信されるので、`fetch("/public/data/foods.json")` で取得する。
アプリの起動時に一度読み、以降はメモリに保持する。ブラウザのキャッシュが効くため再訪時の負荷はない。

## 実装の手順

1. **API クライアントを書く**

   `src/client/api/` に置き、`src/shared/` の Zod スキーマで応答を検証する。
   コンポーネントから `fetch` を直接呼ばない。

2. **データ取得を組む**

   取得中と失敗時の表示を必ず用意する。
   失敗したまま何も出ない画面を作らない。

3. **画面を書く**

   - スマートフォンの縦画面を基準に設計する。PC は横幅が広がるだけでよい。
   - フォームの検証は `src/shared/` の Zod スキーマを使う。API 側と同じものを使うこと。
   - 日付の表示は `Intl.DateTimeFormat("ja-JP")` に統一する。

4. **テストを書く**

   ドメインロジックは Vitest で素の関数として試す。
   画面の経路は Playwright で確認する。

## 表示の約束

- 嗜好バッジは `ALLERGY` を最優先で表示し、他の嗜好と明確に区別する。安全に関わるためである。
- 栄養値は、計算から除外した材料が一つでもあれば「概算値」と明示し、除外した材料名を一覧できるようにする。計算できた材料が一つもなければ数値を出さず「未算出」と表示する。
- レシピ提案は、スコアの根拠(どの食材が効いたか)を表示する。数値だけを出さない。

## 表示テキスト

表示する日本語は定数へ集約する。
将来の多言語化を妨げないためだが、いま多言語の仕組みは入れない。
