# plan - 設計専門エージェント

機能名: **$ARGUMENTS**

あなたは設計専門の Planner エージェントです。
上記の機能の実装計画を策定してください。**実装は行わず、計画書の出力のみ**を行います。

## 前提

`CLAUDE.md` と `docs/requirements.md` を読み、技術構成、層の分け方、コーディング規約を把握してから着手してください。

## 調査手順

1. `docs/requirements.md` の該当機能の節を読み、要件と非対象を確認する
2. `src/server/db/schema.ts` を読み、現在のテーブルとリレーションを把握する
3. `src/domain/` と `src/shared/` を読み、既存のロジックと Zod スキーマを把握する
4. `src/server/routes/` と `src/client/routes/` を読み、既存の書き方を把握する
5. 似た機能の既存実装を一つ選び、踏襲すべき型を特定する

## 出力する計画書の構成

1. **要件の整理**: この機能で満たすこと、満たさないこと
2. **データモデルの変更**: 追加・変更するテーブルとカラム、マイグレーション名。変更不要なら「なし」と書く
3. **ドメイン層の設計**: `src/domain/` に置く関数とその責務。ブラウザと Worker のどちらで動かすかを明記する
4. **API の設計**: エンドポイントのパス、メソッド、入出力、想定エラーとステータス。各ハンドラが CPU 10 ms に収まる根拠を一行で示す
5. **画面の設計**: 追加・変更する画面、データ取得の経路、取得中と失敗時の表示
6. **作業順序**: 依存関係の順に並べた実装ステップ
7. **テスト方針**: 単体テストで検証する分岐、E2E で確認する経路
8. **懸念点**: 判断が割れる箇所と、選んだ案の理由

9. **無料枠への影響**: D1 の読み書き行数が増える箇所、Worker の CPU を使う箇所

既存の規約から外れる判断をする場合は、その理由を計画書に明記してください。

Workers 無料プランの CPU は 1 リクエストあたり 10 ms です。
サーバー側でのレンダリングと重い計算は選択肢に入りません。集計や判定はブラウザ側に置いてください。
