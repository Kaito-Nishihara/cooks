# 0051 フォームのライブラリを入れず、入力の状態を自分で持つ

決めた日: 2026-10-11

## 状況

「共通設計: 画面の共通仕様」は、入力の状態を持つ仕組みについて、フォームのライブラリ(React Hook Form など)を使うか、自分で書くかを決めず、条件が最も厳しいレシピの編集の画面と一緒に決めることにした。

レシピの編集の画面は、次のことをする。

- グループの中の材料、手順、コツを、足す、消す、戻す、並べ替える。
- 入力のたびに検証し、入力が止まったら自動で保存する。
- 入力のたびに、材料の全体から栄養の値を計算し直す。
- 保存するたびに、入力の全体と元のレシピから、差分(編集内容)を作る(決定の記録 0049)。
- ほかの人の内容を読み込むときに、入力の全体を置き換える。

業務のロジックは `frontend/src/domain/` に、React に頼らない形で書く決まりである。

## 決めたこと

フォームのライブラリを入れず、入力の状態は React の `useReducer` で持ち、状態を書き換える処理を `frontend/src/domain/recipe/` の関数として書く。

送信のボタンがある画面(ログイン、登録、レシピ帳の名前、招待の作成)も、ライブラリを使わず、値、触れたかどうか、エラー、送信中を持つ小さな共通の処理を `src/hooks/` に 1 つ置く。

## 理由

- 行を足す、消す、戻す、並べ替える処理に、この画面の決まりが多い。足した行の識別子の振り方、最後の 1 行は消せないこと、食材を替えたら摂取する割合を消すこと、戻した行が入る位置、などである。これらを React に頼らない関数にすると、単体テストで確かめられる。ライブラリの配列の操作(行の追加や移動)を使うと、決まりが部品の中に散らばる。
- 画面は、入力のたびに、入力の全体を見る(栄養の値、差分、保存するかどうかの判定)。ライブラリの利点である「変えた欄だけを描き直す」動きが、この画面では生きない。
- 入力の形と API の形が違う(決定の記録 0049)。ライブラリの検証の仕組みは、入力の形と送る形が同じであることを前提にした作りが多い。
- アプリの中で、入力の持ち方を 1 通りにできる。レシピの編集だけを自分で書き、ほかの画面でライブラリを使うと、2 通りになる。
- 外の部品集を入れない判断(決定の記録 0020)と、向きがそろう。

## 却下した案

- **React Hook Form と、Zod をつなぐ部品を使う**: React のフォームで広く使われている。配列の欄を扱う仕組み(`useFieldArray`)、検証、触れたかどうかの管理が付いてくる。上の理由のとおり、この画面の決まりを部品の側に書くことになり、入力の全体を見る処理のために、全体を監視する書き方が要る。ログインや登録のような単純な画面には合う。
- **レシピの編集だけ自分で書き、ほかの画面は React Hook Form を使う**: それぞれの画面に合う。入力の持ち方が 2 通りになり、検証とエラーの出し方の決まり(「共通設計: 画面の共通仕様」の 3.8)を、2 か所で守ることになる。
- **状態を持つライブラリ(Zustand など)を使う**: 入力の状態を、部品の外に置ける。この画面の入力は、この画面でしか使わない。`useReducer` で足りる。

## 影響

- 値、触れたかどうか、エラーの管理を、自分で書く。単純な画面のための共通の処理が 1 つ増える。
- 「共通設計: 画面の共通仕様」の 3.8 の決まり(検証する時点、エラーの出し方)は、変わらない。
- この判断は、書いて確かめたものではない。段階 3 でレシピの編集の画面を書き、自分で書く量が手に余るときは、React Hook Form を入れる方向で見直す。
- このプロジェクトは、標準的なやり方を経験することを優先している。その考え方からは、React Hook Form を選ぶ理由がある。利用者に、どちらにするかを確かめる。
