# 0046 メールアドレスを、全体を小文字にそろえて重複を判定する

決めた日: 2026-10-11

## 状況

登録では、同じメールアドレスを 2 回登録できないようにする(要件定義の 4.4)。
「同じ」をどう判定するかを決める必要があった。
`Misaki@Example.com` と `misaki@example.com`、全角で打った `misaki@example.com`、`misaki+a@example.com` と `misaki@example.com` を、同じとみなすかどうかである。

要件定義の 7.3 と「共通設計: 認証」の 4.2 は、小文字にそろえて保存すると決めている。
そろえる範囲、使える文字、比べる場所は決まっていなかった。

## 決めたこと

メールアドレスは、半角の英数字と記号だけを受け付け、前後の空白を取り、`@` の前も後ろも小文字にそろえた値を保存して、その値が同じなら同じメールアドレスとみなす。
そろえるのは `auth-service` で、データベースは、そろえた後の値をそのまま比べる。

## 理由

- 利用者は、登録のときとログインのときで、大文字と小文字を打ち分けない。スマートフォンは、先頭の文字を自動で大文字にすることがある。区別すると、正しいパスワードを入れてもログインできない人が出る。
- メールの決まりの上では、`@` の前は大文字と小文字を区別できる。実際に区別している事業者は、ほぼない見込みである。区別しないことで、2 人の別の人が同じ扱いになる場合より、1 人の人が 2 つに分かれる場合のほうが多い。
- 使える文字を半角に限ると、Unicode の正規化を考えなくて済む。同じ見た目で違う文字(全角と半角、合成した文字)が、別のメールアドレスとして登録されることがない。
- 保存する値をそろえておくと、探すときも、重複を拒むときも、列の値をそのまま比べればよい。ログインの失敗の記録のハッシュも、同じ値から作れる。

## 却下した案

- **`@` の前だけ、大文字と小文字を区別する**: メールの決まりに厳密に合う。ログインできない人が出る害のほうが大きい。
- **入力のまま保存し、比べるときだけ小文字にする(`lower(email)` のインデックスか、`citext` の型)**: 利用者が打った形を残せる。比べ方の決まりがデータベースの側に移り、サービスの値オブジェクトと 2 か所で持つことになる。`citext` は PostgreSQL の拡張で、入れる手順が増える。打った形を画面に出す必要も、今はない。
- **事業者ごとの決まりでそろえる(Gmail の `.` と、`+` より後ろを取り除く)**: 1 人が、形を変えたメールアドレスでいくつもアカウントを作るのを防げる。事業者ごとの決まりをアプリが知る必要があり、決まりが変わると、別の人を同じとみなすおそれがある。アカウントをいくつも作られて困る機能が、このアプリにはない。
- **全角の文字を NFKC で半角に直して受け付ける**: 日本語の入力のまま打った人を助けられる。正規化の結果が、ブラウザと Java で食い違う文字があると、画面では通り、サービスでは別の値になる。エラーの文で、半角で入れるように伝えれば足りる。
- **日本語などを含むメールアドレス(国際化されたメールアドレス)を受け付ける**: 使っている人は少ない見込みである。受け付けると、正規化と、大文字と小文字の対応が言語によって違う問題を持ち込む。

## 影響

- `users` の `email` に、小文字であることを確かめる制約(`ck_users_email_lower`)を付ける。サービスがそろえ忘れたときに、データベースが拒む。
- 利用者が大文字で登録しても、画面に出るメールアドレスは小文字になる。
- `misaki+a@example.com` と `misaki@example.com` は、別のアカウントとして登録できる。
- 日本語を含むメールアドレスの人は、登録できない。要望が出たら、この決定を見直す。
- メールを送る機能を足すときは、小文字にそろえた値へ送ることになる。`@` の前の大文字と小文字を区別する事業者の利用者には届かないおそれがある。そのときに、打った形を別の列に残すかを決める。
