# 0056 招待の文字列を、API の本文で渡す

決めた日: 2026-10-11

## 状況

招待の文字列は、知っている人なら誰でも招待を受けられる秘密の値である。
そのままの形で保存もログ出力もしない(`CLAUDE.md` の「破ってはいけない決まり」)。

要件定義の 8 章は、招待の内容を見る API を `GET /api/invitations/{token}`、参加する API を `POST /api/invitations/{token}/accept` としていた。
招待の文字列が、パスに入る。

画面の URL では、招待の文字列をフラグメントに入れ、サーバーへ送らないと決めてある(決定の記録 0031)。
残るのは、API を呼ぶときのパスである。
「画面設計: 画面の一覧と遷移」は、入口の記録にパスの後ろを残さないことを、「共通設計: 実行環境」に頼んでいた。
入口(Envoy Gateway)は、要求のパスを記録に出す。

## 決めたこと

招待の内容を見る API を `POST /api/invitations/lookup`、参加する API を `POST /api/invitations/accept` とし、招待の文字列を要求の本文(`{ "token": "..." }`)で渡す。

## 理由

- 要求の本文は、サービスも入口も記録に出さない決まりである(「共通設計: サービスの共通構成」の 4.6)。本文で渡せば、秘密の値をログに出さない決まりを、入口の記録の書式に頼らずに守れる。
- パスは、入口のほかにも、その手前に置く仕組み(配置した先の負荷分散の装置など)の記録に残ることがある。どの仕組みを置くかは、まだ決まっていない。
- パスが決まった文字列になるので、サービスの要求の記録と、入口の記録を、パスごとに数えられる。
- 画面は、招待の文字列を URL に使える形に変換しなくて済む。

## 却下した案

- **パスに入れたまま、入口の記録の書式からパスの後ろを外す**: 要件定義のとおりで、内容を見る API を `GET` にできる。入口の設定を 1 つ誤ると、秘密の値が記録に残る。手前に仕組みを足すたびに、同じ設定が要る。
- **ヘッダーで渡す(`X-Invitation-Token`)**: `GET` のままにできる。ヘッダーを記録に出さない決まりは同じだが、ヘッダーをまとめて記録に出す設定は、本文を出す設定よりも使われやすい。独自のヘッダーを足すことにもなる。
- **クエリで渡す**: パスと同じに、記録に残る。

## 影響

- 要件定義の 8 章の表を直した。
- 内容を見るだけの API が `POST` になる。画面は、この API を読み取りとして扱い、通信の失敗のときに自動でやり直す(「機能設計: 招待と共有」の 3.2)。「共通設計: 画面の共通仕様」の 4.3 は `POST` を操作としているので、ここだけが違う。
- 「画面設計: 画面の一覧と遷移」の 3.6、7 章、8 章の、API のパスを直した。
- 決定の記録 0031 の「影響」のうち、「招待の文字列は、招待の API のパスには入る」は、この記録で置き換えた。
- 入口の記録に出るパスを隠す設定は、要らなくなった。
- 後から、招待の内容をログインなしで見せることにしたときも、本文で渡す形のままでよい。
