# 0064 API の仕様を、パスの始まりで 2 つに分ける

決めた日: 2026-10-25

## 状況

API の仕様は、コードから SmallRye OpenAPI で書き出す(「共通設計: API の共通仕様」の 4.11)。
外に出す `/api` と、サービスの間だけで使う `/internal` は、別の仕様に分ける。
画面側の型に、使わない API が混ざらないようにするためである。
Quarkus の 3.40 は、1 つのサービスから名前付きの仕様を複数書き出せる。
どの入口をどちらの仕様に入れるかを、何で決めるかを選ぶ必要があった。
あわせて、エラーの形 `ErrorResponse` を、どの操作にどう載せるかも決める必要があった。

## 決めたこと

共通のライブラリのフィルターが、パスの始まり(`/api/` と `/internal/`)で入口を振り分ける。
同じフィルターの仲間が、すべての操作のエラーの応答(`default`)を `ErrorResponse` に向ける。

## 理由

- 入口のパスの始まりは、置き場の決まり(`/api` と `/internal`)そのものである。印を別に付けないので、付け忘れが起きない。
- 新しい入口は、パスを決めれば、正しい仕様に入る。
- エラーは入口で組み立てず、共通の部品が返す。エラーの応答も共通の部品が仕様に載せると、3 つのサービスで同じ定義になる。

## 却下した案

- **入口ごとに、注釈でどちらの仕様かの印(Quarkus の profile)を付ける**: Quarkus の標準のやり方である。印を付け忘れた入口は、両方の仕様に入る。`/internal` の入口が画面側の型に混ざる。
- **仕様を 1 つ書き出し、後から別の道具で 2 つに切り分ける**: 書き出しの後に手順が 1 つ増える。CI で、コードと仕様を比べるときにも、同じ手順が要る。
- **入口ごとに、エラーの応答を注釈で書く**: エラーの状態ごとに注釈が増え、書き忘れると型から抜ける。

## 影響

- 仕様は、ビルドのたびに `api/<サービス名>.yaml` と `api/<サービス名>-internal.yaml` に書き出される。同じ中身の `.json` も書き出されるが、コミットしない(`api/.gitignore`)。
- ビルドするコンテナ(`services/compose.yaml` の `maven` と `auth-service`)に、`api/` を渡す。
- 各サービスの設定に、名前付きの仕様 `internal` を書く。書かないと、フィルターの指す仕様がないとして、ビルドが失敗する。
- 入力の長さの決まりは、値オブジェクトが持つ。独自の検証の注釈は仕様に出ないので、入力の型に `@Schema` で、値オブジェクトの定数を書く。
- 仕様は、管理用のポート(9000)の `/q/openapi` と `/q/openapi-internal` でも返る。このポートは入口から届かない。
- Quarkus が、名前付きの仕様とフィルターの選び方を変えたときは、この決定を見直す。
