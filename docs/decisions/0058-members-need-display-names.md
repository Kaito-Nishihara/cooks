# 0058 表示名を取れないときは、メンバーの一覧を返さない

決めた日: 2026-10-11

## 状況

メンバーの一覧と、招待の確認の画面には、表示名が要る。
表示名は `auth-service` が持ち、`book-service` は自分のデータベースに写さない(要件定義の 6 章)。
`book-service` は、要るたびに `auth-service` の `GET /internal/users` を呼ぶ。

この呼び出しが失敗したときに、メンバーの一覧をどう返すかを決める必要があった。
「機能設計: 登録とログイン」は、この点を「機能設計: 招待と共有」に任せている。

## 決めたこと

表示名を取れないときは、一覧を返さず、503 と `DEPENDENCY_UNAVAILABLE` を返す。
役割を変える API と、招待の内容を見る API も、同じにする。

## 理由

- 持ち主は、メンバーの一覧を見て、役割を変え、メンバーを外す。名前のない一覧では、どの行が誰かが分からず、違う人を外すおそれがある。外す操作は取り消せない。
- 招待の確認の画面は、「誰のレシピ帳に参加するか」を確かめるためのものである。持ち主の名前がないと、確かめられない。
- `auth-service` が止まっているときは、入口がログインを確かめられず、どの要求も 503 になる。`book-service` に要求が届いたのに、表示名だけが取れない、という場面は、短い間しか起きない見込みである。その短い間のために、応答の形を増やさない。
- ほかのサービスの呼び出しと同じ動き(「共通設計: サービスの共通構成」の 6.4)になる。画面も、ほかの 503 と同じに、自動でやり直してから「もう一度」を出す。

## 却下した案

- **表示名を `null` にして、一覧を返す**: `auth-service` が応答しなくても、人数と役割は見える。上の理由のとおり、名前のない行に対する操作が危ない。画面に「名前を取れなかった」ときの出し方と、操作を止める決まりが要る。消されたアカウント(応答に含まれない識別子)の `null` と、区別も付かない。
- **表示名を `book-service` のデータベースに写しておく**: `auth-service` を呼ばずに済む。ほかのサービスが持つ情報を写さない決まりに反する。表示名を変える機能を足したときに、写しを直す仕組みが要る。
- **表示名を `book-service` のメモリに、短い間だけ覚えておく**: 呼ぶ回数が減り、短い間の失敗をしのげる。メンバーは 20 人までで、呼ぶのは 1 回なので、減らす利点が小さい。覚えた値が古くなる場合の扱いが増える。

## 影響

- `GET /api/books/{bookId}/members`、`PATCH /api/books/{bookId}/members/{userId}`、`POST /api/invitations/lookup` は、`auth-service` が応答しないと 503 を返す。
- メンバーを外す、抜ける、招待を作る、招待の一覧、招待を取り消す、参加する、の 6 つは、`auth-service` を呼ばない。入口がログインを確かめられる間は、働く。
- `auth-service` が、ある識別子を応答に含めなかったとき(消されたアカウント)は、失敗ではない。その人の `displayName` を `null` にして返し、画面は「(名前のない利用者)」と出す。
- 短い間の失敗が、実際に利用者の目に付くようであれば、メモリに覚えておく案を見直す。
