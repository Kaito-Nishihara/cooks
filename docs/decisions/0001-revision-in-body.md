# 0001 改訂番号を要求の本文で渡す

決めた日: 2026-10-10

## 状況

レシピの編集内容と献立は、複数の人が同時に編集することがある。
後から保存した人が、先に保存した人の内容を黙って上書きしないようにする必要がある。
そのために、保存の要求がどの時点の内容をもとにしているかを、画面からバックエンドへ伝える方法を決める。

## 決めたこと

改訂番号(`revision`)を整数で持ち、保存の要求の本文に入れて渡す。
合わないときは 409 と `REVISION_CONFLICT` を返す。

## 理由

- 画面側の型を OpenAPI の仕様から生成するので、本文の項目にしておけば、渡し忘れを型検査で止められる。
- 応答の本文にも同じ項目があるので、取得した値をそのまま次の保存に使える。
- 整数なので、ログやテストで前後の関係が読み取りやすい。

## 却下した案

- **`ETag` と `If-Match` のヘッダーで渡す**: HTTP の標準のやり方で、合わないときの状態は 412 になる。ヘッダーは生成した型に必須の項目として現れにくく、渡し忘れを型検査で止めにくい。要件定義が 409 と決めている点とも合わない。
- **更新日時で比べる**: 同じ秒のうちに 2 回保存されると区別できない。時計のずれの影響も受ける。
- **比べずに後から保存した内容で上書きする**: 作りは一番簡単だが、相手の変更が知らないうちに消える。要件定義の「黙って上書きしない」に反する。

## 影響

- 編集内容と献立のテーブルに、改訂番号の列を持つ。
- 画面は、取得した改訂番号を持ち続け、保存のたびに応答の番号で置き換える。
- 外部の道具(キャッシュ、プロキシ)が `ETag` を使って同じ判定をすることはできない。必要になったら、ヘッダーも合わせて返す形に広げる。
