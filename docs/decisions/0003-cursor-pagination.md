# 0003 一覧をカーソルで分けて返す

決めた日: 2026-10-10

## 状況

一覧を返す API が、該当するものをどう返すかを決める。
当初は、件数に上限があるので全件を一度に返す案だった。
利用者から、一覧は分けて返すべきだという指摘があり、分けて返すことにした。
ここでは、その分け方を決める。

## 決めたこと

続きの位置を示す文字列(カーソル)で分ける。
要求は `limit` と `cursor`、応答は `items` と `nextCursor` とする。

## 理由

- 取得の途中でデータが増えたり減ったりしても、同じものが 2 回出たり、抜けたりしない。メンバーや編集済みのレシピは、ほかの人が同時に変えることがある。
- 何件目から読むかを数え直さないので、後ろのほうを取るときも速さが変わらない。
- 識別子に UUID のバージョン 7 を使うので、作った順に並べるときに、そのまま並び順の値として使える。

## 却下した案

- **全件を一度に返す**: 作りは一番簡単である。件数の上限を引き上げたときに、応答が大きくなり、すべての画面を直すことになる。利用者の指摘で取り下げた。
- **ページの番号で分ける(`page` と `size`)**: 「3 ページ目へ飛ぶ」ができ、分かりやすい。取得の途中で 1 件が消えると、次のページの先頭の 1 件が前のページへずれて、画面に出ないまま抜ける。足されると、同じものが 2 回出る。
- **何件目からかで分ける(`offset` と `limit`)**: ページの番号と同じ弱点がある。後ろのほうを取るほど、読み飛ばす分だけ遅くなる。

## 影響

- 「3 ページ目へ飛ぶ」「全部で何ページか」は出せない。画面は「続きを読み込む」の形にする。
- 並び順を API ごとに固定する。画面から並び順を選ぶ機能は作れない。必要になったら、並び順ごとにカーソルの中身を変える形に広げる。
- 全件が要る画面(一覧で編集済みの印を付けるとき)は、続きがなくなるまで繰り返し呼ぶ。繰り返しは API を呼ぶクライアントにまとめる。
- 件数の上限(レシピ帳、メンバー、招待、編集済みのレシピ)は残す。ページ分けとは別に、増えすぎを防ぐためである。
