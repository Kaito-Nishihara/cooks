# 0005 サービスの間では、署名付きトークンで本人を伝える

決めた日: 2026-10-10

## 状況

ログインの状態は、`auth-service` のセッションで持つ(決定の記録 0004)。
`book-service` と `kitchen-service` は、要求を送ってきた人が誰かを知る必要がある。
セッションを知っているのは `auth-service` だけなので、ほかのサービスへ本人を伝える方法を決める。

## 決めたこと

入口が、要求を後ろへ渡す前に `auth-service` にクッキーを確かめさせる。
`auth-service` は、利用者の識別子を書いた署名付きトークン(JWT、期限は 60 秒)を返す。
入口はそれを要求に付けて後ろへ渡し、各サービスは署名を確かめて本人を特定する。

## 理由

- 各サービスは、公開の鍵で署名を確かめるだけで済む。要求のたびに `auth-service` へ問い合わせない。
- 署名があるので、途中で利用者の識別子を書き換えられない。
- セッションの確認を入口の 1 か所で行うので、どのサービスにも同じ決まりが効く。サービスごとに確認を書き忘れることがない。
- 期限が 60 秒なので、ログアウトの後に使い回せる時間が短い。

## 却下した案

- **各サービスが、クッキーを受け取って `auth-service` に問い合わせる**: 仕組みは単純である。すべてのサービスがクッキーに触ることになり、確認の書き忘れが起きうる。サービスがほかのサービスを呼ぶたびに、問い合わせが重なる。
- **入口が、利用者の識別子をただのヘッダー(`X-User-Id`)で渡す**: 署名の確認が要らず、一番簡単である。入口を通らずにサービスへ届く経路が 1 つでもあると、誰にでもなりすませる。クラスタの中の通信をすべて信用する前提になる。
- **セッションを 3 つのサービスで共有するデータベースに置く**: 問い合わせが要らなくなる。サービスごとにデータベースを分けるという決まりを破る。

## 影響

- `auth-service` が、署名の鍵の組を持ち、公開の鍵を配る。鍵の入れ替えの手順が要る。
- 入口に、後ろへ渡す前に別のサービスへ確認を任せる機能が要る。入口の製品を選ぶときの条件になる。
- 入口は、ブラウザから届いた `Authorization` ヘッダーを捨てる必要がある。捨て忘れると、偽のトークンが後ろへ届く。偽のトークンは署名の確認で落ちるが、入口の設定をテストで確かめる。
