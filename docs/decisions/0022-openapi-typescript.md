# 0022 画面側の型を openapi-typescript で作り、API を呼ぶ関数は手で書く

決めた日: 2026-10-11

## 状況

画面側の型は、各サービスの OpenAPI の仕様(`api/<サービス名>.yaml`)から作り、手で書かない(要件定義の 6 章)。
仕様から何を作るかには幅がある。
型だけを作る道具と、API を呼ぶ関数や、取得の仕組みまで作る道具がある。
どこまでを道具に作らせるかを決める。

## 決めたこと

openapi-typescript で、仕様から TypeScript の型だけを作る。
API を呼ぶ関数は、サービスごとのファイル(`src/api/auth.ts` など)に手で書き、名前を仕様の `operationId` と同じにし、引数と戻り値には作った型を使う。

## 理由

- 作られるのは型だけで、実行されるコードが増えない。要求を送る処理は `src/api/client.ts` の 1 つの関数だけになり、エラーの形の読み取り、期限、要求の識別子の取り出しを、そこで確実に行える。
- 関数を手で書いても、型は仕様から来る。API の入力や出力が変わると、型検査が失敗して気づける。
- 関数ごとの事情を書ける。例: 改訂番号を持つものの取得は、404 を「まだ保存されていない」として `null` で返す(「共通設計: 画面の共通仕様」の 4.1)。
- API は 20 個ほどで、関数を手で書く量は多くない。

## 却下した案

- **関数まで作る道具(Orval、Hey API など)を使う**: 関数を書く手間がなくなり、`operationId` と関数の名前が機械的にそろう。要求を送る部分も作られるので、エラーの扱いを差し込むには、道具ごとの差し替えの仕組みに合わせる必要がある。作られるコードが多く、道具の版を上げたときの差分が大きくなる。
- **openapi-fetch を使い、パスの文字列で呼ぶ**: 型だけを作る点は同じで、関数を書かずに `client.PUT("/api/books/{bookId}/...")` の形で呼べる。呼ぶ場所にパスの文字列が散らばり、`operationId` を関数の名前にするという決まり(「共通設計: API の共通仕様」の 4.11)と合わない。
- **型を手で書く**: 仕様と食い違っても気づけない。要件定義が禁じている。

## 影響

- API を足したら、型を作り直し、関数を 1 つ手で足す。足し忘れた API は、画面から呼べないだけで、誤った呼び出しにはならない。
- 関数の名前が `operationId` と同じであることは、機械的には保証されない。レビューで確かめる。
- 型を作るコマンドは、開発の土台を作るときに決め、`CLAUDE.md` に書く。Node は Docker のコンテナの中で動かす。
- 仕様の書き方によって、作られる型が使いにくいことがある(`null` を許す項目など)。開発の土台で `auth-service` の仕様から実際に作って確かめる。使えないと分かったら、この記録を新しい記録で置き換える。
