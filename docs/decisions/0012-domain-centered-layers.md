# 0012 サービスを、ドメインを中心にした層で作る

決めた日: 2026-10-11

## 状況

サービスの中の、コードの分け方を決める。
利用者から、ドメインを中心にした構成で実装するという指示があった。

## 決めたこと

サービスを、入口、ユースケース、ドメイン、基盤の 4 つの層に分け、業務の決まりをドメインに集める。
ドメインは、Quarkus にも、データベースにも、HTTP にも頼らない Java だけで書く。

## 理由

- 業務の決まり(役割ごとにできること、期限、上限)が 1 か所に集まる。決まりを変えるときに、探す場所が決まっている。
- ドメインは、起動もデータベースも要らずにテストできる。場合分けの多い決まりを、速く、数多く確かめられる。
- 枠組みやデータベースを替えても、ドメインは変わらない。
- 層の間の頼る向きを、テストで機械的に確かめられる。AI に実装させるときに、決まりを破るコードが入ったら、テストが止める。
- 広く使われている設計の考え方を、実際の規模のアプリで経験できる。

## 却下した案

- **入口、業務、保存の 3 層にし、テーブルの行に対応するクラスをそのまま業務で使う**: クラスの数が少なく、書く量が減る。Quarkus の Panache が想定する書き方に近い。業務の決まりが、データベースの注釈が付いたクラスと、業務のクラスの `if` とに散らばる。テストに、いつもデータベースが要る。
- **層ごとに Maven の部品を分け、頼る向きをビルドで禁じる**: 決まりを破ると、コンパイルが通らなくなる。1 つのサービスが 4 つの部品になり、3 つのサービスで 12 個になる。同じことを、依存を調べるテストで確かめられる。
- **すべての外とのやり取りに約束を置く(ポートとアダプターを徹底する)**: 入口の側にも約束を置き、どこからでも差し替えられるようにする。入口は HTTP の 1 種類だけなので、差し替える場面がない。約束を置くのは、ドメインとユースケースが外を使うところ(リポジトリと、ほかのサービスの呼び出し)に限る。

## 影響

- 集約と、テーブルの行に対応するクラスを別に持つので、互いに変えるコードが要る。3 層の案より、書く量が増える。
- 「バックエンドは薄く保つ」という要件(6 章)は変わらない。栄養計算や分量の換算をドメインに持ち込まない。ドメインに書くのは、権限、期限、上限、改訂番号の決まりである。
- 編集内容や献立のように、決まりが少なく、ほぼ「受け取って保存する」だけの機能では、ドメインのクラスが小さくなる。小さくても、層を飛ばさない。機能ごとに構成を変えると、どこに何があるかが分からなくなるためである。
- 層の決まりは、依存を調べるテスト(ArchUnit)で守る。
