# 0025 材料、手順、コツに、レシピの中で変わらない識別子を付ける

決めた日: 2026-10-11

## 状況

編集内容は、元のレシピに重ねる形で持つ(要件定義 4.5)。
利用者は、材料と手順とコツを、直す、足す、消す、並べ替えることができる。
元のレシピも、後から Claude Code が直すことがある。
編集内容が「元のレシピのどの行を直したのか」を、どう指すかを決める必要があった。

## 決めたこと

元のレシピの、材料のグループ、材料、手順、コツの 1 行ずつに、種類を表す 1 文字と数からなる識別子(`g1`、`i1`、`s1`、`t1`)を付け、一度付けたら変えず、消しても使い回さない。

## 理由

- 並び順が変わっても、行が足されても、同じ行を指し続けられる。
- 元のレシピが更新されたときに、「どの行が変わったか」「編集した行が元から消えたか」を、行ごとに判定できる。
- 短く、人が読める。Claude Code が JSON を直すときに、どの行のことかを取り違えにくい。
- 編集内容を、行ごとの差分で持つ場合にも、直した後の全体で持つ場合にも使える。持ち方は Issue #12 で決めるので、どちらにも使える形にしておく。

## 却下した案

- **並び順の番号で指す**: 識別子の項目が要らない。元のレシピに行が 1 つ足されるだけで、編集内容の指す先がずれる。ずれたことに、誰も気づけない。
- **内容から作る(材料の名前や、内容のハッシュ)**: 番号を振る手間がない。名前を「鶏もも肉」から「鶏もも肉(皮つき)」に直しただけで、別の行になる。同じ材料を 2 つのグループに書くと、重複する。
- **乱数の文字列(UUID など)**: 使い回しが起きない。Claude Code が書く「乱数」は、乱数である保証がない。長く、差分が読みにくい。
- **レシピに「次に使う数」の項目を持つ**: 消した行の数を、ファイルだけで覚えておける。項目が増え、その項目の直し忘れという別の誤りが生まれる。使い回しを仕組みで止める方法は、CI で `main` の版と比べる検証として、段階 0 で決める。

## 影響

- 元のレシピの JSON に、行ごとの `id` が増える。
- `recipe` スキルは、レシピを直すときに、`id` を変えない、使い回さない、という決まりを守る。
- `check:data` は、形と重複を確かめる。過去の版との使い回しは、今は確かめない。
- 使い回しが起きると、古い編集内容が、別の行を直したり消したりする。編集内容の持ち方(Issue #12)を決めるときに、この影響を小さくできるかを検討する。
- `u` で始まる識別子は、利用者が足した行のために空けておく。
- データベースの JSON の中に入る「リポジトリのファイルを指す識別子」が、`slug` と食材マスタの識別子に加えて、1 種類増える。
