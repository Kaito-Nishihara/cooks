# 0057 招待の文字列を 256 ビットの乱数にし、SHA-256 のハッシュで持つ

決めた日: 2026-10-11

## 状況

要件定義の 4.7 は、招待のリンクの文字列を「推測できない長さの乱数」とし、データベースにはハッシュだけを保存すると決めている。
期限は 7 日、使えるのは 1 回である。

長さ、文字の種類、ハッシュの方式、当てずっぽうに試されたときの守り方を決める必要があった。

## 決めたこと

暗号に使える乱数で 32 バイト(256 ビット)を作り、URL に使える Base64 で 43 文字にする。
データベースには、SHA-256 のハッシュを 16 進数 64 桁で保存し、ハッシュで行を探す。

## 理由

- セッションの識別子と同じ作り方である(「共通設計: 認証」の 4.3)。作る処理と、ハッシュにする処理を、共通のコードの 1 つにできる。秘密の値の作り方が 1 通りになり、確かめる場所が減る。
- 256 ビットあれば、当てずっぽうに試して当たる見込みはない。試した回数を数えて受け付けなくする仕組みを、持たなくて済む。
- 使う文字が、英数字、`-`、`_` だけである。URL のフラグメントにそのまま置け、メッセージのアプリで送っても、途中で切れたり書き換わったりしにくい。
- 画面は、形(43 文字と文字の種類)を見て、写しそこねたリンクを、API を呼ばずに見分けられる。
- SHA-256 は、同じ値からいつも同じハッシュができる。受け取った文字列をハッシュにして、一意のインデックスで 1 行を探せる。
- 元の値が長い乱数なので、ハッシュから総当たりで元に戻すことはできない。パスワードのような遅い方式は要らない。

## 却下した案

- **短い文字列にする(8 文字ほどの英数字)**: 口頭でも伝えられ、手で打てる。試して当てられる長さになり、失敗の回数を数えて受け付けなくする仕組みが要る。リンクを写して渡す使い方では、短さの利点がない。
- **招待の識別子(UUID)をそのまま使う**: 作る処理が要らない。UUID のバージョン 7 は、先頭が作った時刻で、乱数の部分が短い。識別子は一覧の応答やログに出すものなので、秘密の値と兼ねられない。
- **bcrypt でハッシュにする**: データベースが漏れたときに、元に戻しにくい。塩が行ごとに違うので、ハッシュで行を探せない。招待の識別子を一緒に渡す形になり、リンクが長くなる。元の値が 256 ビットの乱数なので、遅い方式にする利点もない。
- **署名付きのトークン(JWT)にして、データベースに持たない**: 行を探さずに、中身を確かめられる。取り消しと「1 回だけ」を確かめるには、結局、行が要る。

## 影響

- `invitations` の `token_hash` は `char(64)` で、一意の制約を持つ。
- 招待の文字列は、作ったときの応答でだけ返す。後から、もう一度出すことはできない。渡しそこねたら、取り消して作り直す。
- 1 つの招待を何人でも使えるようにする(家族の全員に、同じリンクを渡す)ことは、していない。要件定義が 1 回と決めているためである。要るようになったら、要件定義を直し、`used_by` と `used_at` の持ち方を見直す。
- 期限の 7 日は、設定(`app.invitation.ttl-days`)で持つ。
- 配置した後に、試す要求が実際に来て負荷になるようであれば、入口で要求の数を絞ることを考える。
