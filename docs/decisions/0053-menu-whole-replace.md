# 0053 献立の保存は、その日の全体を置き換える

決めた日: 2026-10-11

## 状況

献立への操作は、料理を 1 品足す、外す、食事を移す、ご飯を 1 杯増やす、のように小さいものが多い。
献立はレシピ帳のメンバーが共有するので、2 人が同じ日の献立を同時に変えることがある。
保存の API を、その日の献立の全体を置き換える形にするか、操作ごとの形にするかを決める必要があった。

## 決めたこと

保存は `PUT /api/books/{bookId}/menus/{day}` の 1 つとし、改訂番号を付けて、その日の献立の全体を置き換える。
操作ごとの API は作らない。

## 理由

- 要件定義の 4.6 が「同時に編集したときの扱いは 4.5 と同じにする」と決め、8 章が献立の保存を `PUT` と改訂番号で書いている。レシピの編集と同じ形にすると、要件定義を変えずに済む。
- 改訂番号、409、`ConflictDialog`、自動保存の処理を、レシピの編集と献立で 1 つずつ持てば足りる(「共通設計: API の共通仕様」の 4.10、「共通設計: 画面の共通仕様」の 3.7 と 4.5)。
- 要件定義の 2.2 が、複数人が同時に入力した内容を自動で統合することを、対象にしないと決めている。操作ごとの API は、2 人の操作をバックエンドが順に当てるので、自動で統合する作りになる。
- 献立は小さい。30 品とご飯の杯数で 2KB ほどの見込みで、全体を送っても重くない。
- 献立の画面では、ご飯のボタンを続けて押すような操作を、1 回の保存にまとめられる。

## 却下した案

- **操作ごとの API(料理を足す `POST`、外す `DELETE`、食事を移す `PATCH`、ご飯の杯数を変える `PUT`)**: 2 人が同時に別の料理を足しても、どちらも 409 にならずに入る。API が 4 つ以上に増え、それぞれに 5 通りの立場の確認が要る。「すべて外す」と、ほかの人の「足す」が前後したときの結果を、利用者が予想しにくい。要件定義の 4.6 と 8 章を直す必要がある。
- **全体の置き換えと、料理を足す操作だけの API を両方持つ**: いちばん多い「足す」だけが衝突しなくなる。保存の道が 2 つになり、改訂番号を進める決まりを 2 か所に書くことになる。
- **改訂番号を持たず、後から来た保存で上書きする**: 作りは最も簡単である。ほかの人が足した料理が、黙って消える。要件定義の 4.5 の「黙って上書きしない」に反する。

## 影響

- 2 人が同時に同じ日の献立を変えると、後から届いた保存が 409 になる。献立の画面では `ConflictDialog` で選び、レシピ一覧と詳細の「献立に追加」では、通知を見て押し直す(「機能設計: 今日の献立」の 3.9)。
- 「献立に追加」は、押した時点の最新の献立を取得してから保存する。開いたままの画面の古い改訂番号で、409 が続くのを防ぐためである。
- 画面は、自分が知らない slug の料理も、保存のときにそのまま送る必要がある。捨てると、ほかの人が足した料理を消す(同 3.8)。
- 同時に変える場面が多く、押し直しが負担になると分かったら、料理を足す操作だけを自動でやり直すか、操作ごとの API を足すかを見直す。
