# 0050 編集内容の単位と識別子は、バックエンドで形だけを検証する

決めた日: 2026-10-11

## 状況

入力値は、画面とバックエンドの両方で検証する(要件定義 4.5)。
編集内容には、単位(`g`、`大さじ` など 15 種類)、食材マスタの識別子、元のレシピの行の識別子が入る。
これらの一覧は、リポジトリのファイル(`data/`)と、画面のスキーマ(`frontend/src/schema/`)にある。
`kitchen-service` は、元のレシピも食材マスタも持たない(「データ設計」の 6 章)。

「データ設計」は、単位の一覧を `kitchen-service` でも検証するかどうかを、この機能の設計に回した。
検証するなら、一覧を Java と TypeScript の 2 か所に持つことになる。

## 決めたこと

`kitchen-service` は、単位、食材マスタの識別子、行の識別子、レシピの slug について、文字の種類と長さだけを確かめ、一覧にあるかどうかは確かめない。

型、必須、文字数、件数、数の範囲、行の中の組み合わせ(分量は数と単位か、表記のどちらか一方)は、`kitchen-service` が確かめる。
範囲は「機能設計: レシピ帳とレシピの編集」の 4.10 に書いた。

## 理由

- 一覧を 1 か所だけに持てる。単位を足すときに、Java の一覧を直し忘れて、画面から選べる単位が保存できない、という食い違いが起きない。
- 食材マスタの識別子と行の識別子は、すでに形だけを確かめると決めている。単位だけを一覧で確かめても、守れる範囲が増えない。
- 一覧にない単位が保存されても、壊れる範囲が小さい。その材料は、換算率が引けないので栄養計算から除かれ、「概算値」と出る。編集の画面では、単位の欄にエラーが出て、選び直すまで保存できない。影響は、その人が編集できるレシピ帳の、その 1 行に留まる。
- バックエンドが守るべきものは、権限、大きさの上限、読めない形のデータを入れないこと、である。この 3 つは、形の検証で守れる。

## 却下した案

- **単位の一覧を Java にも持って検証する**: API を直接呼んでも、一覧にない単位を保存できなくなる。一覧が 2 つの言語に分かれ、直し忘れを仕組みで止めるには、2 つを比べる検証が別に要る。
- **単位の一覧を、ビルドのときに `data/` から Java へ生成する**: 一覧は 1 か所になる。単位の一覧は、今は画面のスキーマにあり、`data/` のファイルにはない。サービスのビルドが、画面のコードかデータのファイルに頼ることになる。
- **`kitchen-service` に元のレシピと食材マスタを持たせ、指す先まで確かめる**: 存在しないレシピや食材を指す編集内容を拒める。画面とサービスで、別の版のデータを見ることが起きる(「データ設計」の 6 章)。

## 影響

- API を直接呼べば、一覧にない単位、存在しない食材の識別子、存在しないレシピの slug の編集内容を保存できる。保存できる件数は、レシピ帳ごとの上限(1,000 件)で抑える。
- 重ねる処理と編集の画面は、一覧にない単位と、指す先のない識別子を受け取っても、止まらずに表示する作りにする。
- 単位を足すときに直すのは、画面のスキーマと「データ設計」の表だけである。サービスは作り直さなくてよい。
- 一覧にない値が、実際に保存されることが続くようなら、この記録を見直す。
