# 0009 サービスに共通するコードを 1 つのライブラリにまとめる

決めた日: 2026-10-11

## 状況

3 つのサービスは、エラーの形、例外の変換、要求の識別子、ログの項目、トークンからの本人の特定を、同じ動きにする必要がある。
同じ動きをするコードを、どこに持つかを決める。

## 決めたこと

業務に関わらない共通のコードを、`services/service-common` という 1 つのライブラリにまとめ、3 つのサービスがそれを使う。

## 理由

- エラーの形やログの項目は、3 つのサービスで同じでなければならない。1 か所にあれば、食い違わない。
- 直すときに、1 か所を直せば 3 つに反映される。
- 共通のコードのテストを、1 回書けば済む。

## 却下した案

- **各サービスの中に、同じコードを写して持つ**: サービスが、ほかのサービスのビルドに左右されなくなる。マイクロサービスの「共有しない」という考え方には、こちらが忠実である。3 か所を同じように直し続ける必要があり、1 か所だけ直し忘れると、サービスごとにエラーの形が変わる。AI に実装させるときにも、写しの 1 つだけが変わる誤りが起きやすい。
- **Quarkus の拡張として作る**: Quarkus が用意する、機能を足すための正式な形である。作るのに覚えることが多く、今の量のコードには大きすぎる。
- **共通のコードを、別のリポジトリで版を付けて配る**: サービスごとに、使う版を選べる。リポジトリが 1 つで、3 つのサービスを一緒に配置するので、版を選ぶ必要がない。

## 影響

- `service-common` を変えると、3 つのサービスをすべて作り直し、テストし直すことになる。
- 業務のコードを置くと、あるサービスの都合が、ほかのサービスに広がる。置いてよいものを「共通設計: サービスの共通構成」の 4.3 に限る。
- コンテナのイメージを作るときに、サービスのディレクトリだけでなく、`services/` の全体を材料にする必要がある。
- サービスを別のリポジトリへ分けるとき、または、サービスごとに違う版を使う必要が出たときに、見直す。
