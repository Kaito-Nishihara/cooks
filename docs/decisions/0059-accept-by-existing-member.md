# 0059 すでにメンバーの人が招待を受けても、役割を変えず、招待を使わない

決めた日: 2026-10-11

## 状況

招待のリンクは、持ち主が自分で相手に渡す。
リンクを開くのは、招待された人とは限らない。
次の場合がある。

- 持ち主が、作ったリンクを自分で開いて確かめる。
- すでにメンバーである人が、別の役割の招待を開く。
- 参加に成功した人が、応答が届かなかったために、もう一度「参加する」を押す。

「画面設計: 画面の一覧と遷移」は、この場合の動きを「機能設計: 招待と共有」に任せていた。

## 決めたこと

すでにメンバーである人(持ち主を含む)が招待を受けたときは、役割を変えず、招待を使わず、200 と今の役割を返す。
応答の `isNewMember` を `false` にして、新しく参加した場合と区別する。
招待の内容を見る API は、呼んだ人の今の役割(`currentRole`)を返し、画面は「参加する」を出さない。

## 理由

- 役割を変えるのは、持ち主がメンバーの一覧から行う操作だけにする。役割が変わる道筋が 1 つになり、確かめやすい。
- 編集できる人が、見るだけの招待を開いても、役割が下がらない。
- 持ち主が自分で開いて確かめただけで、相手に渡した招待が使えなくなることがない。
- 同じ人が同じ招待を 2 回送っても、結果が同じになる。応答だけが届かなかったときに、利用者に「この招待は使えません」と見せずに済む。
- エラーの `code` を足さずに済む。

## 却下した案

- **招待の役割で、今の役割を置き換える**: 招待を、役割を上げる手段としても使える。編集できる人が、見るだけの招待を誤って開くと、役割が下がる。「高いほうにだけ変える」とすれば防げるが、決まりが 1 つ増える。役割を上げたいときは、持ち主が一覧から変えれば足りる。
- **409 と、新しい `code`(`ALREADY_MEMBER`)で拒む**: すでにメンバーであることが、はっきり伝わる。`code` の一覧と、画面の `code` ごとの動きに、1 行ずつ足すことになる。利用者から見れば、目的(そのレシピ帳を使える状態になる)は達しているので、失敗として見せる理由が薄い。
- **招待を使用済みにする**: 「1 回使うと無効」の決まりを、文字どおりに守れる。持ち主が確かめただけで、相手に渡したリンクが使えなくなる。

## 影響

- 参加する API の応答に `isNewMember` を持つ。内容を見る API の応答に `currentRole` と `bookId` を持つ。
- 招待の確認と参加の画面に、「すでにメンバー」と「持ち主」の 2 つの状態を足した。「このレシピ帳を開く」で、そのレシピ帳へ切り替える。
- 使用済みの招待の行を、期限が過ぎるまで残す。使った人自身がもう一度送ったときに、成功を返すためである。
- 今とは別のアカウントで参加したい人のために、確認の画面に「別のアカウントで参加する」を置く。ログアウトしてから、招待の文字列をフラグメントに付けたまま、ログインの画面へ移る。
