# 0021 API から取った内容を TanStack Query で持つ

決めた日: 2026-10-11

## 状況

画面は静的に書き出し、ページを開いた後にブラウザから API を呼ぶ。
そのため、どの画面にも、読み込み中、エラー、取り直し、やり直しの扱いが要る。
ログインの状態(`GET /api/me`)とレシピ帳の一覧(`GET /api/books`)は、ヘッダーと本文の両方が使うので、同じ要求を 2 回送らない仕組みも要る。
これらを、画面ごとに書くか、1 つの仕組みに任せるかを決める。

## 決めたこと

API から取った内容と、その取得の状態を、TanStack Query で持つ。
取得と保存の処理は `src/hooks/` に書き、ページと部品はそれを呼ぶ。

## 理由

- 読み込み中、エラー、成功の状態を、どの取得でも同じ形で受け取れる。「共通設計: 画面の共通仕様」の 3.7 の 4 つの状態を、画面ごとに組み立てずに済む。
- 同じ名前の取得は、同時に何か所から呼んでも要求が 1 回にまとまる。
- 取得のやり直しの条件(503 と通信の失敗のときだけ、2 回まで)を、1 か所に設定できる。
- 内容に名前を付けて持つので、レシピ帳を切り替えたときやログアウトしたときに、関わる内容をまとめて捨てられる。
- サーバー側の機能を使わない、ブラウザだけの構成で働く。
- React で API の取得を扱うときに、広く使われているやり方を経験できる。

## 却下した案

- **部品の中で `useEffect` と `useState` を使って、自分で書く**: 頼るものが増えない。読み込み中とエラーの扱い、要求のまとめ、古い応答が後から届いたときの扱いを、画面ごとに書くことになり、書き方がばらつく。
- **SWR を使う**: 取得については同じことができ、覚えることが少ない。保存の扱い(送信中の状態、成功の後に持っている内容を置き換えること)の仕組みが薄く、自動保存と改訂番号の扱いを自分で書く量が増える見込みである。
- **アプリ全体の状態を 1 つの置き場(Redux など)にまとめ、API の内容もそこに持つ**: 画面の間で状態を共有しやすい。このアプリで共有する状態は、ログインの状態と今開いているレシピ帳だけで、どちらも API の内容から決まる。置き場を別に持つと、API の内容と二重に持つことになる。
- **Next.js のサーバー側での取得を使う**: 静的に書き出すので使えない(要件定義の 6 章)。

## 影響

- 画面側が頼るライブラリが 1 つ増える。
- 入力中の画面で、取り直した内容が入力を上書きしないように、編集の画面では取り直した内容を入力へ反映しない決まりを置く(「共通設計: 画面の共通仕様」の 4.2)。
- 新しいとみなす時間(30 秒)と、やり直しの回数は、見込みで置いた。実装して見直す。
- ライブラリの版は、開発の土台を作るときに、その時点の安定版に決める。
