# 0052 保存の応答が届かなかったときは、取得した内容を比べて自分の保存かを見分ける

決めた日: 2026-10-11

## 状況

編集内容と献立は、改訂番号で、同時に編集したことを見つける(決定の記録 0001)。
画面が持っている改訂番号が古いと、保存は 409 と `REVISION_CONFLICT` で拒まれ、画面は「ほかの人が先に変更しました」と出して、相手の内容を読み込むか、自分の内容で上書きするかを選ばせる。

保存は成功したのに、応答だけが届かないことがある(期限切れ、通信の切断)。
画面は失敗として扱い、改訂番号を古いまま持つ。
利用者が「もう一度」を押すと、自分の保存に対して 409 が返り、いない相手の内容について選ばされる。

「共通設計: 画面の共通仕様」は、この扱いを、レシピの編集の設計に回した。

## 決めたこと

保存が、成功とも 400 番台の失敗とも分からない形で終わったときは、送った本文を覚えておき、次の保存が 409 になったら最新の内容を取得して、最後に保存した人、改訂番号、元にした版、内容が覚えておいたものと合うときは、自分の保存として扱い、ダイアログを出さない。

細かい順は、「機能設計: レシピ帳とレシピの編集」の 3.4 に書いた。
今日の献立も、同じ処理(`useAutoSave`)を使う。

## 理由

- 画面だけで直せる。API も、テーブルも変えない。
- 409 のときは、もともと最新の内容を取得する(上書きを選んだときに、取得を挟む決まりである)。取得を 1 回足すだけで、比べられる。
- 4 つの条件をすべて見るので、ほかの人の変更を、自分の保存と取り違えにくい。最後に保存した人が自分で、改訂番号がちょうど 1 つ進んでいて、内容が送ったものと同じ、という状態は、自分の保存が届いていたときにしか起きにくい。
- 取り違えた場合に失うものがない。内容が同じなので、どちらの保存だったとしても、保存されているものは、自分が送ったものと同じである。

## 却下した案

- **何もしない(いつもダイアログを出す)**: 作るものがない。通信が不安定なときに、1 人で使っている人が「ほかの人が先に変更しました」と出されて、選ばされる。
- **保存の要求に、要求ごとの識別子を付け、同じ識別子の 2 回目を、サービスが成功として返す**: 応答が届かなかった保存を、そのままやり直せる。サービスが、処理した識別子を覚えておく場所(列かテーブル)と、消す仕組みが要る。数人で使うアプリには重い。
- **取得した内容が、今の入力と同じなら保存済みとする(覚えておかない)**: 覚えておくものがない。応答が届かなかった後で利用者が入力を続けると、今の入力は、届いていた保存と違うので、ダイアログが出てしまう。
- **409 のときに、`details.currentRevision` をそのまま付けて送り直す**: 取得が要らない。確かめずに上書きする入口になる(「共通設計: API の共通仕様」の 4.10)。

## 影響

- 自動保存の処理(`useAutoSave`)が、「結果が分からない保存」の本文を 1 つ覚える。保存が 1 回成功するか、ダイアログを出した時点で忘れる。
- 取得の応答に、最後に保存した人の識別子(`updatedBy`)が要る。編集内容の API は、これを返す。献立の API も返す必要がある。
- 内容を比べる処理は、値がないことの表し方(`null` と、項目がないこと)をそろえてから比べる。
- 削除(「元に戻す」)の応答が届かなかったときは、もう一度送ると 404 になる。これは成功として扱う。
