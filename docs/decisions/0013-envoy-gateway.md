# 0013 入口に Envoy Gateway を使う

決めた日: 2026-10-11

## 状況

入口の製品を決める。
条件は、Gateway API に対応していることと、「共通設計: 認証」の 4.6 の決まり(後ろへ渡す前に `auth-service` に確かめさせる、返ってきたヘッダーで置き換える、クッキーを後ろへ渡さない)を満たせることである。
候補を kind の上で実際に動かして比べた。

## 決めたこと

Envoy Gateway を使う。
試した版は 1.9.2 である。

## 理由

2 つの候補に、同じ代役のサービスと同じ 12 通りの要求を使った。

| 確かめたこと | Envoy Gateway 1.9.2 | Traefik 3.7.14 |
|---|---|---|
| 後ろへ渡す前に確かめさせる | できた | できた |
| `Authorization` を置き換える | できた | できた |
| クッキーを後ろへ渡さない | できた | できた |
| 401 と 403 の本文をそのまま返す | できた | できた |
| 確かめられないときに拒む | できた | できた |
| そのときの状態を 503 にし、本文を決まった形にする | 設定でできた | 500 で本文なし。直すには、エラーの本文を返す別のサービスが要る |
| 入口が自分で応答を返す(稼働の確認、`/internal` の 404) | 設定でできた | 標準の機能にない。別のサービスか、追加の部品が要る |
| Compose で同じ設定ファイルを読む | できた | Compose 用に、別の書式で書き直す必要がある(試していない) |

- 決まりを、すべて設定だけで満たせた。
- 振り分けとログインの確認の設定を、kind と Compose で同じファイルにできた。要件定義の「どちらも同じ設定で動かす」を、そのまま満たす。
- 中身は Envoy で、広く使われている。

## 却下した案

- **Traefik**: 中心の決まりは満たした。確かめる要求は `GET` の決まったパスになり、元のメソッドとパスをヘッダーで渡すので、`auth-service` の側は作りやすい。入口が自分で応答を返す機能と、エラーの本文を決まった形にする機能が足りない。Compose では別の書式で設定を書くことになり、2 つの設定がずれる。
- **NGINX Gateway Fabric、Istio など**: 動かしていない。Istio は、サービスの間の通信まで受け持つ大きな仕組みで、今の規模には重い。

## 影響

- 入口が `auth-service` を呼ぶ形が、製品で決まる。元の要求と同じメソッドで、`/internal/auth/verify` の後ろに元のパスを付けて呼ぶ。「共通設計: 認証」の 4.6 を、これに合わせて直した。
- ログインの確認と、入口が返す応答は、Gateway API の標準ではなく、Envoy Gateway の書式で書く。製品を替えるときは、この部分を書き直す。
- Compose で Kubernetes なしに動かす形は、試作では動いた。長く使ったときの安定は、まだ分からない。不具合が続くときは、Compose の入口だけを見直す。
