# 0023 ログインが要る画面を、ブラウザの中の処理で守る

決めた日: 2026-10-11

## 状況

編集、献立、レシピ帳の設定、招待の画面は、ログインが要る(要件定義の 10 章)。
画面は静的に書き出したファイルで、入口は `/api` で始まらないパスではログインを確かめない(「共通設計: 認証」の 4.6)。
セッションのクッキーは、画面のスクリプトから読めない(`HttpOnly`)。
ログインしていない人がこれらの画面を開いたときに、どこで、どうやってログインの画面へ送るかを決める。

## 決めたこと

ログインが要る画面を 1 つの共通の枠(`src/app/(member)/layout.tsx`)で包み、枠が `GET /api/me` の結果を見て、ログインしていなければ `/login?next=...` へ移す。
これは表示の都合であり、権限の判定はバックエンドが行う。

## 理由

- 画面のファイルには、利用者ごとのデータが入っていない。データは API からしか取れず、API は入口と各サービスがログインと役割を確かめる。ブラウザの中の守りを外されても、見えるのは中身のない画面である。
- 入口の設定を変えずに済む。「`/api` で始まらないパスは確かめない」という決まりが 1 つのままで、元のレシピの画面は `auth-service` が止まっていても開ける。
- ログインの状態を確かめられないとき(`auth-service` が止まっている)と、ログインしていないときとを、画面で区別して出し分けられる。
- ログインが要る画面を 1 つのディレクトリに集めるので、守りの付け忘れが起きない。

## 却下した案

- **入口で、ログインが要る画面のパスも確かめ、ログインしていなければログインの画面へ送る**: 中身のない画面も配らずに済む。入口の設定に、画面のパスの一覧を持つことになり、画面を足すたびに入口を直す必要がある。`auth-service` が止まると、これらの画面が開けず、「今は使えない」という案内を画面で出せない。守れるものは、もともと秘密でない静的なファイルだけである。
- **ログインしたことを示す、スクリプトから読める別のクッキーを足し、それを見て出し分ける**: API を呼ばずに、すぐに出し分けられる。セッションの期限切れやログアウトで、クッキーと実際の状態が食い違う。結局 `GET /api/me` で確かめ直すことになり、状態を 2 か所に持つだけになる。
- **Next.js のミドルウェアで確かめる**: サーバー側の機能なので、静的な書き出しでは使えない。

## 影響

- ログインが要る画面を開くと、`GET /api/me` が返るまでの間、骨組みの表示が出る。
- ログインしていない人にも、ログインが要る画面のファイル(HTML と JavaScript)は配られる。画面のコードに、秘密の値や、ほかの人に見せられない情報を書かない。
- 画面でボタンを隠していても、API は権限を確かめる。役割ごとの可否は、API のテストで確かめる(要件定義の 11 章の段階 5)。
- 画面の中身が、枠が「ログインしている」と決める前に API を呼ばないことを、受け入れ条件(`AC-UI-21`)で確かめる。
