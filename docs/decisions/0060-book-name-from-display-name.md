# 0060 自分のレシピ帳の最初の名前に、表示名を入れる

決めた日: 2026-10-11

## 状況

自分のレシピ帳は、その人の最初の `GET /api/books` で `book-service` が作る。
最初の名前を、全員同じ「わが家のレシピ帳」にしていた。
招待し合った 2 人のレシピ帳の切り替えの欄に、同じ名前が 2 つ並び、役割の表示でしか見分けられない。

## 決めたこと

最初の名前を「<表示名>のレシピ帳」とし、表示名は、レシピ帳を作るときに `book-service` が `auth-service` から取る。

## 理由

- 共有を始めた時点で、だれのレシピ帳かが名前で分かる。持ち主が名前を変えなくても区別できる。
- 利用者が選んだ(2026-10-11)。
- `auth-service` を呼ぶのは、1 人につき、レシピ帳を作る 1 回だけである。すでにレシピ帳がある人の一覧の取得は、今までどおり、ほかのサービスに頼らない。
- 表示名を返す内部の API(`GET /internal/users`)は、メンバーの一覧のためにすでにある。新しい API を足さない。

## 却下した案

- **全員「わが家のレシピ帳」にする**: ほかのサービスを呼ばずに作れる。招待し合うと、同じ名前が並ぶ。
- **サービスの間のトークンに、表示名を入れる**: 呼び出しが要らない。トークンはログに残ることがあり、個人の情報を広げない、という決まり(「共通設計: 認証」の 4.7)に反する。
- **画面が、最初の名前を付けて作る要求を送る**: 表示名は画面が持っている。レシピ帳を作る API を足すことになり、登録の直後に画面が閉じられると、レシピ帳のない利用者ができる。
- **`auth-service` が応答しないときは、「わたしのレシピ帳」で作る**: 一覧を必ず返せる。名前を後から自動で直す機会がなく、応答しなかった時に登録した人だけ、違う名前が残る。

## 影響

- 登録の直後に `auth-service` が応答しないと、最初の `GET /api/books` が 503 を返す。画面は、レシピ帳の一覧を「読み込めない」として出し、やり直せる。
- 名前は、作った時点の表示名の写しである。表示名を変える機能を足しても、レシピ帳の名前は付いていかない。
- 名前は 40 文字までなので、35 文字を超える表示名は、途中で切って「…」を付ける。
- アーキテクチャ図の通信の向きは変わらない。`book-service` から `auth-service` への呼び出しは、メンバーの一覧のためにすでにある。
