# 0007 PostgreSQL のサーバーを 1 つにし、データベースをサービスごとに分ける

決めた日: 2026-10-11

## 状況

サービスは、ほかのサービスのデータベースを読まない(要件定義の 6 章)。
この決まりを守るための、データベースの置き方を決める。

## 決めたこと

PostgreSQL のサーバーを 1 つ置き、その中にデータベースを 3 つ(`auth`、`book`、`kitchen`)作る。
サービスごとに接続する利用者を分け、自分のデータベースにだけ接続できる権限にする。

## 理由

- 接続の権限で分けるので、ほかのサービスのテーブルを読もうとしても、データベースが拒む。決まりを、約束ではなく仕組みで守れる。
- 手元の機械で動かすコンテナが 1 つで済む。Kubernetes の上で、サービスが 3 つ、画面が 1 つ、入口が 1 つ動くので、データベースまで 3 つにすると重くなる。
- 後からサーバーを分けるときに、変えるのは接続先の設定だけである。テーブルもコードも変わらない。

## 却下した案

- **サービスごとに PostgreSQL のサーバーを置く**: 「サービスごとにデータベースを持つ」という考え方に、一番忠実である。あるサービスのデータベースが重くなっても、ほかに響かない。版もサービスごとに選べる。手元で動かすものが 3 つに増え、起動、保存先、秘密の値の管理も 3 倍になる。今の規模では、分けることで得られるものがない。
- **1 つのデータベースの中で、スキーマで分ける**: 設定は一番簡単である。1 つの接続で複数のスキーマを読めるので、権限の設定を誤ると、ほかのサービスのテーブルが読めてしまう。データベースをまたぐ問い合わせを、うっかり書けてしまう。
- **1 つのデータベースを 3 つのサービスで共有する**: サービスを分ける意味がなくなる。

## 影響

- サーバーが止まると、3 つのサービスがすべて止まる。「あるサービスが止まっても、ほかは動き続ける」という要件は、データベースについては満たさない。
- 配置する場所を決めるときに、サーバーを分けるかどうかを見直す。そのときの判断の材料は、サービスごとの負荷の差と、止まったときの影響である。
