# おうちレシピ帖 要件定義書

作成日: 2026-10-10

2026-09-25 版(Vite と Cloudflare Workers の構成)は、ブランチ `archive/vite-workers-app` に残している。
本書はそれを置き換える。

## 1. 目的と背景

Claude Code が作ったレシピを、ブラウザで見て、自分の作り方に合わせて直し、栄養の値を確かめるためのアプリを作る。
直した内容と献立は自分のレシピ帳に保存し、別のアカウントの人を招待して共有できる。

レシピを作るのは Claude Code であり、アプリではない。
アプリは AI を呼び出さない。

### このプロジェクトのもう一つの目的

アプリを作ることに加えて、次の 2 つを目的とする。

- **技術を学ぶ**: Next.js、Quarkus、マイクロサービス、Kubernetes を、一通り動くものを作りながら経験する。
- **AI 駆動開発を試す**: この構成で、Claude Code に作らせ、確かめさせる進め方を試す。

そのため、技術の選び方は「最小の手間で作れること」よりも「標準的なやり方を経験できること」を優先する。
数人で使うアプリとしては大きすぎる構成を、承知のうえで選んでいる。

配置する場所は、機能ができてから決める。
それまでは、手元の Kubernetes(kind)で動くことを完成の基準にする。

## 2. スコープ

### 2.1 対象とする機能

| 優先度 | 機能 | 内容 |
|---|---|---|
| P0 | レシピ一覧 | 検索、ジャンルでの絞り込み |
| P0 | レシピ詳細 | 材料、手順、コツ、写真の表示。人数に合わせた分量の換算 |
| P0 | 栄養計算 | 材料と分量から、成分表を使って 1 人分の栄養の値を算出する |
| P0 | ログイン | メールアドレスとパスワードで登録し、ログインする |
| P0 | レシピ帳 | 編集内容と献立の入れ物。登録すると自分のレシピ帳が 1 つできる |
| P0 | レシピの編集 | 材料、分量、手順、コツを直し、レシピ帳に保存する |
| P0 | 今日の献立 | 料理を朝食、昼食、夕食に並べ、1 日の栄養の値を合計する |
| P0 | 招待と共有 | レシピ帳に別のアカウントの人を招待する。権限は「見るだけ」か「編集できる」を選ぶ |
| P1 | レシピの複製 | 元のレシピを複製して、アレンジ版としてレシピ帳に持つ |
| P1 | 書き出し | レシピ帳の中身をファイルに保存する。Claude Code が元のレシピへ反映するときの入力にもなる |
| P1 | 印刷 | レシピ詳細を紙 1〜2 枚に収めて印刷する |

### 2.2 対象としない機能

- アプリの中でのレシピの生成(AI の呼び出し)
- 外部のアカウント(Google など)でのログイン
- メールの送信。メールアドレスの確認とパスワードの再設定は、配置する場所が決まってから足す
- レシピ 1 品ごとの共有。共有はレシピ帳の単位で行う
- 複数人が同時に入力した内容の自動での統合
- 好き嫌いの管理、レシピの提案、買い物リスト、調理ログ
- ビタミンとミネラルの表示、体重管理

## 3. 利用者と権限

元のレシピは、ログインしなくても誰でも見られる。
編集、献立、共有にはログインが要る。

レシピ帳ごとに、利用者は次のいずれかの役割を持つ。

| 役割 | できること |
|---|---|
| 持ち主 | 見る、編集する、招待する、メンバーの役割を変える、メンバーを外す、レシピ帳の名前を変える |
| 編集できる人 | 見る、編集する |
| 見るだけの人 | 見る |
| メンバーでない人 | 何もできない。レシピ帳があることも分からない |

持ち主はレシピ帳に 1 人で、ほかの人に替えられない。
利用者は、自分のレシピ帳のほかに、招待されたレシピ帳を複数持てる。
画面の上部で、今開いているレシピ帳を切り替える。

権限は必ずバックエンドで判定する。
画面側でボタンを隠すのは表示の都合であり、権限の判定にはならない。

## 4. 機能要件

各機能の末尾に受け入れ条件を置く。
受け入れ条件は、そのまま Playwright、Vitest、API のテストにする。

### 4.1 レシピ一覧

- すべてのレシピを、写真、料理名、分類、調理時間のカードで並べる。
- 検索は料理名、読み、材料名、ジャンルを対象にする。空白で区切った語をすべて含むレシピを残す。
- カタカナとひらがな、全角と半角、大文字と小文字を区別しない。
- ジャンルは、レシピに付いている値から絞り込みのボタンを作る。選んだジャンルは URL に残す。
- 検索とジャンルは組み合わせて使える。該当がないときはその旨を表示する。
- 今開いているレシピ帳で編集したレシピには、編集済みであることが分かる印を付ける。

受け入れ条件:

- 「鶏もも肉」で検索すると、材料に鶏もも肉を含むレシピだけが残る。
- 「ハンバーグ」と「はんばーぐ」で同じ結果になる。
- ジャンル「副菜」を選んで再読み込みしても、絞り込みが保たれる。

### 4.2 レシピ詳細

- 写真、料理名、リード文、基本情報(調理時間、難易度、道具)、材料、手順、コツ、写真の出典を表示する。
- ログインしていてレシピ帳に編集内容があるときは、編集後の内容を表示し、元のレシピとの切り替えができる。
- 人数を 1〜6 人で切り替えると、材料の分量を換算して表示する。
- 分量は読みやすい表記に整える。g と ml は 5 刻み、大さじと小さじは分数(1/2、1/3、1/4 刻み)で表す。個や本のように数で数える単位は、分けて使わない食材(卵など)では整数、そのほかでは分数で表す。
- 「少々」「適量」のように数値で表せない分量は、換算せずそのまま表示する。
- 材料にはチェックを付けられる。手順は終えたものに印を付けられる。どちらもページを閉じると消えてよい。

受け入れ条件:

- 2 人分で「鶏もも肉 250g」のレシピを 4 人分にすると「500g」と表示される。
- 2 人分で「大さじ1」の材料を 3 人分にすると「大さじ1と1/2」と表示される。
- 「適量」の材料は、人数を変えても「適量」のままである。

### 4.3 栄養計算

- 表示する項目はエネルギー(kcal)、たんぱく質、脂質、炭水化物、食塩相当量の 5 項目とする。
- レシピ詳細では 1 人分の値を表示する。
- 算出は次の順で行う。材料の分量を g に換算し、食材が参照する成分表の 100g あたりの値に掛け、全材料を合算して、人数で割る。
- 計算はブラウザで行う。材料や分量を編集すると、その場で値が変わる。バックエンドは栄養の値を計算せず、保存もしない。

#### 概算であることの扱い

次の材料は計算から除く。

- 数値で表せない分量(「少々」「適量」)
- 単位から g への換算率が登録されていない材料
- 食材マスタにない材料、または成分表の食品番号が設定されていない食材。ただし、栄養の値がないと分かっている食材(水)は除かず、0 として計算に入れる

除いた材料が一つでもあるときは「概算値」と明示し、除いた材料名を一覧できるようにする。
正確そうに見える数値だけを出して、実際には調味料が抜けている状態を避けるためである。

計算できた材料が一つもないレシピでは、数値を出さず「栄養値は未算出」と表示する。
水と、摂取する割合が 0 の材料は、g に換算できなくても除かず 0 として計算に入れるが、「計算できた材料」には数えない。
成分表に値がない成分は、その成分についてだけ、その材料を除く。
式、丸め方、表示の桁は、[機能設計: 栄養計算](design/nutrition.md) に書く。

揚げ油のように全量を食べない材料は、レシピのデータに「摂取する割合」を持たせて計算に反映する。

受け入れ条件:

- 既知の材料だけのレシピで、手計算の値と一致する(単体テスト)。
- 「適量」の材料を含むレシピで「概算値」と表示され、その材料名が一覧に出る。
- 材料の分量を 2 倍にすると、その材料の分だけ 1 人分の値が増える。

### 4.4 登録とログイン

認証は自前で持つ。

- メールアドレス、パスワード、表示名で登録する。
- 登録した人が初めてレシピ帳の一覧を取得したときに、その人のレシピ帳を 1 つ作る。画面は登録の直後に一覧を取得するので、利用者からは登録と同時にできたように見える。
- メールアドレスとパスワードでログインする。ログアウトできる。
- パスワードは 12 文字以上とする。文字の種類は問わない。長さのほうが強度に寄与するためである。
- パスワードはそのまま保存しない。ソルト付きの遅いハッシュ(bcrypt)にして保存する。
- ログインに成功すると、バックエンドがセッションを発行し、クッキーでブラウザに渡す。クッキーは画面のスクリプトから読めない設定(HttpOnly)にし、ほかのサイトからの要求には付かない設定(SameSite)にする。
- セッションは 30 日で期限が切れる。使うたびに期限を延ばす。
- セッションの識別子は推測できない長さの乱数とし、データベースにはハッシュだけを保存する。
- ログアウトすると、そのセッションをバックエンドで無効にする。パスワードを変えると、その人のほかのセッションをすべて無効にする。
- ログインの失敗は、メールアドレスが登録されているかどうかを区別せず、同じ文言で返す。登録の有無を外から調べられないようにするためである。
- 同じメールアドレスへのログインの失敗が続いたときは、一定の時間、そのメールアドレスでのログインを受け付けない。
- 変更を伴う API は、ほかのサイトから送られた要求を拒む(CSRF 対策)。
- 保存する個人の情報は、メールアドレス、表示名、パスワードのハッシュに限る。
- ログインが切れた状態で保存しようとしたときは、入力中の内容を失わずに、再度のログインを求める。

メールを送らないので、今の段階ではメールアドレスの持ち主であることを確認しない。
パスワードを忘れたときの再設定もできない。
どちらも、配置する場所とメールの送信手段が決まってから足す(12 章)。

受け入れ条件:

- 登録の後にレシピ帳の一覧を取得すると、自分のレシピ帳が 1 つあり、役割が持ち主になっている。
- レシピ帳の一覧を 2 回取得しても、自分のレシピ帳は増えない。
- 登録済みのメールアドレスでもう一度登録しようとすると、拒まれる。
- 11 文字のパスワードでは登録できない。API に直接送っても 400 が返る。
- データベースに、パスワードとセッションの識別子がそのままの形で入っていない。
- ログインしていない状態で編集の API を呼ぶと 401 が返る。
- ログアウトした後、同じクッキーで API を呼ぶと 401 が返る。
- 誤ったパスワードと、登録のないメールアドレスとで、応答の内容が同じである。

### 4.5 レシピの編集

- 編集できるのは、材料(食材、分量、単位、追加、削除、並べ替え)、手順(見出し、本文、目安時間、追加、削除、並べ替え)、コツ、基本の人数、メモとする。
- 料理名、写真、ジャンルは編集の対象にしない。これらを変えたいときは Claude Code で元のレシピを直す。
- 材料の食材は、食材マスタから選ぶ。マスタにない食材は名前を自由に入力でき、その材料は栄養計算から除かれる。
- 編集した内容は、今開いているレシピ帳に保存する。保存は入力が止まってから自動で行い、保存ボタンを置かない。保存中、保存済み、失敗の状態を画面に出す。
- 元のレシピは書き換えない。編集内容は、元のレシピに対する上書きとして別に持つ。
- 「元に戻す」で、そのレシピの編集内容を捨てて元のレシピに戻せる。捨てる前に確認する。
- 元のレシピが後から更新されたときは、編集内容を残したまま、元が更新されたことを知らせる。
- 入力値は画面とバックエンドの両方で検証する。分量に負の数や文字が入ったときは、その欄に理由を表示し、保存しない。
- 見るだけの人には、編集の入口を出さない。

#### 同時に編集したとき

編集内容は改訂番号を持つ。
保存するときに、画面が持っている改訂番号がバックエンドの番号と違えば、保存を拒み、ほかの人が先に変更したことを知らせる。
利用者は、相手の内容を読み込み直すか、自分の内容で上書きするかを選ぶ。
黙って上書きしない。

受け入れ条件:

- 材料の分量を変えて再読み込みしても、変えた値が表示される。
- 「元に戻す」を実行すると、元のレシピの値に戻り、一覧の編集済みの印が消える。
- 分量に「-1」を入れると、エラーが表示され、保存されない。API に直接送っても 400 が返る。
- 古い改訂番号で保存すると 409 が返り、保存されている内容は変わらない。
- 見るだけの人が編集の API を呼ぶと 403 が返る。

### 4.6 今日の献立

- レシピ一覧とレシピ詳細から、料理を献立に追加できる。追加した時刻に合う食事(朝食、昼食、夕食)に入る。
- 献立のページで、料理を別の食事に移す、外す、すべて外すことができる。
- ご飯(茶碗 1 杯 150g)を、食事ごとに何杯でも足せる。
- 食事ごとのエネルギーの小計と、1 日の 5 項目の合計を表示する。
- たんぱく質、脂質、炭水化物がエネルギーに占める割合を、目標の範囲と並べて表示する。
- エネルギーと食塩相当量を、1 日の目安と並べて表示する。目安は日本人の食事摂取基準(2020年版)の値を使う。
- 献立は日付ごとに、今開いているレシピ帳に保存する。保存するのは料理の識別子と食事の区分で、栄養の値はその都度計算する。
- 編集したレシピが献立に入っているときは、編集後の値で合計する。
- 日付を前後に移して、ほかの日の献立を見られる。
- 同時に編集したときの扱いは 4.5 と同じにする。

受け入れ条件:

- 料理を 2 品追加すると、合計が 2 品の 1 人分の値の和になる。
- 献立に入っているレシピの分量を編集すると、献立の合計も変わる。
- 再読み込みしても、別の端末でログインしても、献立が保たれる。

### 4.7 招待と共有

- 持ち主は、役割(見るだけ、編集できる)を選んで招待リンクを作る。
- 招待リンクは 7 日で期限が切れ、1 回使うと無効になる。持ち主は、使われる前のリンクを取り消せる。
- 招待された人がログインしてリンクを開くと、レシピ帳の名前、持ち主の表示名、与えられる役割を確認する画面が出る。参加を選ぶとメンバーになる。
- アプリはメールを送らない。リンクは持ち主が自分で相手に渡す。
- 持ち主は、メンバーの一覧を見て、役割を変え、メンバーを外せる。
- メンバーは、自分からレシピ帳を抜けられる。持ち主は抜けられない。
- 招待リンクの文字列は推測できない長さの乱数とし、データベースにはハッシュだけを保存する。

受け入れ条件:

- 期限が切れたリンク、使用済みのリンク、取り消したリンクでは参加できない。
- 持ち主でない人が、招待の作成、役割の変更、メンバーの削除の API を呼ぶと 403 が返る。
- 外されたメンバーは、そのレシピ帳の API がすべて 404 になる。
- メンバーでない人がレシピ帳の識別子を指定して API を呼ぶと、404 が返る。403 にしないのは、レシピ帳があることを知らせないためである。

## 5. 非機能要件

- **動かす場所**: 手元の Kubernetes(kind)で、コマンド 1 つで一式が起動する。配置する場所は 12 章で決める。
- **サービスの独立**: あるサービスが止まっても、ほかのサービスの機能は動き続ける。止まったサービスに頼る操作は、理由が分かる形で失敗する。
- **セキュリティ**: 権限はすべての API でバックエンドが判定する。入力値はバックエンドで検証し、大きさに上限を設ける。秘密の値をリポジトリに置かない。パスワードとセッションの扱いは 4.4 に従う。
- **個人情報**: 保存するのは 4.4 に挙げた 3 項目に限る。利用者は自分のアカウントとレシピ帳を削除できる(P1)。
- **アクセシビリティ**: キーボードだけで操作できる。写真には代替の説明を付ける。色だけで状態を伝えない。
- **対応する画面**: 幅 360px から崩れずに表示できる。
- **言語**: 画面は日本語だけとする。

## 6. 技術構成

| 役割 | 採用 |
|---|---|
| 画面 | Next.js(App Router)+ React + TypeScript + Tailwind CSS。静的に書き出し、コンテナから配る |
| API | Quarkus(REST)+ Java 21 のマイクロサービス 3 つ |
| データベース | PostgreSQL。サービスごとにデータベースを分ける |
| テーブルの変更管理 | Flyway。サービスごとに持つ |
| ログイン | 自前の認証。メールアドレスとパスワード、クッキーによるセッション |
| 入口 | Kubernetes の Gateway API。実装は Envoy Gateway。パスでサービスへ振り分け、ログインの確認を認証のサービスに任せる |
| サービス間の本人確認 | 短い期限の署名付きトークン(JWT) |
| API の約束 | 各サービスが出力する OpenAPI の仕様。画面側の型はここから生成する |
| 実行環境 | Kubernetes。手元では kind |
| 手元での開発 | Docker Compose(1 つのサービスを書いて確かめる間)と kind(つないで確かめるとき) |
| テスト | 画面は Vitest と Playwright、API は JUnit と REST Assured |

### サービスの分け方

| サービス | 受け持つもの | 持つデータ |
|---|---|---|
| `auth-service` | 登録、ログイン、セッション、パスワード。入口からのログインの確認に答える | 利用者、セッション |
| `book-service` | レシピ帳、メンバー、招待。「誰がどのレシピ帳で何をできるか」の正本 | レシピ帳、メンバー、招待 |
| `kitchen-service` | レシピの編集内容、献立 | 編集内容、献立 |
| `frontend` | 画面の静的なファイルを配る | なし |

分ける基準は、データの持ち主と変わる理由である。
ログインの仕組み、共有の仕組み、料理の中身は、それぞれ別の理由で変わる。
これ以上は分けない。分けるほど、サービス間の通信と確かめる量が増えるためである。

### サービスの間の決まり

- **ほかのサービスのデータベースを読まない。** 必要な情報は、持ち主のサービスの API から取る。
- **外に出す API と、サービスの間だけで使う API を分ける。** 後者は `/internal` の下に置き、入口から届かないようにする。
- **サービスの間の呼び出しには、期限を付ける。** 応答がないまま待ち続けない。
- **権限が確かめられないときは拒む。** `kitchen-service` は保存の前に、`book-service` にその人の役割を問い合わせる。`book-service` が応答しないときは 503 を返し、保存しない。
- **利用者の表示名のように、ほかのサービスが持つ情報を自分のデータベースに写さない。** 画面に要るときは、持ち主のサービスから取る。

### ログインの状態の伝え方

1. ブラウザは、セッションのクッキーを付けて入口に要求を送る。
2. 入口は、要求を後ろのサービスへ渡す前に、`auth-service` にクッキーを確かめさせる。
3. `auth-service` は、セッションが有効なら、利用者の識別子を入れた署名付きトークン(期限は 1 分)を返す。
4. 入口は、そのトークンを要求に付けて後ろのサービスへ渡す。
5. 後ろのサービスは、`auth-service` が公開する鍵で署名を確かめ、利用者を特定する。

ブラウザに見えるのはクッキーだけである。
後ろのサービスはセッションを知らず、トークンの署名だけを確かめる。
サービスがほかのサービスを呼ぶときは、受け取ったトークンをそのまま渡す。

### 登録したときのレシピ帳の作成

登録は `auth-service`、レシピ帳は `book-service` の仕事である。
レシピ帳は、登録のときではなく、利用者が初めて `book-service` に来たときに作る。
登録の処理を 2 つのサービスにまたがらせると、片方だけ成功した状態を戻す仕組みが要るためである。

メッセージ基盤(Kafka など)は、今の段階では入れない。
サービスの間で、後から届けば足りる連絡が出てきたときに入れる。

### 画面は静的に書き出す

Next.js のサーバー側の機能(Route Handlers、Server Actions、実行時のサーバーでの描画)は使わない。
ビルド時にすべてのページを HTML に書き出し、ブラウザから API を呼ぶ。
サーバー側の処理をバックエンドのサービスに任せ、権限の判定が画面側に漏れるのを防ぐためである。

元のレシピはビルド時にページへ組み込む。
編集内容は、ページを開いた後に API から取得して、ブラウザ側で元のレシピへ重ねる。

### バックエンドは薄く保つ

バックエンドの仕事は、ログインの検証、権限の判定、入力値の検証、保存と取得に留める。
栄養計算と分量の換算はブラウザで行い、バックエンドに同じ計算を持たせない。
同じ計算を 2 つの言語で書くと、結果が食い違うためである。

### API の約束を一つにする

各サービスの OpenAPI の仕様を、画面と API の間の唯一の約束とする。
仕様は Quarkus のコードから出力し、リポジトリにコミットする。
画面側の型はこの仕様から生成し、手で書かない。
API を変えて仕様を更新し忘れたときは、CI が差分を検出して失敗する。

API のエラーは、どのサービスも `{ code, message }` の形で返す。

### 画面と API を同じオリジンで配る

ログインの状態をクッキーで持つので、画面と API は同じオリジン(同じドメインとポート)で配る。
入口が、パスの先頭で振り分ける。

| パス | 振り分け先 |
|---|---|
| `/api/auth`、`/api/me` | `auth-service` |
| `/api/books/{bookId}/recipe-edits`、`/api/books/{bookId}/menus` | `kitchen-service` |
| そのほかの `/api/books`、`/api/invitations` | `book-service` |
| そのほか | `frontend` |

### 手元での動かし方

2 通りの動かし方を使い分ける。

- **Docker Compose**: 1 つのサービスを書いている間に使う。Quarkus の開発モードで動かし、変更をすぐに確かめる。単体テストと API のテストもここで走らせる。
- **kind**: サービスをつないで確かめるときと、ブラウザのテストのときに使う。コンテナのイメージを作ってクラスタに載せる。

どちらも入口の振り分けとログインの確認を同じ設定で動かし、片方でしか起きない不具合を減らす。

## 7. データモデル

### 7.1 元のレシピ(リポジトリのファイル)

1 品を 1 つの JSON ファイル(`data/recipes/<slug>.json`)で持つ。
項目ごとの型と制約、完全な例は、[データ設計: 元のレシピ、食材マスタ、成分表](design/data-recipe.md) に書く。

| 項目 | 内容 |
|---|---|
| `slug` | 識別子。ファイル名と同じ |
| `version` | 元のレシピを直すたびに 1 増やす整数。編集内容がどの版に対するものかを判定する |
| `name`、`reading`、`romanName` | 料理名、検索用のひらがなの読み、写真に添えるローマ字の名前 |
| `arrangeLabel`、`arrangeOf`、`arrangeChanges` | アレンジ版のとき、変更点の名前、元のレシピの識別子、変更点の箇条書き |
| `genres` | 料理の系統、料理の種類の順に並べる。決まった値の一覧から選ぶ |
| `description`、`lead` | 検索エンジンに出す紹介と、リード文 |
| `time`、`level`、`tool` | 調理時間(分)、難易度(1〜3)、道具 |
| `servings` | 基本の人数。2 とする |
| `ingredientGroups` | 材料のグループ。識別子、名前、材料の並び |
| `steps` | 手順。識別子、見出し、本文、目安時間 |
| `tips` | コツ。識別子と本文 |
| `photos` | 写真。ファイル名、役割(ヒーローかギャラリー)、代替の説明、説明文、出典(題名、URL、作者、ライセンスの種類と版、取ってきた場所) |

材料のグループ、材料、手順、コツは、レシピの中で変わらない識別子(`id`)を持つ。
編集内容が、元のレシピのどの行を直したのかを指すためである。

材料は次の項目を持つ。

| 項目 | 内容 |
|---|---|
| `id` | レシピの中での材料の識別子 |
| `ingredientId` | 食材マスタの識別子。マスタにない材料では持たない |
| `name` | 表示する名前。「鶏もも肉」「しょうが(すりおろし)」 |
| `amount`、`unit` | 分量の数値と単位。数値で表せないときは持たない |
| `note` | 数値で表せない分量の表記。「少々」「適量」「好みで」 |
| `intakeRatio` | 摂取する割合(0〜1)。省略時は 1。揚げ油や、飲み干さない汁に使う |

栄養の値はレシピに持たせない。
材料から計算した値と食い違うのを防ぐためである。

### 7.2 食材マスタと成分表(リポジトリのファイル)

`data/ingredients.json` に、人が選ぶ単位で食材を持つ。

| 項目 | 内容 |
|---|---|
| `id` | 識別子 |
| `name`、`aliases` | 名称と別名 |
| `category` | 野菜、肉、魚介、卵と乳製品、穀類、調味料、その他 |
| `foodNumber` | 代表となる成分表の食品番号。未設定の食材は栄養計算から除く |
| `noNutrition` | 栄養の値がすべて 0 の食材(水)に付ける印。付いた食材は、食品番号がなくても栄養計算から除かない |
| `gramsPerUnit` | 単位から g への換算率。「大さじ: 18」「個: 50」のように持つ |
| `wholeUnits` | 表示のときに整数に丸める単位。卵の「個」のように、分けて使わない食材に付ける |
| `note` | 食品番号と換算率を選んだ根拠。画面には出さない |

成分表は調理の形ごとに分かれていて(「こまつな 葉 生」「こまつな 葉 ゆで」)、人が選ぶには細かすぎる。
そのため食材マスタを上に置き、そこから食品番号を 1 件参照する。

成分表の扱いは次のとおりとする。

- 出典は文部科学省の**日本食品標準成分表(八訂)増補2023年**とする。
- 変換スクリプトで Excel から `data/foods.json` を作り、リポジトリにコミットする。変換元の Excel はコミットしない。
- 保持する成分はエネルギー、たんぱく質、脂質、炭水化物、食塩相当量の 5 項目で、可食部 100g あたりの値とする。
- 欠損の記号を区別して読む。`-`(未測定)は `null`、`Tr`(微量)と `(Tr)`、`(0)` と `0` は `0`、括弧の付いた数は括弧を外した数として扱う。
- ブラウザには、食材マスタが参照している食品だけを渡す。全件(2,538 件)を配ると読み込みが重くなるためである。
- 栄養の値を出す画面に、出典表記「出典: 文部科学省「日本食品標準成分表(八訂)増補2023年」。栄養の値は、この成分表の値をもとに、このアプリが計算したものです。」を常に載せる。成分表の利用の条件が、加工したときはその旨を書くことを求めているためである。

元のレシピ、食材マスタ、成分表をデータベースに入れないのは、アプリから書き換えない読み取り専用のデータだからである。
Claude Code が作り、Git で履歴を持ち、版ごとに差し替える。

### 7.3 データベース

データベースはサービスごとに分ける。

| サービス | テーブル | 内容 |
|---|---|---|
| `auth-service` | `users` | 利用者。メールアドレス、表示名、パスワードのハッシュ |
| `auth-service` | `sessions` | ログインのセッション。利用者、識別子のハッシュ、期限、最後に使った日時 |
| `auth-service` | `login_attempts` | ログインの失敗の記録。メールアドレスのハッシュ、失敗の回数、受け付けない期限 |
| `book-service` | `books` | レシピ帳。名前、持ち主 |
| `book-service` | `book_members` | レシピ帳のメンバー。利用者と役割(持ち主、編集できる、見るだけ) |
| `book-service` | `invitations` | 招待。レシピ帳、役割、リンクのハッシュ、期限、作った人、使った人、使った日時、取り消した日時 |
| `kitchen-service` | `recipe_edits` | レシピの編集内容。レシピ帳、レシピの識別子、元にした版、内容、改訂番号、最後に保存した人 |
| `kitchen-service` | `menus` | 献立。レシピ帳、日付、品の並び、改訂番号、最後に保存した人 |

ほかのサービスが持つ利用者やレシピ帳は、識別子だけで参照する。
データベースをまたぐ外部キーは張れないので、参照先が消えたときの扱いを各サービスで決める。

決まりは次のとおりとする。

- `recipe_edits` はレシピ帳とレシピの識別子の組で 1 件、`menus` はレシピ帳と日付の組で 1 件とする。
- 編集内容と献立の品の並びは JSON の列で持つ。バックエンドは型を付けて検証してから保存する。
- 記録した瞬間(作成日時、更新日時)は時刻帯付きの日時で持つ。暦の上の一日(献立の日付)は日付の型で持ち、時刻を付けない。時刻を付けると、時間帯の扱いで前後の日にずれるためである。
- メールアドレスは小文字にそろえて保存し、重複を許さない。
- レシピ帳を消すと、`book-service` はメンバーと招待を消し、`kitchen-service` に編集内容と献立を消させる。
- クエリには上限の件数を設ける。

## 8. API

パスはすべて `/api` の下に置く。
レシピ帳に関わる API は、すべてログインとメンバーであることを求める。
どのサービスが受け持つかは、6 章の振り分けの表に従う。
`GET /api/health` は入口が答える。各サービスは、Kubernetes が稼働を確かめるための入口を別に持つ。

| メソッドとパス | 内容 | 必要な役割 |
|---|---|---|
| `GET /api/health` | 稼働の確認 | なし |
| `POST /api/auth/register` | 登録する。利用者を作り、ログインした状態にする。レシピ帳は、最初の `GET /api/books` で作る | なし |
| `POST /api/auth/login` | ログインする | なし |
| `POST /api/auth/logout` | ログアウトする | ログイン |
| `PUT /api/me/password` | パスワードを変える。今のパスワードを付けて送る | ログイン |
| `GET /api/me` | 自分の情報(識別子、メールアドレス、表示名) | ログイン |
| `GET /api/books` | 参加しているレシピ帳の一覧と、それぞれでの役割。自分のレシピ帳がなければ作る | ログイン |
| `PATCH /api/books/{bookId}` | レシピ帳の名前を変える | 持ち主 |
| `GET /api/books/{bookId}/recipe-edits` | 編集済みのレシピの一覧(識別子、改訂番号、元にした版、最後に保存した日時) | 見るだけ以上 |
| `GET /api/books/{bookId}/recipe-edits/{slug}` | 編集内容を取得する | 見るだけ以上 |
| `PUT /api/books/{bookId}/recipe-edits/{slug}` | 編集内容を保存する。改訂番号を付けて送る | 編集できる以上 |
| `DELETE /api/books/{bookId}/recipe-edits/{slug}` | 編集内容を捨てる。改訂番号を付けて送る | 編集できる以上 |
| `GET /api/books/{bookId}/menus/{day}` | その日の献立を取得する | 見るだけ以上 |
| `PUT /api/books/{bookId}/menus/{day}` | その日の献立を保存する。改訂番号を付けて送る | 編集できる以上 |
| `GET /api/books/{bookId}/members` | メンバーの一覧 | 見るだけ以上 |
| `PATCH /api/books/{bookId}/members/{userId}` | 役割を変える | 持ち主 |
| `DELETE /api/books/{bookId}/members/{userId}` | メンバーを外す。自分を指定すると抜ける | 持ち主、または本人 |
| `GET /api/books/{bookId}/invitations` | 有効な招待の一覧 | 持ち主 |
| `POST /api/books/{bookId}/invitations` | 招待を作る。リンクの文字列はこの応答でだけ返す | 持ち主 |
| `DELETE /api/books/{bookId}/invitations/{invitationId}` | 招待を取り消す | 持ち主 |
| `POST /api/invitations/lookup` | 招待の内容を確認する。リンクの文字列は本文で渡す。何も書き換えない | ログイン |
| `POST /api/invitations/accept` | 招待を受けてメンバーになる。リンクの文字列は本文で渡す | ログイン |

サービスの間だけで使う API は次のとおりとする。入口からは届かない。

| メソッドとパス | 持ち主 | 内容 |
|---|---|---|
| `/internal/auth/verify` で始まるパス(どのメソッドでも) | `auth-service` | 入口から呼ばれる。クッキーを確かめ、署名付きトークンを返す |
| `GET /internal/auth/keys` | `auth-service` | 署名を確かめるための公開鍵 |
| `GET /internal/users?ids=` | `auth-service` | 利用者の表示名をまとめて返す。メンバーの一覧に使う |
| `GET /internal/books/{bookId}/roles/{userId}` | `book-service` | その人のレシピ帳での役割を返す。メンバーでなければ 404 |
| `DELETE /internal/books/{bookId}/contents` | `kitchen-service` | レシピ帳の編集内容と献立をすべて消す |

## 9. データの検証

元のレシピと食材マスタは Claude Code が書くので、誤りを仕組みで止める。
`npm run check:data` で次を検証し、CI でも走らせる。
検証する項目の全体は、[データ設計: 元のレシピ、食材マスタ、成分表](design/data-recipe.md) の 5.11 に書く。

- すべてのレシピがスキーマに通る。
- レシピの `slug` がファイル名と一致し、重複がない。
- 材料の `ingredientId` が食材マスタに存在する。
- 食材マスタの `foodNumber` が成分表に存在する。
- 材料の単位が、g か、その食材の `gramsPerUnit` に登録されている単位である。登録がないものは警告として一覧に出す。
- 写真のファイルが存在し、ライセンスが CC0、Public domain、CC BY、CC BY-SA のいずれかである。
- アレンジ版の `arrangeOf` が指すレシピが存在する。

## 11. 既存の資産の移行とリリース計画

### 移行

`recipes/` にある静的レシピ集の 38 品を、7.1 の形式に移す。

- 材料は、表示用の文字列(「大さじ2」)から数値と単位に分け、食材マスタの識別子を付ける。
- 写真は画面側の公開ディレクトリに移し、出典を各レシピのデータに持たせる。
- カロリーは今の概算値を捨て、成分表から計算し直す。今の値との差が大きいレシピは、材料の対応を見直す。
- 移行が終わり、新しいアプリで 38 品が表示できたら、`recipes/` を削除する。

`recipe` スキルは、HTML ではなく 7.1 の形式のデータを出すように改訂する。

### 段階

| 段階 | 内容 | 終わりの条件 |
|---|---|---|
| 0 | 開発の土台 | 画面と 3 つのサービスで、型検査、lint、テストが Docker の中で通る。kind に一式を載せ、登録してログインし、入口を通って `GET /api/me` が返るところまでを一通りつなぐ。4.4 の受け入れ条件が通る |
| 1 | スキーマと移行、一覧、詳細 | 38 品が一覧と詳細に表示され、データの検証が通る |
| 2 | 成分表と栄養計算 | 38 品で 1 人分の値が表示され、除いた材料が一覧できる |
| 3 | レシピ帳とレシピの編集 | 4.5 の受け入れ条件が通る |
| 4 | 今日の献立 | 4.6 の受け入れ条件が通る |
| 5 | 招待と共有 | 4.7 の受け入れ条件が通る。すべての API について、役割ごとの可否をテストで確かめている。`book-service` を止めた状態で、編集の保存が 503 で拒まれることを確かめている |
| 6 | 配置 | 置く場所を決めて本番に置く。メールの送信手段を決め、メールアドレスの確認とパスワードの再設定を足す |
| 7 | P1 の機能 | 複製、書き出し、印刷 |

各段階は、受け入れ条件のテストが通ってから次へ進む。
段階 0 でログインまでつなぐのは、後から足すと全体に手が入るためである。

## 12. 未決事項

- **配置する場所**: 機能ができてから決める。条件は、Kubernetes と PostgreSQL が動くこと、画面と API を同じオリジンで配れることである。
- **メールの送信**: 配置する場所と合わせて決める。それまでは、メールアドレスの確認とパスワードの再設定を持たない。パスワードを忘れた利用者は、管理者がデータベースで対応する。
- **ネイティブイメージ**: 配置する場所で起動の速さが必要になったら使う。それまでは通常の JVM で動かす。
- **成分表の記号の意味**: 変換元の Excel の入手先と列の構成は確かめた(データ設計の 5.6)。括弧の付いた記号の正確な意味を、成分表の第 1 章で確かめてから変換スクリプトを書く。
- **食材マスタの初期件数**: 38 品に出てくる材料から始める。表示する名前は 132 通りで、同じ食材をまとめた件数は移行で確定する。
- **バックアップ**: 配置する場所で戻せる範囲を確かめ、足りなければ書き出しの機能(P1)を前倒しする。
