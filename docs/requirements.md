# mana-cooks 要件定義書

作成日: 2026-09-25

## 1. 目的と背景

二人暮らしの献立決めを支えるための、個人向けクッキングアプリを作る。
解きたい課題は「毎日の献立が決まらない」「相手の苦手な食材をうっかり使う」「買い物の買い忘れ」の三つである。

本アプリは不特定多数への公開を目的としない。
利用者は二人(オーナーとパートナー)に限定し、その前提で認証と権限を最小構成にする。

運用費を発生させないことを制約とする。
Cloudflare の無料枠の範囲に収まる構成を選び、有料のサービスと独自ドメインを使わない。
この制約は技術選定を強く縛る(6 章)。

## 2. スコープ

### 2.1 対象とする機能

| 優先度 | 機能 | 概要 |
|---|---|---|
| P0 | 食材マスタ | 食材の登録、分類、単位の管理 |
| P0 | 好き嫌い管理 | 利用者ごとに食材の嗜好とアレルギーを登録する |
| P0 | レシピ管理 | レシピの登録、編集、一覧、詳細、検索 |
| P1 | レシピ提案 | 二人の嗜好を踏まえてレシピを並べ替えて提示する |
| P1 | 献立カレンダー | 日付と食事区分にレシピを割り当てる |
| P1 | 買い物リスト | 献立から必要な材料を集約してリスト化する |
| P1 | 栄養表示 | レシピと献立のエネルギーと主要栄養素を概算で表示する |
| P2 | 調理ログ | 作った日、評価、メモを残す |

### 2.2 対象としない機能

外部レシピサイトの自動取り込み、SNS 共有、スマートフォンのネイティブアプリ、多言語対応は今回の範囲に含めない。
栄養表示は主要 5 項目の概算にとどめ、ビタミンとミネラルの表示、摂取基準との比較、体重管理の機能は含めない。
将来対応の余地は残すが、初回リリースでは実装しない。

## 3. 利用者

| ロール | 想定 | 権限 |
|---|---|---|
| オーナー | アプリの管理者 | 全データの参照と編集、食材マスタの編集、利用者の招待 |
| パートナー | 彼女 | 全レシピの参照と編集、自分の嗜好の編集、献立と買い物リストの編集 |

レシピ、食材マスタ、献立、買い物リストは二人の共有データとする。
嗜好(好き嫌い)と調理ログだけが利用者ごとの個人データである。

## 4. 機能要件

### 4.1 認証

認証は **Cloudflare Access** に任せ、アプリでパスワードを持たない。

- ログインはメールアドレスへ届くワンタイムコードで行う。Access が許可したアドレスだけが通る。
- Access は Worker のコードに到達する前にリクエストを弾く。認証に Worker の CPU を使わない。
- アプリは Access が確認したメールアドレスを `users` 表と突き合わせ、表示名と役割を得る。
  Access を通っていても `users` に行が無いアドレスは 403 とする。
- 識別トークン(`Cf-Access-Jwt-Assertion`)は Worker 側でも検証する。
  Access の適用範囲に漏れがあったときに素通りさせないためである。
- サインアップ画面とログイン画面は設けない。初期ユーザーはシード(`scripts/seed.ts`)で作成する。

パスワードを自前で扱わないのは、無料プランでは安全に扱えないためである。
workerd は PBKDF2 の反復回数を 10 万回で頭打ちにしており、その 10 万回で CPU 10〜30 ms を消費する。
無料プランの上限は 1 リクエストあたり 10 ms なので、反復回数を下げないと収まらない。
そして 10 万回は OWASP が推奨する 60 万回を大きく下回る。
無料枠に合わせてハッシュを弱くする判断は採らない。

Cloudflare Zero Trust の Access は 50 ユーザーまで無料で、`workers.dev` の URL も保護できる。

#### ローカル開発

ローカルでは Access が動かないため、`DEV_USER_EMAIL` に指定したアドレスの利用者として扱う。
この変数がある間は識別トークンの検証を行わない。本番の環境変数に置かないこと。
`DEV_USER_EMAIL` も Access の設定も無い場合は、素通りさせず 401 を返す。

### 4.2 食材マスタと成分表

食材データは二層で持つ。

| 層 | 内容 | 件数の目安 |
|---|---|---|
| 食材マスタ (`Ingredient`) | 人が選ぶ単位。「こまつな」「豚ばら肉」 | 200〜400 |
| 成分表 (`foods.json`) | 日本食品標準成分表の収載食品をそのまま保持 | 約 2,500 |

成分表の収載単位は調理形態別に分かれており(「こまつな 葉 生」「こまつな 葉 ゆで」)、利用者に選ばせる単位としては細かすぎる。
そのため食材マスタを上に置き、そこから代表となる食品番号を 1 件参照する。
好き嫌い、レシピの材料、買い物リストはすべて食材マスタだけを参照し、成分表は栄養計算からのみ引く。

成分表はデータベースへ入れず、リポジトリ管理の JSON として持つ(8 章を参照)。
アプリから書き換えない読み取り専用データであり、版ごと差し替えられるほうが扱いやすいためである。

#### 食材マスタ

- 食材は名称、カテゴリ(野菜、肉、魚介、乳製品、穀類、調味料、その他)、標準単位(g、ml、個、大さじ等)を持つ。
- 名称は一意とする。表記ゆれは別名(エイリアス)で吸収する。
- 代表となる成分表の食品番号を任意で持つ。未設定の食材は栄養計算の対象外とする。
  番号の入力は、`public/data/foods.json` を用意して存在を検証できるようになってから開く。
- 食品番号は JSON 側のキーを指すため、データベースの外部キー制約では守れない。食材の保存時に、その番号が `public/data/foods.json` に存在することを検証する。
- レシピや嗜好から参照されている食材は削除できない。

#### 成分表データの取り込み

- 出典は文部科学省の**日本食品標準成分表(八訂)増補2023年**とする。Excel 形式で公開されており、出典を明記すれば二次利用できる。
- 変換スクリプトで Excel から `public/data/foods.json` を生成し、生成物をリポジトリへコミットする。変換はビルド時とアプリ実行時には行わない。
- アプリは起動時に `public/data/foods.json` を読み、メモリへ常駐させる。実行中に外部へ問い合わせない。
- 保持する成分はエネルギー(kcal)、たんぱく質(g)、脂質(g)、炭水化物(g)、食塩相当量(g)の 5 項目とし、すべて可食部 100 g あたりの値とする。
- 欠損記号を区別してパースする。`-`(未測定)と `Tr`(微量)は `null` として扱い、`(0)` と `0` は `0` として扱う。`null` と `0` を混同しない。
- 読み込み時に Zod で全件を検証する。想定外の形式があれば起動を止め、黙って欠損値として扱わない。
- 画面のいずれかに出典表記「日本食品標準成分表(八訂)増補2023年から引用」を常時掲載する。

#### 単位の重量換算

- 食材ごとに、単位から g への換算率を持つ(`大さじ1 = 15 ml`、`卵 1個 = 50 g` 等)。
- 初期値は `public/data/unit-conversions.json` から投入し、以降はデータベースで管理する。利用者が編集するデータであるためである。
- 換算率が未登録の組み合わせは栄養計算の対象外とする。
- 換算率は利用者が編集できる。実際に使う分量に合わせて調整するためである。

### 4.3 好き嫌い管理

- 利用者は食材ごとに嗜好レベルを登録する。
- 嗜好レベルは `LOVE`(大好き)、`LIKE`(好き)、`NEUTRAL`(普通)、`DISLIKE`(苦手)、`HATE`(食べられない)、`ALLERGY`(アレルギー)の六段階とする。
- 未登録の食材は `NEUTRAL` として扱う。
- 嗜好には自由記述のメモを添えられる(例: 「火を通せば食べられる」)。
- 一覧画面ではカテゴリ別に表示し、二人分を並べて比較できる。
- `ALLERGY` は安全に関わるため、画面上で明確に区別して表示する。
- 嗜好を編集できるのは本人と、全データを編集できるオーナーに限る。
  好き嫌いは本人にしか分からないため、パートナーは他人の分を書き換えられない。
- 「普通」へ戻す操作は、嗜好の登録を消すことで表す。行が無い状態が `NEUTRAL` を意味する。

### 4.4 レシピ管理

レシピは次の情報を持つ。

- 基本情報: タイトル、説明、写真、人数分、下ごしらえ時間、調理時間、出典URL
- 材料: 食材マスタへの参照、分量、任意材料フラグ、表示順
- 手順: 表示順、本文、手順写真(任意)
- 分類: カテゴリ(主菜、副菜、汁物、主食、デザート)を一つ、タグ(和食、時短、作り置き等)を複数

カテゴリは固定の集合のため、コード側(`src/shared/enums.ts`)に定数として持つ。
タグは利用者が自由に増やせるため、データベースで持つ。

材料の分量は「数値 + 単位」を基本とし、数値化できないものは自由記述として受け付ける。
入力欄は数値と単位を分けて持ち、「少々」「適量」は自由記述欄へ入れる。
自由記述の材料は栄養計算の対象外とする。

機能として、作成、編集、削除、一覧、詳細表示、キーワード検索、カテゴリとタグによる絞り込み、お気に入り登録を備える。
一覧では各レシピに「この人が食べられるか」を示すバッジを表示する。

### 4.5 レシピ提案

指定した対象者(既定は二人)の嗜好をもとに、レシピをスコア順に並べて提示する。

判定と並べ替えの規則は次のとおり。

1. 対象者のいずれかが `ALLERGY` の食材を必須材料に含むレシピは、候補から除外する。
2. `HATE` の食材を必須材料に含むレシピは、既定で除外する(画面上の切り替えで表示できる)。
3. 任意材料に該当する場合は除外せず、「この材料を抜けば作れる」と表示する。
4. 残った候補に加点する。`LOVE` は +3、`LIKE` は +1、`DISLIKE` は -2 を材料ごとに合算する。
5. 直近 14 日以内に調理ログがあるレシピは減点し、献立の偏りを抑える。

スコアの算出根拠(どの食材が効いたか)を詳細画面に表示し、結果を説明できるようにする。

### 4.6 献立カレンダー

- 週表示と月表示を持つ。
- 一日は朝食、昼食、夕食、間食の四区分とする。
- 各区分にレシピを複数割り当てられる。
- レシピを割り当てない自由記述の予定(外食等)も登録できる。
- 提案機能から献立へ直接割り当てられる導線を持つ。

### 4.7 買い物リスト

- 期間(開始日と終了日)を指定して、献立から材料を集約したリストを生成する。
- 同一食材は分量を合算せず、レシピごとの分量を併記する(単位が揃わないため)。
- 手動での項目追加と削除ができる。
- 購入済みのチェックができ、チェック状態は二人で共有する。

### 4.8 調理ログ

- レシピ詳細から「作った」を記録する。日付、5 段階評価、メモを残す。
- 記録はレシピ提案の減点と、よく作るレシピの集計に使う。

### 4.9 栄養表示

- 表示する項目はエネルギー(kcal)、たんぱく質、脂質、炭水化物、食塩相当量の 5 項目とする。
- レシピ詳細では 1 人分あたりの値を表示する。レシピの人数分で割って算出する。
- 献立カレンダーでは 1 日の合計値を表示する。
- 算出は次の順で行う。材料の分量を g へ換算し、食材マスタが参照する成分表の 100 g あたりの値に掛け、全材料を合算する。

#### 概算であることの扱い

次の材料は計算から除外する。

- 自由記述の分量(「少々」「適量」)
- 単位から g への換算率が未登録の材料
- 代表となる食品番号が未設定の食材

除外した材料が一つでもある場合、表示に「概算値」と明示し、除外した材料名を一覧できるようにする。
計算に含めた材料の割合も併記する。
正確そうに見える数値だけを出して、実際には調味料が抜けている状態を避けるためである。

計算できた材料が一つもないレシピでは、数値を出さず「栄養値は未算出」と表示する。

## 5. 非機能要件

| 項目 | 要件 |
|---|---|
| 対応環境 | スマートフォンのブラウザを主とし、PC ブラウザにも対応する。最新の Chrome と Safari を対象とする |
| 導線 | PWA のマニフェストを持ち、スマートフォンのホーム画面へ追加できる。オフライン動作は対象としない |
| 性能 | レシピ一覧と提案の表示は 100 レシピ規模で 1 秒以内。Worker の CPU 時間は 1 リクエストあたり 10 ms 未満に収める |
| 可用性 | 24 時間稼働させる。個人利用のため冗長構成は取らない |
| 運用費 | 月額 0 円とする。無料枠を超える構成を採らない |
| セキュリティ | 認証は Cloudflare Access に任せ、パスワードを保持しない。疎通確認を除く全 API を認証必須とする。画像アップロードは形式とサイズを検証する |
| バックアップ | D1 のエクスポートを日次で取得し、7 世代保持する。R2 の画像はオブジェクトの一覧と併せて保管する |
| ログ | Workers のログへ構造化して出力する。無料プランの保持期間は短いため、永続化が要る記録はログに頼らない |
| 国際化 | 日本語のみ。表示するテキストは定数へ集約し、将来の多言語化を妨げない |

## 6. 技術構成

| レイヤ | 採用 |
|---|---|
| 画面 | Vite + React + TypeScript + Tailwind CSS(SPA) |
| API | Hono on Cloudflare Workers |
| ORM | Drizzle ORM |
| データベース | Cloudflare D1 (SQLite 互換) |
| マスタデータ | リポジトリ管理の JSON。静的アセットとして配信する |
| 画像保存 | Cloudflare R2 |
| 配信 | Cloudflare Workers Static Assets |
| ローカル開発 | Docker Compose 上の `vite dev`(@cloudflare/vite-plugin) |
| テスト | Vitest(単体) + Playwright(E2E) |

### サーバー側でレンダリングしない

画面はブラウザ側で描画する SPA とし、サーバー側のレンダリングを行わない。

Workers の無料プランは 1 リクエストあたりの CPU 時間が 10 ms である。
サーバー側で React を描画するとこれに収まらず、`Error 1102` で失敗する。
静的アセットの配信は無料かつ無制限で CPU を消費しないため、画面を静的アセットとして配り、Worker には D1 を引いて JSON を返す仕事だけを残す。

この制約は結果として都合がよい。
栄養値の算出とレシピ提案のスコア計算はドメイン層に置き、**ブラウザ側で実行する**。
Worker の CPU を一切使わず、成分表もブラウザがキャッシュした JSON を引くだけで済む。
レシピが 100 件規模であれば、一覧をまとめて取得して手元で計算するほうが速い。

### ORM に Drizzle を使う

Prisma はクライアントとクエリエンジンで約 2.5 MB あり、無料プランの圧縮 3 MB というバンドル上限に対して現実的に収まらない。
起動時の CPU も 10 ms に算入されるため、重いランタイムは二重に不利になる。
Drizzle は 7 KB 程度で D1 をネイティブに対応しており、この構成では実質的に唯一の選択肢である。

### ディレクトリ構成

```
src/
├── client/            # React SPA
│   ├── routes/        # 画面
│   ├── components/    # 再利用UI
│   └── api/           # Worker API を呼ぶ fetch クライアント
├── server/            # Hono の Worker
│   ├── index.ts       # エントリ。静的アセットと /api/* の振り分け
│   ├── routes/        # リソースごとのハンドラ
│   ├── middleware/    # 認証、エラー変換
│   └── db/            # Drizzle のスキーマとクエリ
├── domain/            # 業務ロジック。client と server の両方から使う
│   ├── nutrition/     # 栄養値の算出
│   ├── suggestion/    # レシピ提案のスコア計算
│   └── errors.ts
└── shared/            # Zod スキーマと型。client と server で共有する
drizzle/               # drizzle-kit が生成するマイグレーション
public/data/           # マスタデータの JSON。/public/data/*.json として配信される
scripts/               # 成分表の変換スクリプト
index.html             # SPA のシェル
wrangler.jsonc
vite.config.ts
compose.yaml
```

型検査は `tsconfig.app.json`(`src/`)と `tsconfig.node.json`(設定と `scripts/`)に分ける。
`src/` からは Node の型を見せない。Worker でもブラウザでも動かないコードが型検査を通るのを防ぐためである。

`src/domain/` は React にも Hono にも Drizzle にも依存させない。
同じコードをブラウザと Worker の両方で動かすための制約である。
`src/shared/` の Zod スキーマは、画面の入力検証と API の入力検証で同じものを使う。

### データの置き場の使い分け

| 性質 | 置き場 | 対象 |
|---|---|---|
| 読み取り専用で版ごと差し替えるもの | `public/data/*.json`(静的アセット) | 成分表、単位換算の初期値 |
| 固定の集合 | `src/shared/enums.ts` | 嗜好レベル、食材の分類、レシピの分類、食事区分 |
| 利用者が書き込むもの | D1 | 利用者、食材マスタ、嗜好、レシピ、献立、買い物リスト、調理ログ、単位換算 |
| 大きなバイナリ | R2 | レシピと手順の画像 |

利用者が書き込むデータを JSON ファイルで持たない。
二人が同時に触る場面(買い物リストのチェック、献立の編集)で読み書きが競合し、後から書いた側が相手の変更を消すためである。

成分表(`public/data/foods.json`)は静的アセットとして配信し、ブラウザが取得してキャッシュする。
Worker も D1 も経由しないため、無料枠を一切消費しない。

### 運用環境

Cloudflare の無料枠で完結させる。サーバーを持たず、ドメインを取得しない。

| 資源 | 無料枠 | 二人での利用 |
|---|---|---|
| Workers リクエスト | 10 万/日 | 十分 |
| Workers CPU | 10 ms/回 | JSON を返すだけなら収まる |
| 静的アセット | 無制限・無料 | 画面と成分表を配る |
| D1 | 5 GB、読み 500 万行/日、書き 10 万行/日 | 十分 |
| R2 | 10 GB | 十分 |

公開 URL は `workers.dev` のサブドメインを使う。HTTPS は自動で付く。

D1 は 2026 年 9 月 1 日から、無料アカウントで 1 日の行数上限を超えたクエリがエラーを返すようになった。
二人の利用では届かないが、全件走査を繰り返すクエリを書くと落ちる。
一覧の取得に上限件数を設け、`SELECT *` の無条件取得をしない。

### SPA のフォールバック

`not_found_handling: "single-page-application"` を設定しても、Worker が存在する場合、
静的アセットに無い URL はまず Worker へ渡る。
そのため Worker の最後に、`ASSETS` バインディング経由で SPA のシェルを返すハンドラを置く。

`/api/*` の 404 はそれより前で JSON として返す。
API のパス誤りに index.html が返ると、原因が分かりにくくなるためである。

### 無料枠を守るための制約

- Worker のハンドラで重い計算をしない。整形と検証に留め、集計はブラウザ側かクエリ側で行う。
- 画像は R2 へ直接置き、Worker を経由して配信しない。
- Worker のバンドルを膨らませない。依存を足すときは圧縮後のサイズを確認する。
- `public/data/*.json` を Worker のバンドルへ取り込まない。静的アセットとして配る。

## 7. データモデル

```
User ──< IngredientPreference >── Ingredient
User ──< CookingLog >── Recipe
User ──< Favorite >── Recipe

Recipe ──< RecipeIngredient >── Ingredient
Ingredient ──< UnitConversion   (単位 → g の換算率)
Ingredient ──> foods.json       (代表食品番号。DB外の参照)
Recipe ──< RecipeStep
Recipe ──< RecipeTag >── Tag
Recipe ──> Category

MenuEntry ──> Recipe  (date, mealType)
ShoppingList ──< ShoppingListItem ──> Ingredient
```

| モデル | 役割 |
|---|---|
| `User` | 利用者。パスワードは持たない。Access のメールアドレスと突き合わせる |
| `Ingredient` | 食材マスタ |
| `IngredientAlias` | 食材の表記ゆれ吸収 |
| `UnitConversion` | 食材ごとの単位から g への換算率 |
| `IngredientPreference` | 利用者ごとの嗜好レベル |
| `Recipe` | レシピ本体 |
| `RecipeIngredient` | レシピの材料(数値量、単位、自由記述、任意フラグ) |
| `RecipeStep` | レシピの手順 |
| `Category` | レシピのカテゴリマスタ |
| `Tag` / `RecipeTag` | レシピのタグ |
| `Favorite` | お気に入り |
| `CookingLog` | 調理ログ |
| `MenuEntry` | 献立の一コマ |
| `ShoppingList` / `ShoppingListItem` | 買い物リスト |

スキーマは Drizzle で `src/server/db/schema.ts` に定義し、マイグレーションは `drizzle-kit` で生成して `wrangler d1 migrations apply` で適用する。

成分表はデータベースに含めない。`public/data/foods.json` が正本である。
`Ingredient.foodNumber` はその JSON のキーを指す文字列であり、データベースの外部キー制約は効かない。
整合性はアプリ側の検証で保つ。

D1 は SQLite であるため、小数は浮動小数になる。
成分値と分量は概算表示のため許容する。誤差が問題になる値をこの型で扱わない。

削除は物理削除とする。
`deletedAt` を追加できる構造にはしておく。

## 8. リポジトリ管理のデータファイル

| ファイル | 内容 | 更新の契機 |
|---|---|---|
| `public/data/foods.json` | 成分表の収載食品と成分値(約 2,500 件) | 成分表の増補版が出たとき |
| `public/data/ingredients.json` | 食材マスタの初期データ | 初期構築時。以降はアプリ上で編集する |
| `public/data/unit-conversions.json` | 単位換算の初期値 | 同上 |
| `scripts/build-foods.ts` | 成分表 Excel から `foods.json` を生成する変換スクリプト | 増補版の取り込み時に手で実行する |
| `scripts/seed.ts` | `public/data/*.json` から D1 へ初期データを投入する | 初期構築時 |

画像は R2 に置く。リポジトリには含めない。

`public/data/` は静的アセットとして配信され、`/public/data/*.json` で取得できる。
秘密情報を置かない。

`ingredients.json` と `unit-conversions.json` は初期投入にのみ使う。
投入後はデータベース側が正本となり、JSON を編集しても反映されない。
再投入は空のデータベースに対してのみ行う。

## 9. 画面一覧

画面はクライアント側のルーティング(React Router)で切り替える。
下記のパスはブラウザの URL であり、サーバー側のルートではない。
どのパスへ直接アクセスされても、Worker は同じ HTML を返す。

| 画面 | パス | 概要 |
|---|---|---|
| ログイン | `/login` | メールアドレスとパスワードの入力 |
| ホーム | `/` | 今日の献立、提案レシピ、買い物リストの要約 |
| レシピ一覧 | `/recipes` | 検索、カテゴリとタグの絞り込み |
| レシピ詳細 | `/recipes/[id]` | 材料、手順、嗜好バッジ、1 人分の栄養値、調理ログの記録 |
| レシピ編集 | `/recipes/[id]/edit`, `/recipes/new` | 登録と編集 |
| 提案 | `/suggest` | 対象者を選んでスコア順に表示 |
| 食材と好み | `/ingredients` | 食材マスタと嗜好の登録、二人分の比較 |
| 食材詳細 | `/ingredients/[id]` | 100 g あたりの成分値、単位換算率の編集、代表食品番号の割り当て |
| 献立カレンダー | `/menu` | 週表示と月表示、1 日の栄養合計 |
| 買い物リスト | `/shopping` | 期間指定の生成とチェック |
| 設定 | `/settings` | 表示名、パスワード変更 |

## 11. 未決事項

- レシピ一覧をブラウザへ一括で渡す方式が、何件まで実用に耐えるか。100 件想定では問題ないが、増えたときに一覧の取得を分割する境界を決める。
- 画像を R2 のどの経路で配信するか。公開バケットにするか、署名付き URL を使うか。認証の要否と、Worker を経由させない方針との兼ね合いで決める。
- 食材マスタの初期データをどこまで用意するか。成分表 2,500 件から日常的に使う 200〜400 件を選ぶ作業が要る。カテゴリを絞って機械的に抽出するか、手で選ぶかを決める。
- 単位換算率の初期値をどこまで用意するか。調味料の大さじ・小さじは一律の換算でよいが、「1個」「1本」は食材ごとに異なる。よく使う食材から順に埋める運用でよいか。
- 成分表の増補版が更新されたときの取り込み手順。食品番号は版をまたいで変わりうるため、食材マスタからの参照が切れる場合の扱いを決める。差し替え後に全食材の `foodNumber` を検証し、消えた番号を一覧するコマンドを用意する案がある。
- 画像のアップロード経路。Worker を経由すると CPU と帯域を使うため、R2 への直接アップロード(署名付き URL)が望ましいが、実装の手間との兼ね合いを見る。
