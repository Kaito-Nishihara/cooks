おうちレシピ帖 アーキテクチャ

2026-10-10 時点の設計。正本は 要件定義 の 6 章で、この図はその内容を絵にしたものである。

全体の構成

ブラウザからの要求は、すべて入口を通る。入口はパスで振り分け、ログインが要る要求は先に auth-service に確かめさせる。データベースはサービスごとに分け、ほかのサービスのデータベースを読まない。

外からの要求と、データベースの読み書き サービスの間だけの呼び出し(/internal、REST と署名付きトークン) ビルド時

サービスの受け持ち

サービス受け持つもの入口が振り分けるパス持つデータ
frontend 画面の静的なファイルを配る ほかに当てはまらないパス なし。元のレシピはビルド時に組み込む
auth-service 登録、ログイン、セッション、パスワード。入口からのログインの確認に答える /api/auth、/api/me 利用者、セッション
book-service レシピ帳、メンバー、招待。「誰がどのレシピ帳で何をできるか」の正本 /api/books、/api/invitations レシピ帳、メンバー、招待
kitchen-service レシピの編集内容、献立 /api/books/{bookId}/recipe-edits、/api/books/{bookId}/menus 編集内容、献立

レシピの編集を保存するときの流れ

ログインの確認と権限の確認が、どのサービスで行われるかを示す。

  1. ブラウザが、セッションのクッキーを付けて PUT /api/books/{bookId}/recipe-edits/{slug} を送る。
  2. 入口が、要求を渡す前に auth-service にクッキーを確かめさせる。
  3. auth-service は、セッションが有効なら、利用者の識別子を入れた署名付きトークン(期限は 1 分)を返す。無効なら入口が 401 を返す。
  4. 入口が、トークンを付けて要求を kitchen-service へ渡す。
  5. kitchen-service が、トークンの署名を確かめて利用者を特定する。
  6. kitchen-service が、book-service にその人のレシピ帳での役割を問い合わせる。
  7. メンバーでなければ 404、見るだけの人なら 403 を返す。book-service が応答しなければ 503 を返す。どの場合も保存しない。
  8. 改訂番号が合えば保存し、合わなければ 409 を返す。

この図で読み取ってほしい決まり

  1. ブラウザに見えるのはクッキーだけである。トークンは入口より後ろでしか使わない。
  2. 権限は book-service が正本である。ほかのサービスは、権限を自分で判断せずに問い合わせる。
  3. 権限が確かめられないときは拒む。
  4. 栄養計算と分量の換算はブラウザだけで行う。どのサービスも同じ計算を持たない。
  5. 元のレシピ、食材マスタ、成分表はデータベースに入れない。リポジトリのファイルとして持ち、ビルド時に画面へ組み込む。
入口の実装と、クラスタへ載せる道具は未決である(requirements.md の 12 章)。決まったらこの図に名前を書き足す。
