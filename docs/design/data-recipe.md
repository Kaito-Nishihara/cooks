# データ設計: 元のレシピ、食材マスタ、成分表

対応する Issue: #7

## 1. 目的

Claude Code が作るレシピのデータの形を決める。
この形は、レシピを作る側(`recipe` スキル)と、表示して計算する側(画面)の間の約束になる。
約束を先に決めておくと、スキルが書いた誤りを、画面を開く前に検証の仕組みで止められる。

## 2. 範囲

やること:

- 元のレシピの JSON の全項目と制約
- 使える単位の一覧と、分量の表記の決まり
- 食材マスタの項目と、識別子の付け方
- 単位から g への換算率の持ち方
- 成分表の入手、変換の手順、欠損の扱い
- ブラウザへ渡すデータの形と大きさ
- データの検証(`check:data`)の項目
- 静的レシピ集の 38 品を移す手順
- 写真の置き場、大きさ、出典の持ち方
- `recipe` スキルを直す点
- 編集内容を元のレシピに重ねるために要る識別子

やらないこと:

- 編集内容の JSON の形。レシピの編集の仕様書(Issue #12)に書く。ここでは、編集内容が元のレシピのどこを指すかの識別子だけを決める
- 栄養計算の式の細部と、画面での値の丸め方。栄養計算の仕様書に書く
- 分量を分数に直す計算の細部。レシピ詳細の仕様書に書く
- データをページへ組み込む仕組み(Next.js のどの機能で読むか)。画面の共通設計(Issue #6)に書く
- 献立のデータの形。今日の献立の仕様書に書く

### この文書で使う言葉

| 言葉 | 意味 |
|---|---|
| 元のレシピ | Claude Code が作り、リポジトリの `data/recipes/` に置く 1 品分の JSON。アプリからは書き換えない |
| 編集内容 | 利用者がレシピ帳の中で元のレシピを直した内容。`kitchen-service` のデータベースに入る |
| 重ねる | 元のレシピに編集内容を当てはめて、表示する 1 つのレシピを作ること。ブラウザで行う |
| 食材マスタ | 食材の一覧(`data/ingredients.json`)。人が選ぶ粒度で食材を持ち、成分表の食品を 1 件指す |
| 成分表 | 文部科学省の日本食品標準成分表。食品ごとに、可食部 100g あたりの栄養の値を載せた表 |
| 食品番号 | 成分表が食品に付けている 5 桁の番号。例: `11221`(にわとり 若どり もも 皮つき 生) |
| 可食部 | 食材のうち、皮や殻や芯を除いた食べる部分 |
| 換算率 | ある単位の 1 つ分が何 g かを表す数。例: 醤油の大さじ 1 は 18g |
| `slug` | レシピの識別子。ファイル名と同じ。例: `oyakodon` |
| スキーマ | JSON の形の決まりを、機械が確かめられる形で書いたもの。ここでは Zod(TypeScript の検証のライブラリ)で書く |
| `check:data` | データの誤りを検証するコマンド。`npm run check:data` で走らせる |
| 摂取する割合 | 材料のうち実際に食べる分の割合。揚げ油のように全量を食べない材料に付ける |

## 4. API

なし。
元のレシピ、食材マスタ、成分表は、リポジトリのファイルである。
画面のビルドのときにページへ組み込み、API では配らない。

## 5. データ

### 5.1 ファイルの置き場と、書き方の共通の決まり

| ファイル | 中身 | 書く人 |
|---|---|---|
| `data/recipes/<slug>.json` | 元のレシピ。1 品 1 ファイル | Claude Code(`recipe` スキル) |
| `data/ingredients.json` | 食材マスタ | Claude Code(`recipe` スキル) |
| `data/foods.json` | 成分表から変換したもの | 変換スクリプト。手で書き換えない |
| `frontend/public/photos/<slug>/<ファイル名>` | 写真 | Claude Code(`recipe` スキル) |
| `frontend/src/schema/` | 上の 3 種類の JSON のスキーマ(Zod) | 実装する Claude |

どのファイルもデータベースに入れない。
アプリから書き換えない読み取り専用のデータだからである(要件定義 7.2)。

JSON の書き方は次のとおりとする。

- 文字コードは UTF-8、改行は LF とし、ファイルの末尾に改行を 1 つ置く。Git の差分で、内容の変更だけが見えるようにするためである。
- Windows の Git は、設定によって、取り出すときに改行を CRLF に変える。`data/` の JSON が LF のまま取り出されるように、段階 0 で `.gitattributes` に `data/**/*.json text eol=lf` を書く。
- 字下げは半角の空白 2 つとする。
- 項目名は camelCase とする。API の JSON(`common-api.md` の 4.3)と同じ決まりにして、画面のコードで 2 通りの書き方が混ざらないようにする。
- 値がない項目は、項目ごと書かない。`null` と空の文字列を書かない。「ない」の表し方を 1 つにするためである。例: 目安時間のない手順は `timeText` を持たない。
- スキーマにない項目を書くと、検証で落とす。項目名の打ち間違い(`ingredentId` など)が、黙って無視されるのを防ぐためである。
- 一番外側に、形の版を表す `schemaVersion`(整数。今は 1)を持つ。形を変えたときに、古い形のファイルを見分けるためである。編集内容の JSON の列(`common-database.md` の 5.5)と同じ考え方である。

### 5.2 元のレシピ

#### レシピの項目

「必須」が「○」の項目は必ず書く。
文字数は、Unicode の文字の数で数える。

| 項目 | 型 | 必須 | 制約 | 内容 |
|---|---|---|---|---|
| `schemaVersion` | 整数 | ○ | `1` | JSON の形の版 |
| `slug` | 文字列 | ○ | 英小文字、数字、ハイフン。先頭と末尾はハイフンにしない。64 文字まで。ファイル名(拡張子を除く)と同じ | レシピの識別子 |
| `version` | 整数 | ○ | 1 以上 | 元のレシピの版。下の「版の決まり」に従う |
| `name` | 文字列 | ○ | 1〜40 文字 | 料理名。例: 「親子丼」 |
| `reading` | 文字列 | ○ | 1〜100 文字。ひらがな、長音の記号、半角の空白だけ | 検索用の読み。別名があれば半角の空白で区切って足す。例: 「そぼろどん さんしょくどん」 |
| `romanName` | 文字列 | ○ | 1〜40 文字。英大文字、数字、半角の空白、ハイフンだけ | 料理名のローマ字。写真の上に小さく添える。例: 「OYAKODON」 |
| `arrangeLabel` | 文字列 | | 1〜30 文字 | アレンジ版のときだけ書く。変更点の名前。例: 「鶏むね肉でさっぱり」 |
| `arrangeOf` | 文字列 | | `slug` と同じ形。`arrangeLabel` があるときだけ書ける | アレンジの元になったレシピの `slug`。元のレシピがこのレシピ集にないときは書かない |
| `arrangeChanges` | 文字列の配列 | | 1〜5 件。1 件は 1〜100 文字。`arrangeLabel` があるときは必須で、ないときは書けない | 元から何をどう変えたかの箇条書き |
| `genres` | 文字列の配列 | ○ | ちょうど 2 件。1 件目は系統、2 件目は種類。値は下の「ジャンルの値」から選ぶ | 絞り込みに使う分類 |
| `description` | 文字列 | ○ | 1〜120 文字。改行を含めない | 検索エンジンと共有のときに出る、1〜2 文の紹介 |
| `lead` | 文字列 | ○ | 1〜200 文字。改行(`\n`)は 2 つまで | リード文。改行は、画面でも改行として表示する |
| `time` | 整数 | ○ | 1〜600 | 調理時間(分) |
| `level` | 整数 | ○ | 1、2、3 のいずれか | 難易度。画面では星の数で表す |
| `tool` | 文字列 | ○ | 1〜40 文字 | 主に使う道具。例: 「小さめのフライパン」 |
| `servings` | 整数 | ○ | `2` | 基本の人数。材料の分量は、この人数の分で書く |
| `ingredientGroups` | 配列 | ○ | 1〜10 件。材料の合計は 50 件まで | 材料のグループ |
| `steps` | 配列 | ○ | 1〜20 件 | 手順。並び順が作る順である |
| `tips` | 配列 | ○ | 0〜10 件 | コツ |
| `photos` | 配列 | ○ | 1〜6 件。`role` が `hero` のものがちょうど 1 件 | 写真 |

`servings` を 2 に固定するのは、要件定義 7.1 の決まりである。
人数の換算は「表示する人数 ÷ `servings`」を分量に掛けて行うので、項目としては残す。

一覧のカードに出す分類(今の静的レシピ集の `kicker`)は、項目として持たない。
`genres` の 2 件目と同じ値だからである。
今の 38 品すべてで、`kicker` と `genres` の 2 件目が一致することを確かめた。

アレンジ版の画面での名前は、`name` と `arrangeLabel` から「親子丼(鶏むね肉でさっぱり)」の形に組み立てる。
組み立てた名前を別の項目で持つと、片方だけ直したときに食い違うためである。

#### 版の決まり

`version` は、編集内容が元のレシピのどの版をもとにしたかを判定するために使う(要件定義 4.5 の「元のレシピが後から更新されたとき」)。

- 新しく作ったレシピは `1` から始める。
- レシピのファイルを直して `main` に入れるたびに、1 増やす。1 つの PR の中で何度直しても、増やすのは 1 回である。
- 利用者に見えない変更(字下げの直しなど)でも増やす。「見える変更かどうか」の判断を人に任せると、増やし忘れが起きるためである。
- 写真のファイルだけを差し替え、JSON を変えないときは増やさない。写真は編集の対象でないためである。

例: 親子丼の醤油を大さじ 2 から大さじ 1.5 に直す PR では、`version` を 1 から 2 にする。
`version` が 1 のときに保存された編集内容は、`baseVersion` が 1 なので、画面は「元が更新された」と知らせる。

#### ジャンルの値

ジャンルは、決まった値の一覧から選ぶ。
自由な文字列にすると、「炒めもの」と「炒め物」のような表記のゆれで、絞り込みのボタンが 2 つに分かれるためである。

| 軸 | 値 |
|---|---|
| 系統(1 件目) | 和食、韓国風、中華、洋食 |
| 種類(2 件目) | 丼もの、ご飯もの、麺、煮物、汁物、炒め物、炒め煮、焼き物、揚げ物、卵料理、副菜 |

一覧は、今の 38 品が使っている値である。
値を足すときは、スキーマの一覧と、この表と、`recipe` スキルの表の 3 か所を同じ PR で直す。

#### 材料のグループ

| 項目 | 型 | 必須 | 制約 | 内容 |
|---|---|---|---|---|
| `id` | 文字列 | ○ | `g` と 1〜999 の数。レシピの中で重複しない | グループの識別子。5.4 に従う |
| `name` | 文字列 | ○ | 1〜30 文字 | グループの名前。例: 「具」「割下」「ナムルのタレ(3種分)」 |
| `ingredients` | 配列 | ○ | 1〜30 件 | 材料 |

#### 材料

| 項目 | 型 | 必須 | 制約 | 内容 |
|---|---|---|---|---|
| `id` | 文字列 | ○ | `i` と 1〜999 の数。レシピの中で重複しない | 材料の識別子。5.4 に従う |
| `ingredientId` | 文字列 | | 食材マスタにある `id` | 食材マスタの識別子。マスタにない材料では書かない |
| `name` | 文字列 | ○ | 1〜40 文字 | 表示する名前。切り方や代わりの食材を括弧で添えてよい。例: 「しょうが(すりおろし)」「焼豚(またはハム)」 |
| `amount` | 数値 | | 0 より大きく 10000 以下。小数は 4 桁まで | `servings` 人分の分量 |
| `unit` | 文字列 | | 5.3 の単位の一覧にある値 | 単位 |
| `note` | 文字列 | | 1〜20 文字 | 数値で表せない分量の表記。例: 「少々」「適量」「好みで」「ひとつまみ」 |
| `intakeRatio` | 数値 | | 0 以上 1 以下。`amount` があるときだけ書ける | 摂取する割合。書かないときは 1 として扱う |

分量は、「`amount` と `unit` の組」か「`note`」の、どちらか一方だけを書く。
両方を書くと、どちらを表示して、どちらで計算するかが決まらないためである。

- 数値で表せる例: `{ "amount": 250, "unit": "g" }`
- 数値で表せない例: `{ "note": "適量" }`
- 落とす例: `amount` だけで `unit` がない。`amount` と `note` の両方がある。どちらもない。

`name` を `ingredientId` と別に持つのは、同じ食材でも、レシピごとに見せたい名前が違うためである。
例: 食材マスタの「しょうが」を、あるレシピでは「しょうが(すりおろし)」、別のレシピでは「しょうが」と表示する。
食材マスタから食材が消えても、`name` があれば表示は保てる。

1/3 のように割り切れない分量は、小数 4 桁で書く。
例: 1/3 は `0.3333`、2/3 は `0.6667`。
画面は、分数に直すときに近い分母を選ぶので、この誤差は表示に出ない。

`intakeRatio` は、全量を食べない材料に付ける。
付ける基準は次のとおりとする。

| 場面 | 値 | 例 |
|---|---|---|
| 揚げ油 | 吸う油の割合の見込みを書く | 揚げ油 500ml に `0.1` |
| 飲み干さない汁やつけダレ | 食べる分の見込みを書く | 冷やし中華のタレに `0.7` |
| 香り付けだけで取り出すもの | `0` | ローリエ |
| そのほか | 書かない | |

値は見込みであり、根拠のある数字ではない。
付けたときは、PR の本文に、どの材料に何を付けたかを書く。

#### 手順

| 項目 | 型 | 必須 | 制約 | 内容 |
|---|---|---|---|---|
| `id` | 文字列 | ○ | `s` と 1〜999 の数。レシピの中で重複しない | 手順の識別子。5.4 に従う |
| `title` | 文字列 | ○ | 1〜40 文字 | 見出し。例: 「割下で玉ねぎを煮る」 |
| `text` | 文字列 | ○ | 1〜400 文字。改行を含めない | 本文 |
| `timeText` | 文字列 | | 1〜20 文字 | 目安時間。画面にそのまま出す。例: 「5分」「2〜3分」「30秒」「30分以上」 |

目安時間を数値でなく文字列で持つのは、今の 38 品の書き方 25 通りのうち 13 通りが、「2〜3分」「30分以上」のような、1 つの数で表せない書き方だからである。
手順の目安時間を合計する機能はないので、数値に分ける必要がない。
レシピ全体の調理時間は、`time` に分の数で持つ。

#### コツ

| 項目 | 型 | 必須 | 制約 | 内容 |
|---|---|---|---|---|
| `id` | 文字列 | ○ | `t` と 1〜999 の数。レシピの中で重複しない | コツの識別子。5.4 に従う |
| `text` | 文字列 | ○ | 1〜200 文字。改行を含めない | 本文 |

#### 写真

写真の項目は 5.9 に書く。

#### 持たない項目

- **栄養の値**: 持たない。材料から計算した値と食い違うのを防ぐためである(要件定義 7.1)。
- **検索用の材料名の一覧**: 持たない。今の静的レシピ集は目録に別に書いていたが、材料の `name` と、食材マスタの `name` と `aliases` から作れる。
- **分量の丸め方**: 持たない。5.3 の決まりで、単位と食材マスタから決まる。

### 5.3 単位と、分量の表記

#### 使える単位

単位は、決まった一覧から選ぶ。
自由な文字列にすると、「大さじ」と「大匙」のような表記のゆれで、換算率が引けなくなるためである。

| 単位 | 種類 | 表記の位置 | 例 |
|---|---|---|---|
| `g` | 重さ | 数の後ろ | 250g |
| `ml` | かさ | 数の後ろ | 150ml |
| `大さじ` | かさ(15ml) | 数の前 | 大さじ2 |
| `小さじ` | かさ(5ml) | 数の前 | 小さじ1/2 |
| `カップ` | かさ(200ml) | 数の前 | カップ1/2 |
| `個` | 数 | 数の後ろ | 4個 |
| `本` | 数 | 数の後ろ | 1/2本 |
| `枚` | 数 | 数の後ろ | 2枚 |
| `かけ` | 数 | 数の後ろ | 1かけ |
| `束` | 数 | 数の後ろ | 1/2束 |
| `玉` | 数 | 数の後ろ | 2玉 |
| `株` | 数 | 数の後ろ | 1/2株 |
| `パック` | 数 | 数の後ろ | 1パック |
| `切れ` | 数 | 数の後ろ | 2切れ |
| `袋` | 数 | 数の後ろ | 1/2袋 |

一覧は、今の 38 品が使っている 15 種類である。
単位を足すときは、スキーマの一覧と、この表を同じ PR で直す。
かさの単位の括弧の中の ml は、食材マスタに換算率を書くときの目安である。
画面は、かさの単位どうしを計算で変換しない(5.5)。

#### 分量の表記

分量は、表示のときに読みやすい数に丸める(要件定義 4.2)。
丸め方は 3 通りあり、単位と食材マスタから決める。

| 丸め方 | 内容 | 当てはまる単位 |
|---|---|---|
| 5 刻み | 5 の倍数に丸める。5 を下回らない | `g`、`ml` |
| 分数 | 1/2、1/3、1/4 刻みの分数で表す。例: 「1と1/2」 | `大さじ`、`小さじ`、`カップ`。数の単位のうち、下の「整数」に当たらないもの |
| 整数 | 整数に丸める。1 を下回らない | 数の単位のうち、その食材の `wholeUnits`(5.5)に入っているもの |

数の単位を「分数」と「整数」に分けるのは、食材によって、分けて使えるかどうかが違うためである。
玉ねぎは 1/2 個で使えるが、卵は 1/2 個では使いにくい。

- 例: 玉ねぎ `0.5` 個(2 人分)を 3 人分にすると、0.75 個なので「3/4個」と表示する。
- 例: 卵 `4` 個(2 人分)を 3 人分にすると、6 個なので「6個」、1 人分にすると「2個」と表示する。卵 `1` 個(2 人分)を 3 人分にすると、1.5 個を丸めて「2個」と表示する。
- 例: 食材マスタにない材料の数の単位は、「分数」で表す。

丸め方をレシピの材料に持たせないのは、利用者が材料を足したり単位を変えたりしたときに、丸め方を選ばせずに済むようにするためである。
決めた理由と却下した案は、[決定の記録 0027](../decisions/0027-rounding-from-unit.md) に書いた。

分数に直す計算の細部(どの分母を選ぶか、端数をどこで切り上げるか)は、レシピ詳細の仕様書に書く。
今の実装は `recipes/assets/recipe.js` の `QuantityFormatter` にあり、分母は 2、3、4 から近いものを選んでいる。

丸めるのは表示だけである。
栄養計算には、丸める前の値を使う。

### 5.4 材料、手順、コツの識別子

元のレシピの、材料のグループ、材料、手順、コツには、レシピの中で変わらない識別子(`id`)を付ける。
編集内容が、元のレシピのどの行を直したのかを指せるようにするためである。

並び順の番号(「3 番目の材料」)で指すと、元のレシピに材料が 1 つ足されただけで、編集内容の指す先がずれる。
例: 編集内容が「3 番目の材料を 300g にする」と持っているときに、元のレシピの 2 番目に材料が足されると、別の材料が 300g になる。

決まりは次のとおりとする。

| 対象 | 形 | 例 |
|---|---|---|
| 材料のグループ | `g` と数 | `g1`、`g2` |
| 材料 | `i` と数 | `i1`、`i10` |
| 手順 | `s` と数 | `s1`、`s6` |
| コツ | `t` と数 | `t1`、`t4` |

- 数は 1 から 999 までで、先頭に 0 を付けない。
- 新しく作るレシピでは、上から順に 1 から振る。材料の数は、グループをまたいで通しで振る。
- 一度付けた `id` は変えない。並べ替えても、ほかのグループへ移しても、同じ `id` のままにする。
- 行を消したら、その `id` は欠番にし、使い回さない。
- 行を足すときは、そのレシピの同じ種類で、これまでに使った一番大きい数に 1 を足す。
- `id` は、そのレシピの中だけで意味を持つ。別のレシピの `i1` とは関係がない。
- `u` で始まる `id` を、元のレシピでは使わない。利用者が編集で足した行に、画面が付ける識別子のために空けておく。

例: 親子丼の材料 `i4`(三つ葉)を消して、青ねぎを足すときは、青ねぎを `i11` にする。`i4` にはしない。
`i4` を使い回すと、「`i4` を消す」と持っている編集内容が、青ねぎを消してしまう。

「これまでに使った一番大きい数」は、消した行の分も含む。
今のファイルに残っている数だけでは分からないときは、`git log -p data/recipes/<slug>.json` で過去の版を確かめる。
`check:data` は、ファイルの中の重複と形だけを確かめ、過去の版との使い回しは確かめない(8 章の未決事項)。

編集内容は、元のレシピの行を `id` で指す。
`slug` と食材マスタの識別子に加えて、この `id` も、データベースの JSON の中に入る「リポジトリのファイルを指す識別子」である(`common-database.md` の 5.5 の例外に当たる)。
編集内容を、行ごとの差分で持つか、直した後の全体で持つかは、Issue #12 で決める。
どちらの持ち方でも、同じ `id` で元の行と対応が取れる。

決めた理由と却下した案は、[決定の記録 0025](../decisions/0025-stable-item-ids.md) に書いた。

#### 編集内容の大きさとの関係

編集内容の要求は 256KB までである(`common-api.md` の 4.7)。
元のレシピの上限(5.7 の 32KB)と、各項目の文字数の上限は、編集内容が元のレシピの全体を持つ形になっても 256KB に収まるように決めた。
材料 50 件、手順 20 件、コツ 10 件を、すべて上限の文字数で埋めると、1 文字を UTF-8 で 3 バイトとして 40KB 前後になる見込みである。
編集内容の文字数の上限は、Issue #12 で、この節の上限と同じ値にする。

`data/ingredients.json` に、人が選ぶ粒度で食材を持つ。
成分表は調理の形ごとに食品が分かれていて、人が選ぶには細かすぎるためである(要件定義 7.2)。

#### ファイルの形

```json

      "id": "shoyu",
```

醤油の換算率は、成分表の備考にある「100 mL: 118.1 g」から計算した値である。
卵の 50g は、形を示すための例の値で、根拠を確かめていない。
移行のときに、根拠を確かめて `note` に書く。

#### 項目

| 項目 | 型 | 必須 | 制約 | 内容 |
|---|---|---|---|---|
| `id` | 文字列 | ○ | 英小文字、数字、ハイフン。先頭と末尾はハイフンにしない。64 文字まで。ファイルの中で重複しない | 食材の識別子 |
| `name` | 文字列 | ○ | 1〜30 文字。ファイルの中で重複しない | 名称。編集の画面で、食材を選ぶ一覧に出す |
| `aliases` | 文字列の配列 | ○ | 0〜10 件。1 件は 1〜30 文字 | 別名。食材を選ぶときの検索と、レシピの検索に使う |
| `category` | 文字列 | ○ | 野菜、肉、魚介、卵と乳製品、穀類、調味料、その他 のいずれか | 食材を選ぶ一覧での分類 |
| `foodNumber` | 文字列 | | 数字 5 桁。`data/foods.json` にある番号 | 代表となる成分表の食品番号 |
| `noNutrition` | 真偽値 | | `true` だけ。`foodNumber` と同時に書けない | 栄養の値がすべて 0 の食材に付ける印。今は水だけである |
| `gramsPerUnit` | オブジェクト | | キーは 5.3 の単位のうち `g` 以外。値は 0 より大きく 5000 以下の数 | 単位 1 つ分の g(可食部) |
| `wholeUnits` | 文字列の配列 | | 数の単位だけ。`gramsPerUnit` にあるかどうかは問わない | 表示のときに整数に丸める単位(5.3) |
| `note` | 文字列 | | 1〜200 文字 | 換算率や食品番号を選んだ根拠。画面には出さない |

食材は、`id` の順(文字コードの順)に並べる。
足す場所を一つに決めて、2 つの PR が同じ行を触る衝突を減らすためである。

#### 識別子の付け方

- 日本語の名前をローマ字(ヘボン式)にし、語の区切りをハイフンにする。例: 玉ねぎは `tamanegi`、鶏もも肉は `tori-momo`、醤油は `shoyu`
- 外来語は、もとの言葉の綴りにする。例: ベーコンは `bacon`、マヨネーズは `mayonnaise`
- 長音は、母音を重ねず、記号も付けない。例: 砂糖は `sato`、ごぼうは `gobo`
- 同じ綴りになるときは、後から足すほうに、種類を表す語を足す。例: 塩鮭を `sake` にした後で酒を足すなら `sake-nihonshu`
- 商品名ではなく、一般の名前で付ける。商品名は `aliases` に入れる。例: 「ほんだし」は、`id` を `wafu-dashi-karyu`、`name` を「顆粒和風だし」にして、`aliases` に入れる

一度付けた `id` は変えず、消さない。
編集内容が、データベースの中で `id` を持っているためである。
`name` と `aliases` は、後から直してよい。

食材が要らなくなっても、`id` を消さずに残す。
どうしても消すときは、その `id` を持つ編集内容の材料が、栄養計算から除かれて「概算値」になる(要件定義 4.3)。
表示は、材料が自分で持っている `name` で保たれる。

#### 食品番号の選び方

1 つの食材は、成分表の食品を 1 件だけ指す。

- 調理する前の形(「生」)を選ぶ。レシピの分量は、調理する前の重さで書くためである。例: 鶏もも肉は「にわとり 若どり もも 皮つき 生」(`11221`)
- 部位や種類が分かれているときは、家庭でいちばん使う形を選ぶ。例: 醤油は「こいくちしょうゆ」(`17007`)、砂糖は「車糖 上白糖」(`03003`)
- 炊いたご飯やゆで麺のように、調理した後の形で量る食材は、その形を選ぶ。例: ご飯は「こめ 水稲めし 精白米 うるち米」(`01088`)
- 当てはまる食品がないときは、`foodNumber` を書かない。その食材は栄養計算から除かれる

上の例の食品番号と食品名は、取得した成分表のファイルで確かめた。

`foodNumber` も `noNutrition` もない食材は、栄養計算から除く。
`noNutrition` が `true` の食材は、除かずに、すべての値を 0 として計算に入れる。
水は成分表に食品として載っていないので、この印がないと、水を使うレシピがすべて「概算値」になる。
決めた理由は、[決定の記録 0029](../decisions/0029-no-nutrition-flag.md) に書いた。

ご飯(今日の献立で足す「茶碗 1 杯 150g」)も、食材マスタの 1 件(`gohan`)として持つ。
成分表の値(100g あたり 156kcal)から 150g 分を計算すると 234kcal で、今の静的レシピ集が持っている値と一致する。

#### 単位から g への換算率

換算率は、食材ごと、単位ごとに、`gramsPerUnit` に書いて持つ。
同じ「大さじ 1」でも、食材によって重さが違うためである。
例: 成分表の備考から計算すると、醤油の大さじ 1 は 17.7g、砂糖(上白糖)の大さじ 1 は 9.8g である。

決まりは次のとおりとする。

- `g` は書かない。いつも 1 である。
- 書いていない単位は、換算できないものとして扱う。その単位で書かれた材料は、栄養計算から除かれる(要件定義 4.3)。
- 画面は、単位どうしを計算で変換しない。「大さじ」だけが書いてある食材を「小さじ」で使っても、3 で割って求めることはしない。計算の決まりを「書いてあれば使う、なければ除く」の 1 つにするためである。
- そのため、かさで量る食材(調味料、粉、油、液体)には、`小さじ`、`大さじ`、`カップ`、`ml` の 4 つをそろえて書く。
- 値は、可食部の重さで書く。成分表の値が、可食部 100g あたりだからである。例: 卵 1 個は、殻を除いた重さを書く。
- 数の単位の値は、大きさに幅があるので、中くらいの大きさの見込みを書き、根拠を `note` に書く。

かさの換算率の求め方は、次の順とする。

1. 成分表の備考に「100 mL: ○ g」があれば、それを使う。醤油、みりん、砂糖、油、顆粒和風だしの備考に、この記載があることを確かめた。
2. なければ、計量スプーンの重量表など、出どころの分かる資料の値を使い、`note` に出どころを書く。
3. 分からなければ書かない。見当で書かない。

例: 醤油は「100 mL: 118.1 g」なので、`ml` は 1.18、`小さじ` は 5ml 分で 6、`大さじ` は 15ml 分で 18、`カップ` は 200ml 分で 236 とする。

レシピの分量を g で書いたときは、その値を可食部の重さとして扱う。
「じゃがいも 300g」が皮付きの重さだとしても、皮の分を引かない。
引くための情報(廃棄率)を持たないことにしたためで、その分だけ値は多めに出る。

決めた理由と却下した案は、[決定の記録 0026](../decisions/0026-grams-per-unit-explicit.md) に書いた。

| 食品の件数 | 2,538 件。食品番号に重複はない |
| 行の構成 | 12 行目が成分の識別子、13 行目からがデータ |
| 列の構成 | 1 列目が食品群、2 列目が食品番号、3 列目が索引番号、4 列目が食品名、5 列目が廃棄率 |
| セルの型 | 食品番号も成分の値も、文字列で入っている。食品番号は先頭の 0 を含む 5 桁である(例: `01088`) |

ファイルの URL には日付が入っているので、正誤表が出ると変わる見込みである。
取得するときは、URL を決め打ちにせず、配っているページから「第2章(データ)」のリンクをたどる。

#### 使う列

使う成分は 5 項目である(要件定義 4.3)。
列は、位置ではなく、12 行目の成分の識別子で探す。
列が足されて位置がずれても、誤った列を読まないようにするためである。

| 持つ項目 | 成分の識別子 | 成分表での名前 | 単位 |
|---|---|---|---|
| `kcal` | `ENERC_KCAL` | エネルギー | kcal |
| `protein` | `PROT-` | たんぱく質 | g |
| `fat` | `FAT-` | 脂質 | g |
| `carb` | `CHOCDF-` | 炭水化物 | g |
| `salt` | `NACL_EQ` | 食塩相当量 | g |

成分表には、たんぱく質に「アミノ酸組成によるたんぱく質」(`PROTCAA`)、脂質に「脂肪酸のトリアシルグリセロール当量」(`FATNLEA`)、炭水化物に「利用可能炭水化物」の列もある。
これらを使わず、上の 3 列を使う。
上の 3 列は、値のない(`-` の)食品が、列ごとに 2,538 件のうち 1 件以下だからである。
そのため、たんぱく質、脂質、炭水化物から計算したエネルギーは、成分表のエネルギーと一致しない。

#### 記号の読み方

成分表のセルには、数のほかに記号が入っている。
使う 5 列に出てくる書き方と、その読み方は次のとおりとする。
件数は、取得したファイルで数えた。

| セルの書き方 | 意味 | 読み方 | 5 列での件数 |
|---|---|---|---|
| `190`、`16.6`、`0` | 値 | その数 | 11,480 |
| `(11.3)` | 推計した値 | 括弧を外した数 | 979 |
| `(0)` | 含まれないと推定される | `0` | 49 |
| `Tr` | 微量 | `0` | 173 |
| `(Tr)` | 微量と推定される | `0` | 6 |
| `-` | 測っていない | `null` | 3 |

エネルギー(`ENERC_KCAL`)は、2,538 件すべてが数である。
`-` は、たんぱく質、脂質、食塩相当量に 1 件ずつある。

`Tr` と `-` の意味は、要件定義 7.2 の記述による。
括弧の付いた書き方の意味は、成分表の第 1 章(説明)で確かめていない(8 章の未決事項)。

`Tr` を `0` として読むのは、微量の成分は合計に影響しないためである。
`null` として読むと、その食材を「値が分からない」として計算から除くことになり、本みりん(脂質が `Tr`)を使うレシピがすべて「概算値」になる。
これは、要件定義 7.2 の「`Tr` は `null`」を変える決定である。
決めた理由は、[決定の記録 0028](../decisions/0028-trace-as-zero.md) に書いた。

上の表にない書き方のセルがあったときは、変換スクリプトは失敗して、食品番号と列とセルの中身を出す。
知らない書き方を黙って `0` や `null` にしないためである。

#### 変換した後の形

変換スクリプトは、Excel から `data/foods.json` を作る。
`data/foods.json` はリポジトリにコミットし、変換元の Excel はコミットしない(要件定義 7.2)。

```json
{
  "schemaVersion": 1,
  "source": {
    "title": "日本食品標準成分表(八訂)増補2023年",
    "publisher": "文部科学省",
    "pageUrl": "https://www.mext.go.jp/a_menu/syokuhinseibun/mext_00001.html",
    "fileUrl": "https://www.mext.go.jp/content/20260327-mxt_kagsei-mext-000029402_02.xlsx",
    "updatedOn": "2026-03-27",
    "sha256": "0d5a77077dd6cd91cbc2e6e317b8b218a38728c409eed452f1c10635a0d3099c"
  },
  "foods": [
    { "foodNumber": "01088", "name": "こめ [水稲めし] 精白米 うるち米", "kcal": 156, "protein": 2.5, "fat": 0.3, "carb": 37.1, "salt": 0 },
    { "foodNumber": "11221", "name": "<鳥肉類> にわとり [若どり・主品目] もも 皮つき 生", "kcal": 190, "protein": 16.6, "fat": 14.2, "carb": 0, "salt": 0.2 },
    { "foodNumber": "16025", "name": "<アルコール飲料類> (混成酒類) みりん 本みりん", "kcal": 241, "protein": 0.3, "fat": 0, "carb": 43.2, "salt": 0 }
  ]
}
```

| 項目 | 型 | 制約 | 内容 |
|---|---|---|---|
| `source.updatedOn` | 文字列 | `"YYYY-MM-DD"` | ファイルの中の更新日。暦の上の一日なので、時刻を付けない |
| `source.sha256` | 文字列 | 16 進数 64 桁 | 変換元のファイルの SHA-256。どのファイルから作ったかを後から確かめるために持つ |
| `foods[].foodNumber` | 文字列 | 数字 5 桁。重複しない | 食品番号。先頭の 0 が落ちないように、数値でなく文字列で持つ |
| `foods[].name` | 文字列 | 1〜100 文字 | 成分表の食品名。全角の空白と括弧は、半角に直す |
| `foods[].kcal` | 数値 | 0 以上 | エネルギー。可食部 100g あたりの kcal |
| `foods[].protein`、`fat`、`carb`、`salt` | 数値か `null` | 0 以上 | 可食部 100g あたりの g。測っていない成分は `null` |

- 成分表の全件(2,538 件)を入れる。食材マスタが指していない食品も入れておくと、食材を足すたびに変換をやり直さずに済む。
- 食品は、食品番号の順に並べ、1 件を 1 行に書く。成分表を更新したときに、Git の差分で変わった食品だけが見えるようにするためである。
- 値が `null` の項目だけは、5.1 の「値がない項目は書かない」の例外として、`null` と書く。「測っていない」ことを、項目の書き忘れと区別するためである。
- 大きさは、300KB 前後の見込みである。全件の 5 項目を、項目名を短くした形で書き出して測った値が 296KB だった。

食材が指す食品の成分に `null` があるときは、その成分について、その材料を計算から除き、「概算値」として扱う。
例: 脂質が `null` の食品を指す食材は、エネルギー、たんぱく質、炭水化物、食塩相当量には入り、脂質の合計からだけ除かれる。
計算の細部は、栄養計算の仕様書に書く。

#### 変換の手順

変換スクリプトは `scripts/` に置き、Docker のコンテナの中で動かす(要件定義 6 章のディレクトリ構成)。

1. 配っているページから「第2章(データ)」の Excel を取得し、リポジトリの外か、Git が無視するディレクトリに置く。
2. 変換スクリプトに、Excel のパスを渡して実行する。
3. スクリプトは、シート「表全体」を開き、12 行目から 5 つの成分の識別子の列を探す。1 つでも見つからなければ失敗する。
4. 13 行目から下の、食品番号が数字 5 桁の行を読む。
5. セルを「記号の読み方」の表に従って読む。表にない書き方があれば失敗する。
6. 食品番号の重複があれば失敗する。
7. `data/foods.json` を書き出す。`source.sha256` には、読んだ Excel の SHA-256 を入れる。
8. `npm run check:data` を走らせ、食材マスタの `foodNumber` がすべて残っていることを確かめる。

同じ Excel から 2 回変換すると、同じ内容の `data/foods.json` ができるようにする。
実行した日時のような、毎回変わる値を入れない。
変えていないのに差分が出ると、変わった食品を見落とすためである。

成分表が更新されたときは、同じ手順でやり直す。
PR の本文に、値が変わった食品のうち、食材マスタが指しているものを挙げる。

#### 利用の条件

文部科学省のウェブサイトの利用規約(<https://www.mext.go.jp/b_menu/1351168.htm>)を、2026-10-11 に読んで確かめた。

- コンテンツは、出典を記載すれば、複製、公衆送信、翻案を含めて自由に利用できる。
- 編集や加工をして利用するときは、出典とは別に、編集や加工をしたことを記載する。
- 編集や加工をした情報を、国が作成したかのように公表してはならない。
- この規約は、クリエイティブ・コモンズ・ライセンスの表示 4.0 国際(CC BY 4.0)と互換性がある。
- 数値データ、簡単な表、グラフは著作権の対象でないので、この規約は適用されない、とも書かれている。

このアプリは、成分表から 5 項目を抜き出し、レシピの分量に掛けて合計した値を表示する。
これは加工に当たるので、出典に加えて、アプリが計算した値であることを画面に書く(3 章の出典表記)。
要件定義 7.2 の「日本食品標準成分表(八訂)増補2023年から引用」は、成分表の値をそのまま載せているように読めるので、3 章の文に置き換える。

`data/foods.json` をリポジトリにコミットして公開することも、複製と公衆送信に当たる。
`source` の項目が、出典の記載になる。

### 5.7 ブラウザへ渡すデータ

元のレシピ、食材マスタ、成分表は、画面のビルドのときに読み、ページへ組み込む。
ブラウザは、ビルドのときに作られた形を受け取る。
ビルドのどの仕組みで読み、どのページにどう分けて載せるかは、画面の共通設計(Issue #6)に書く。
ここでは、ブラウザへ渡す形と、大きさの上限を決める。

渡す形は 4 つである。
どれも、`data/` のファイルから計算で作れるもので、リポジトリにコミットしない。

| 形 | 使う画面 | 中身 | 大きさ |
|---|---|---|---|
| レシピの全体 | レシピ詳細、レシピの編集 | `data/recipes/<slug>.json` の全項目。1 品分 | 親子丼で 4.3KB(測った値)。上限は 32KB |
| レシピの要約の一覧 | レシピ一覧 | 全レシピの `slug`、`version`、`name`、`arrangeLabel`、`genres`、`time`、ヒーローの写真の `file` と `alt`、検索用の文字列 | 38 品で 15KB 前後の見込み |
| レシピの材料の一覧 | 今日の献立 | 全レシピの `slug`、`version`、`name`、`servings`、ヒーローの写真の `file`、材料(`id`、`ingredientId`、`name`、`amount`、`unit`、`note`、`intakeRatio`) | 38 品で 50KB 前後の見込み |
| 栄養計算のデータ | レシピ詳細、レシピの編集、今日の献立 | 食材マスタの全件(`note` を除く)と、食材マスタが指している食品だけ | 食材 150 件で 40KB 前後の見込み |

見込みの大きさは、空白を詰めた JSON の、圧縮する前のバイト数である。
38 品の移行が終わったら、実際の値を測って、この表を直す。

決まりは次のとおりとする。

- **成分表は、食材マスタが指している食品だけを渡す。** 全件(2,538 件、300KB 前後)を配ると、読み込みが重くなるためである(要件定義 7.2)。例: 食材マスタが 150 件なら、渡す食品は多くても 150 件である。
- **食材マスタは、全件を渡す。** 編集の画面で、どのレシピにも使われていない食材も選べるようにするためである。
- **食材マスタの `note` は渡さない。** 根拠の覚え書きで、画面に出さないためである。
- **検索用の文字列は、ビルドのときに作る。** 料理名、読み、ジャンル、材料の `name`、その材料が指す食材の `name` と `aliases` をつなげる。表記のゆれをそろえる処理(カタカナとひらがな、全角と半角、大文字と小文字)は、検索の仕様書に書く。
- **栄養の値を、ビルドのときに計算して渡さない。** 計算はブラウザだけで行う(要件定義 4.3)。ビルドのときに計算した値を渡すと、編集内容を重ねた後の値と、計算する場所が 2 つになる。
- **元のレシピの JSON は 1 品 32KB までとする。** `check:data` で確かめる。今の 38 品は、HTML でも 1 品 11KB 以下である。

ブラウザへ渡す形を作る処理は、1 か所にまとめる。
要約と材料の一覧を別々の場所で作ると、片方だけ項目を足し忘れるためである。

### 5.8 静的レシピ集の 38 品を移す手順

移す元は、`recipes/` の 38 品の HTML、`recipes/assets/catalog.js` の目録、`recipes/images/` の写真 102 枚である。
移行は、段階 1(スキーマと移行、一覧、詳細)と段階 2(成分表と栄養計算)で行う(要件定義 11 章)。

#### 今の項目と、移す先

| 今の場所 | 移す先 |
|---|---|
| ファイル名(`oyakodon.html`) | `slug` |
| `h1.hero__title` の本文 | `name` |
| `.hero__ruby` | `romanName` |
| `.hero__kicker` | 移さない。`genres` の 2 件目と同じ値である |
| `.hero__lead`。`<br>` は改行 | `lead`。`<br>` を `\n` にする |
| `meta[name=description]` | `description` |
| 基本情報の「調理時間」 | `time` |
| 基本情報の「難易度」。星の数 | `level` |
| 基本情報の「カロリー目安」 | 移さない。成分表から計算し直す |
| 基本情報の「道具」 | `tool` |
| `data-base-servings` | `servings`。38 品とも 2 である |
| `data-min-servings`、`data-max-servings` | 移さない。1〜6 人は、要件定義 4.2 が決めている |
| `.ing-group__title` | `ingredientGroups[].name` |

| `data-amount` | `amount` |

| `.gallery figure` の `img` と `figcaption` | `photos[]` の `role` が `gallery` のもの。`figcaption` は `caption` |
| フッターの写真の出典 | `photos[].credit` |
| フッターのカロリーの注記(「ご飯は含みません」など) | 移さない。栄養の値は材料から計算する |
| 目録の `reading`、`genres` | `reading`、`genres` |
| 目録の `kicker`、`ingredients`、`nutrition` | 移さない。5.2 の「持たない項目」のとおり |
| 目録の `title`、`arrange` | 38 品にアレンジ版はないので、移すものがない |

今の 38 品を調べた結果は次のとおりである。

- 材料の行は 436 行で、表示する名前は 132 通りある。
- 数値で表せない分量は 58 行で、「少々」が 27、「適量」が 15、「好みで」が 12、「ひとつまみ」が 4 である。
- 単位は 15 種類で、5.3 の一覧と一致する。
- 手順は 206 あり、目安時間の書き方は 25 通りで、目安時間のない手順が 44 ある。
- 難易度は、星 1 つが 21 品、2 つが 14 品、3 つが 3 品である。
- 写真は 102 枚で、すべて JPEG である。ヒーローが 38 枚、ギャラリーが 64 枚で、ギャラリーのないレシピが 1 品ある。

#### 手順

1. **成分表を変換する。** 5.6 の手順で `data/foods.json` を作る。
2. **HTML から下書きを作る。** 上の表に従って、38 品の HTML と目録から JSON の下書きを作る。使い捨てのスクリプトで行い、スクリプトはコミットしない。`id` は 5.4 の決まりで上から順に振り、`version` は 1 にする。
3. **食材マスタを作る。** 132 通りの名前から、括弧書きを除いて同じ食材をまとめ、`data/ingredients.json` を作る。食品番号と換算率は、5.5 の決まりで付ける。
4. **丸め方を移す。** 今の `data-style` が `int` の材料について、同じ食材のすべての行が `int` なら、その単位を食材マスタの `wholeUnits` に入れる。同じ食材で `int` と `frac` が混ざっているもの(今は、玉ねぎとじゃがいもの「個」)は、入れない。
5. **材料に `ingredientId` を付ける。** 「塩とこしょう」のように 2 つの食材をまとめた行は、数値で表せる分量なら 2 行に分け、「少々」のような分量なら `ingredientId` を付けずに残す。
6. **写真を移す。** `recipes/images/<slug>/` を `frontend/public/photos/<slug>/` へ移す。ファイル名は変えない。
7. **写真の出典を確かめる。** 写真ごとに、Wikimedia Commons の API で作者とライセンスを取り直し、フッターの記載と照らす。今のフッターは、どの出典がどのファイルのものかを書いていないので、Commons の画像と見比べて対応を確かめる。確かめられない写真は、差し替える。
8. **検証する。** `npm run check:data` が、エラーなしで通るようにする。警告(換算率のない単位)は、一覧を見て、換算率を足すか、そのままにするかを決める。
9. **カロリーを比べる。** 段階 2 で栄養計算ができたら、38 品の 1 人分のエネルギーを、目録の `nutrition.kcal` と比べる。差が 20% を超えるレシピは、材料の `ingredientId`、食品番号、換算率、`intakeRatio` を見直す。見直しても差が残るときは、理由を PR の本文に書く。
10. **表示を確かめる。** 38 品を新しい画面で開き、今のページと並べて、材料、手順、コツ、写真、出典に抜けがないことを確かめる。
11. **`recipes/` を消す。** 手順 10 が終わってから、`recipes/` を削除する。`recipe` スキルを 5.10 のとおりに直す PR と、同じ PR か、その前の PR で行う。

手順 9 の 20% は、見直すかどうかを決めるための目安で、合否の基準ではない。
今の値は、材料から手で概算した値であり、正しいとは限らないためである。

### 5.9 写真

#### 置き場

写真は `frontend/public/photos/<slug>/<ファイル名>` に置く。
画面の公開ディレクトリに置くと、ビルドのときにそのまま配る対象になるためである(要件定義 11 章)。

- ディレクトリの名前は、レシピの `slug` と同じにする。
- ファイル名は、役割や写っているものを表す英小文字と数字とハイフンにし、拡張子を `.jpg` にする。例: `hero.jpg`、`closeup.jpg`、`teishoku.jpg`
- ヒーローの写真は、必ず `hero.jpg` にする。一覧のカードが、`slug` だけから写真の場所を決められるようにするためである。
- アレンジ版は、元のレシピの写真を使うときも、自分の `slug` のディレクトリに写しを置く。写真の持ち主を 1 つのレシピに決めて、元のレシピを消したときに写真が切れないようにするためである。

#### 形式と大きさ

| 項目 | 決まり |
|---|---|
| 形式 | JPEG |
| 長辺 | 1280px。Wikimedia Commons の 1280px の縮小版を使う |
| 1 枚の大きさ | 1MB まで |
| 1 品の枚数 | 1〜6 枚。ヒーローが 1 枚、ギャラリーが 0〜5 枚 |

今の 102 枚は、いちばん小さいものが 111KB、中央が 244KB、いちばん大きいものが 801KB で、合計は 26MB である。
1MB の上限は、今の写真がすべて収まる値として決めた。

一覧のカードに、1280px の写真をそのまま使うと、38 枚で 9MB 前後を読み込むことになる。
一覧用の小さい写真を作るかどうかと、作る場所は、画面の共通設計(Issue #6)で決める(8 章の未決事項)。
作るときも、元になる写真は、この節の 1280px の 1 枚とする。

#### 項目

| 項目 | 型 | 必須 | 制約 | 内容 |
|---|---|---|---|---|
| `file` | 文字列 | ○ | 英小文字、数字、ハイフンと、拡張子 `.jpg`。40 文字まで。レシピの中で重複しない | ファイル名。ディレクトリを含めない |
| `role` | 文字列 | ○ | `hero` か `gallery` | 役割。`hero` は 1 件だけで、`file` は `hero.jpg` |
| `alt` | 文字列 | ○ | 1〜100 文字 | 代替の説明。写っているものを書く。料理名だけにしない |
| `caption` | 文字列 | | 1〜60 文字。`role` が `gallery` のときだけ書ける | 写真の下に出す説明文 |
| `credit.title` | 文字列 | ○ | 1〜120 文字 | 出典での題名。例: 「Oyakodon 003」 |
| `credit.url` | 文字列 | ○ | `https://` で始まる URL。300 文字まで | 出典のページ。画像のファイルそのものではなく、作者とライセンスが書いてあるページを指す |
| `credit.author` | 文字列 | ○ | 1〜100 文字 | 作者 |
| `credit.license` | 文字列 | ○ | `CC0`、`Public domain`、`CC BY`、`CC BY-SA` のいずれか | ライセンスの種類 |
| `credit.licenseVersion` | 文字列 | | 1〜10 文字。`license` が `CC BY` か `CC BY-SA` のときは必須 | ライセンスの版。例: `4.0`、`2.0` |
| `credit.site` | 文字列 | ○ | 1〜40 文字 | 取ってきた場所。例: 「Wikimedia Commons」 |

`photos` の並び順が、画面での並び順である。
ヒーローを先頭に置く。

出典を、レシピの 1 か所にまとめず、写真ごとに持つのは、写真を 1 枚差し替えたときに、出典の直し忘れが起きないようにするためである。
今のページは、フッターに 3 枚分をまとめて書いていて、どの出典がどの写真のものかが分からない。

ライセンスの種類と版を分けて持つのは、検証で「使ってよい種類か」を確かめるためである。
「CC BY-SA 4.0」のような 1 つの文字列にすると、版の数だけ値が増え、一覧で確かめられない。
CC BY と CC BY-SA は、利用の条件として、ライセンスの名前と版を示すことを求めているので、版を必須にする。

画面は、写真の出典を、題名(出典のページへのリンク)、作者、ライセンス、取ってきた場所の順で表示する。
例: 「Oyakodon 003(Ocdp 撮影、CC0、Wikimedia Commons)」

### 5.10 `recipe` スキルを直す点

`.claude/skills/recipe/SKILL.md` を、HTML ではなく、この文書の形のデータを出すように直す(要件定義 11 章)。
直すのは、38 品の移行が終わり、`recipes/` を消す PR と同じときである。
それまでは、今のスキルのままにする。

| 今 | 直した後 |
|---|---|
| `recipes/<名前>.html` を書く | `data/recipes/<slug>.json` を書く。形はこの文書の 5.2 |
| 見本は `recipes/oyakodon.html` | 見本は `data/recipes/oyakodon.json` |
| 目録 `recipes/assets/catalog.js` に 1 件足す | やめる。一覧はビルドのときに作る |
| 分量を `data-amount`、`data-style`、`data-unit`、`data-prefix` で書く | `amount` と `unit` で書く。単位は 5.3 の一覧から選ぶ。丸め方は書かない |
| カロリーと栄養の値を概算して書く | 書かない。画面が成分表から計算する |
| 材料は名前だけを書く | 食材マスタを引いて `ingredientId` を付ける。ない食材は、食材マスタに足す |
| 写真を `recipes/images/<語幹>/` に保存する | `frontend/public/photos/<slug>/` に保存する。ヒーローは `hero.jpg` にする |
| 写真の出典をフッターにまとめて書く | 写真ごとに `credit` を書く。ライセンスは種類と版に分ける |
| アレンジ版に、バッジ、変更点の枠、`<title>` を書く | `arrangeLabel`、`arrangeChanges`、`arrangeOf` を書く |
| `QuantityFormatter` に style を足して拡張する | やめる。表記を足したいときは、利用者に相談する |
| 確認は、画像とアセットのパスが存在すること | `npm run check:data` が、エラーなしで通ること |

足す手順は次のとおりとする。

- **食材マスタを引く。** 材料ごとに、`data/ingredients.json` の `name` と `aliases` を探す。あれば、その `id` を `ingredientId` に書く。
- **食材を足す。** なければ、5.5 の決まりで食材を足す。食品番号は `data/foods.json` を食品名で探して選び、選んだ理由を `note` に書く。当てはまる食品がなければ、`foodNumber` を書かない。
- **換算率を足す。** レシピで使った単位が、その食材の `gramsPerUnit` になければ、5.5 の決まりで足す。根拠が分からなければ足さず、報告に書く。
- **全量を食べない材料に `intakeRatio` を付ける。** 5.2 の基準に従う。
- **既にあるレシピを直すときは、`version` を 1 増やす。** `id` は 5.4 の決まりを守り、消した行の `id` を使い回さない。
- **報告に書く。** 作ったファイル、写真の出典とライセンス、足した食材と換算率、`check:data` の警告、アレンジの有無と内容を書く。画面で表示を確かめていなければ、そう書く。

スキルの説明(`description`)と、「アプリ本体とは無関係の静的ページである」という記述も、合わせて直す。

### 5.11 データの検証(`check:data`)

元のレシピと食材マスタは Claude Code が書くので、誤りを仕組みで止める(要件定義 9 章)。
`npm run check:data` は、`frontend/` の npm のスクリプトとして置き、`frontend/src/schema/` のスキーマを使う。
画面のビルドと同じスキーマで検証して、「検証は通ったが、ビルドでは落ちる」を防ぐためである。

結果は 2 種類ある。

- **エラー**: 1 件でもあれば、コマンドは 0 以外の終了コードで終わる。CI は失敗する。
- **警告**: 一覧に出すが、コマンドは 0 で終わる。

エラーと警告は、どのファイルの、どの項目の、何が悪いかを 1 行ずつ出す。
例: `data/recipes/oyakodon.json: ingredientGroups[1].ingredients[2].ingredientId "shoyuu" は食材マスタにない(CD-11)`

最初のエラーで止めず、すべてのファイルを検証してから、まとめて出す。
1 件直すたびに走らせ直す手間を減らすためである。

## 6. サービスの間のやり取り

なし。
元のレシピ、食材マスタ、成分表は、どのサービスも読まない。
`kitchen-service` は、編集内容の中の `slug`、`ingredientId`、材料や手順の `id` を、形だけ確かめて保存する。
それらが指す先がリポジトリのファイルにあるかどうかは、確かめない。
サービスにデータのファイルを持たせると、画面とサービスで、別の版のデータを見ることが起きるためである。
指す先がなくなったときの表示は、ブラウザが決める(5.5 の「識別子の付け方」)。
