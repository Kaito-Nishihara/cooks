# 共通設計: 実行環境(kind、入口、Compose)

対応する Issue: #5

## 1. 目的

手元の Kubernetes に一式を載せる方法と、書いている間の動かし方を決める。
要件定義の未決事項のうち、「入口の実装」と「クラスタへ載せる道具」を決める。

入口の実装は、候補を kind の上で実際に動かして比べた。
この文書のうち、動かして確かめたことには「確かめた」と書き、確かめていないことには「見込み」と書く。

## 2. 範囲

やること:

- 手元で使う道具と、その入れ方
- kind のクラスタの構成と名前空間
- 入口の実装と、振り分け、ログインの確認、`/internal` を外から届かなくする方法
- コンテナのイメージの作り方と名前
- クラスタへ載せる道具と、マニフェストの持ち方
- 秘密の値の作り方と渡し方
- クラスタの中での PostgreSQL の置き方
- Compose で、kind と同じ振り分けとログインの確認を再現する方法
- 起動、停止、載せ直しのコマンド

やらないこと:

- 手元でない場所への配置。要件定義の 12 章のとおり、機能ができてから決める
- CI。「開発の進め方: Claude Code のハーネス」に書く
- サービスの中の作り。「共通設計: サービスの共通構成」に書いてある

### この文書で使う言葉

| 言葉 | 意味 |
|---|---|
| クラスタ | Kubernetes が動いている、ひとまとまりの環境 |
| kind | Docker のコンテナを 1 台の機械に見立てて、その中で Kubernetes を動かす道具。手元で試すために使う |
| Pod | Kubernetes がコンテナを動かす単位。ふつうは 1 つのコンテナが入る |
| マニフェスト | 「何を、いくつ、どの設定で動かすか」を書いた YAML のファイル。Kubernetes に渡すと、そのとおりの状態にする |

| Gateway API | 入口の振り分けを書くための、Kubernetes の標準の書式。製品が違っても同じ書式で書ける |
| 入口 | ブラウザからの要求を最初に受け取り、後ろのサービスへ振り分けるもの |
| Secret と ConfigMap | Kubernetes が設定を持つための入れ物。秘密の値は Secret、そうでない値は ConfigMap に入れる |

## 4. API

入口の振り分けと、手元での動かし方を、ここに書く。

### 4.1 手元で使う道具

ホスト側に入れるのは、Docker だけとする。
kind、kubectl、helm は、道具を入れたコンテナの中で動かす。
理由は決定の記録 0014 に書く。

| 道具 | 版 | 使いみち |
|---|---|---|
| kind | 0.33.0 | 手元のクラスタを作る、消す、イメージを載せる |
| kubectl | クラスタの Kubernetes と同じ版 | マニフェストを渡す、状態を見る |
| helm | 4.3.0 | 入口の製品を入れる |

- 道具のコンテナは、Docker のソケットを載せ、kind のネットワークにつないで動かす。クラスタには、クラスタの中の住所で届く。この動かし方で、クラスタの作成、マニフェストの適用、helm での導入ができることを確かめた。
- 版は、道具のイメージの `Dockerfile` に固定する。

**この機械での制約**

この機械の Docker は、古い方式(cgroup v1)で動いている。
Kubernetes 1.37 のノードは、この方式では起動しなかった。
Kubernetes 1.34 のノードは起動した。
そこで、クラスタの Kubernetes は 1.34 に固定する。
Docker を新しい方式(cgroup v2)に切り替えるかどうかは、8 章に書く。

### 4.2 クラスタの構成

| 項目 | 値 |
|---|---|
| クラスタの名前 | `recipe-book` |
| ノード | 1 台。管理の役とアプリを動かす役を兼ねる |
| 外に出すポート | ホストの 8080。入口につながる |
| ブラウザで開く住所 | `http://localhost:8080` |

名前空間は次のとおりとする。

| 名前空間 | 入れるもの |
|---|---|
| `recipe-book` | 画面、3 つのサービス、PostgreSQL、入口の振り分けの設定 |
| `envoy-gateway-system` | 入口の製品の管理側。製品が決めた名前である |

アプリのものを 1 つの名前空間にまとめるのは、手元では区切る利点が小さく、まとめて消せるほうが扱いやすいためである。

### 4.3 入口の実装

入口には **Envoy Gateway** を使う。
比べた結果と理由は、決定の記録 0013 に書く。

「共通設計: 認証」の 4.6 が入口に求めることを、Envoy Gateway 1.9.2 で、代役のサービスを使って確かめた。

| 求めること | 結果 |
|---|---|
| 後ろへ渡す前に、`auth-service` に確かめさせる | できた |
| ブラウザが付けた `Authorization` を捨て、`auth-service` が返したもので置き換える | できた。偽の値を付けて送っても、後ろには `auth-service` の値だけが届いた |
| `auth-service` が返したほかのヘッダーを、後ろへ渡さない | できた。渡すヘッダーを名前で選ぶ |
| クッキーを、`auth-service` 以外へ渡さない | できた。`book-service` と `kitchen-service` と画面には届かなかった |
| `auth-service` が 401 か 403 を返したら、その状態と本文をブラウザへ返す | できた |
| `auth-service` が応答しないときに、後ろへ渡さず 503 を返す | できた。4.5 の設定が要る |
| ログインが要らないパスでは、確かめない | できた |
| `/internal` を、外から届かなくする | できた。入口が 404 を返す |
| `GET /api/health` に、入口が自分で答える | できた |
| 画面の静的なファイルは、`auth-service` が止まっていても返す | できた |

**設定の書き方**

| 書くこと | 使う書式 |
|---|---|
| パスごとの振り分け、ヘッダーの削除 | Gateway API の標準の `HTTPRoute` |
| ログインの確認を `auth-service` に任せる | Envoy Gateway の `SecurityPolicy` |
| 入口が自分で応答を返す(稼働の確認、`/internal` の 404) | Envoy Gateway の `HTTPRouteFilter` |
| 入口が自分で作るエラーの本文を、決まった形にする | Envoy Gateway の `BackendTrafficPolicy` |
| 後ろのサービスの住所 | Envoy Gateway の `Backend` |

振り分けは標準の書式で書き、標準にない機能だけを、製品の書式で書く。

### 4.4 振り分け

振り分けは、ログインが要らないものと、要るものの 2 つの `HTTPRoute` に分ける。
ログインの確認(`SecurityPolicy`)は、後者にだけ付ける。

**ログインが要らないもの**

| 条件 | 行き先 | 削るヘッダー |
|---|---|---|
| `GET /api/health` | 入口が 200 と `{"status":"ok"}` を返す | |
| `POST /api/auth/login`、`POST /api/auth/register` | `auth-service` | `Authorization` |
| `/internal` で始まる | 入口が 404 と `NOT_FOUND` を返す | |
| そのほか(`/api` で始まらない) | `frontend` | `Authorization`、`Cookie` |

**ログインが要るもの**

| 条件 | 行き先 | 削るヘッダー |
|---|---|---|
| `/api/books/{bookId}/recipe-edits` と `/api/books/{bookId}/menus`、その下 | `kitchen-service` | `Cookie` |
| そのほかの `/api/books`、`/api/invitations` | `book-service` | `Cookie` |
| そのほかの `/api` | `auth-service` | なし |

- 条件が重なるときは、より細かい条件が先に当たる。`kitchen-service` 向けのパスは正規表現で書く。この並びで、`/api/books/b1/menus/2026-10-11` が `kitchen-service` へ、`/api/books/b1/members` が `book-service` へ届くことを確かめた。
- `auth-service` 向けの要求にだけ、クッキーを残す。ログアウトのときに、どのセッションを消すかを知るためである。
- ログインが要らないパスでも、ブラウザが付けた `Authorization` を削る。偽のトークンを、後ろのサービスへ届けないためである。
- 最後の「そのほかの `/api`」があるので、決めていない `/api` のパスも、ログインの確認を通ってから `auth-service` に届き、そこで 404 になる。確認なしで後ろに届く `/api` のパスは、上の表の 3 つだけである。

### 4.5 ログインの確認

入口が `auth-service` を呼ぶときの形は、製品が決める。
確かめた結果は、次のとおりである。

| 項目 | Envoy Gateway の動き |
|---|---|
| メソッド | 元の要求と同じ |
| パス | 設定したパスの後ろに、元のパスを付ける。例: `PUT /internal/auth/verify/api/books/b1` |
| 渡すヘッダー | 名前を挙げたものだけ。`Cookie`、`Origin`、`X-Request-Id` を挙げる |
| 本文 | 渡さない |
| 期限 | 2 秒 |

「共通設計: 認証」の 4.6 は、`GET /internal/auth/verify` を呼ぶと書いていた。
実際の動きに合わせて、次のように直した。

- `auth-service` は、`/internal/auth/verify` で始まるパスを、どのメソッドでも受ける。
- 元のメソッドは、届いた要求のメソッドから知る。
- 元のパスは、使わない。

**応答しないとき**

| 起きたこと | 入口の応答(設定なし) | 入口の応答(設定あり) |
|---|---|---|
| `auth-service` につながらない、期限を過ぎた | 403。本文なし | 503 と `DEPENDENCY_UNAVAILABLE` |
| `auth-service` の Pod が 1 つもない | 500。本文なし | 503 と `DEPENDENCY_UNAVAILABLE` |
| 後ろのサービスの Pod が 1 つもない | 503。本文なし | 503 と `DEPENDENCY_UNAVAILABLE` |

設定は 2 つである。

- `SecurityPolicy` で、確かめられないときの状態を 503 にする。
- `BackendTrafficPolicy` で、入口が自分で作った 500、502、503、504 の応答を、503 と、エラーの形の本文に書き換える。後ろのサービスが返した応答は、書き換えない。

設定を入れた後で、表の 3 つの場合のすべてで 503 と決まった形の本文が返ることと、`auth-service` が返す 401 がそのまま返ることを確かめた。

**要求の識別子**

- 入口は、すべての要求に `X-Request-Id` を新しく付ける。ブラウザが付けた値は、捨てる。この動きを確かめた。
- サービスは、入口が付けた値を使う(「共通設計: サービスの共通構成」の 4.5)。
- 入口が自分で作る応答(上の 503 など)に `X-Request-Id` を付けることは、確かめていない(8 章)。

### 4.6 画面の静的なファイル

- `frontend` のコンテナは、Next.js が書き出した静的なファイルを、nginx で配る。
- 末尾に `/` も `.html` もないパスで、対応する HTML を返す。例: `/menu` で `menu.html` を返す。
- ないパスには、404 の状態で、見つからないページを返す。どのパスでも同じ HTML を返す設定は入れない。
- 入口は、`/api` と `/internal` で始まらないパスを、すべて `frontend` へ渡す。

Next.js が書き出すファイルの名前と、nginx の設定は、開発の土台を作るときに確かめる(8 章)。

### 4.7 コンテナのイメージ

| イメージ | 作る材料 | 中身 |
|---|---|---|
| `recipe-book/auth-service` | `services/` の全体 | Maven でビルドし、JVM で動かす |
| `recipe-book/book-service` | 同上 | 同上 |
| `recipe-book/kitchen-service` | 同上 | 同上 |
| `recipe-book/frontend` | リポジトリの全体 | Node でビルドし、書き出したファイルを nginx で配る |

- 材料を `services/` の全体にするのは、共通のライブラリ(`service-common`)を一緒にビルドするためである。
- 材料をリポジトリの全体にするのは、画面のビルドが `data/`(元のレシピ)を読むためである。要らないディレクトリは、除外のファイルで外す。
- イメージは、ビルドの段と動かす段を分ける。動かす段に、ビルドの道具とソースを入れない。
- コンテナは、管理者でない利用者で動かす。
- 手元では、札を `dev` に固定する。作ったイメージを kind に載せ、Pod を起動し直して入れ替える。外の置き場には送らない。
- 配置するときの札は、コミットの識別子にする。配置する場所を決めるときに確定する。

イメージの作り方の細部(元にするイメージ、ビルドの中間結果の残し方)は、開発の土台を作るときに決める。

### 4.8 載せる道具と、マニフェストの持ち方

クラスタへ載せるのには、kubectl に入っている **Kustomize** を使う。
理由は決定の記録 0015 に書く。

Kustomize は、元になるマニフェストに、環境ごとの違いだけを重ねる道具である。

```
deploy/
├── tools/                # 道具のコンテナと、起動や載せ直しのスクリプト
├── kind/
│   └── cluster.yaml      # クラスタの構成
├── gateway/              # 入口の設定。kind と Compose の両方が読む
│   ├── routes.yaml       # 振り分け、ログインの確認、入口が返す応答
│   ├── kind/             # kind だけの設定(待ち受けるポート、後ろの住所)
│   └── compose/          # Compose だけの設定(同上)
└── k8s/
    ├── base/             # 元になるマニフェスト
    │   ├── auth-service/
    │   ├── book-service/
    │   ├── kitchen-service/
    │   ├── frontend/
    │   └── postgres/
    └── overlays/
        └── local/        # 手元の環境だけの違い
```

- サービスごとに、動かすもの(Deployment)、住所(Service)、設定(ConfigMap)を持つ。
- Service は、クラスタの中だけで届く種類にする。外に出るのは入口だけである。
- 稼働の確認は、「共通設計: サービスの共通構成」の 4.8 のとおり、ポート 9000 の 3 つのパスを使う。
- メモリと CPU の、求める量と上限を書く。数字は、開発の土台を作るときに測って決める。
- 入口の製品そのものは、helm で入れる。版は、スクリプトに固定する。

### 4.9 秘密の値

| 値 | 作る時 | 入れ先 |
|---|---|---|
| PostgreSQL の管理者と、3 つの接続する利用者のパスワード | クラスタを作るとき | Secret |
| トークンの署名の鍵の組 | クラスタを作るとき | Secret。`auth-service` にファイルとして載せる |

- 値は、クラスタを作るスクリプトが乱数で作り、そのまま Secret に入れる。ファイルに書き出さない。リポジトリに置かない。
- クラスタを作り直すと、値も変わる。手元のデータは、クラスタと一緒に消える。
- Compose では、同じスクリプトが `.env` と鍵のファイルを作る。どちらもリポジトリに入れない設定にする。
- 秘密でない設定(ほかのサービスの住所、画面のオリジン)は、ConfigMap に入れる。

### 4.10 Compose での再現

1 つのサービスを書いている間は、Compose で動かす。
入口には、kind と同じ Envoy Gateway を、Kubernetes なしで動かす形で使う。

- 振り分けとログインの確認の設定(`deploy/gateway/routes.yaml`)は、kind と Compose で同じファイルを読む。
- 違うのは、待ち受けるポートと、後ろのサービスの住所だけである。
- 同じ形の設定ファイルを、kind と Compose の両方に入れて、4.3 の表の結果が同じになることを確かめた。

| Compose のサービス | 中身 |
|---|---|
| `gateway` | Envoy Gateway。設定をファイルから読む |
| `postgres` | PostgreSQL。データベースを 3 つ作る |
| `auth-service`、`book-service`、`kitchen-service` | Quarkus の開発モード。ソースを載せ、変更をすぐに反映する |
| `frontend` | Next.js の開発用のサーバー |

- 書いているサービスだけを起動できるようにする。例: `auth-service` を書く間は、`gateway`、`postgres`、`auth-service` だけを動かす。
- ほかのサービスを呼ぶサービス(`kitchen-service` など)を 1 つだけ動かすときは、相手を代役にするか、相手も起動する。
- Compose の入口は、起動した直後の数秒、503 を返すことがあった。起動を待ってから使う。

### 4.11 コマンド

コマンドは、道具のコンテナを通して動かす。
ホスト側のシェルの種類に左右されないようにするためである。

| すること | コマンド |
|---|---|
| クラスタを作り、一式を載せる | `docker compose -f deploy/tools/compose.yaml run --rm tools up` |
| 変えたものを作り直して、載せ直す | `... run --rm tools deploy <名前>`。名前を省くと全部 |
| 状態を見る | `... run --rm tools status` |
| ログを見る | `... run --rm tools logs <名前>` |
| クラスタを消す | `... run --rm tools down` |
| 書いている間の起動 | `docker compose up <名前>` |

この一覧は、作る予定の形である。
開発の土台を作るときに、実際に動かして確定し、`CLAUDE.md` に書く。

## 5. データ

PostgreSQL は、クラスタの中で動かす。
置き方の理由は、決定の記録 0016 に書く。

| 項目 | 値 |
|---|---|
| 版 | 18 |
| 動かし方 | 1 つの Pod。再起動しても同じ保存先につながる種類(StatefulSet)にする |
| 保存先 | kind が用意する保存先。8GB |
| データベースと利用者 | 最初の起動のときに、3 つのデータベースと 3 つの利用者を作る(「共通設計: データベースの共通仕様」の 5.1) |

- 版は、大きい番号だけを固定する。小さい番号は、開発の土台を作る時点の最新にする。
- テストのときの PostgreSQL は、Compose で先に起動しておく。Quarkus に起動させない。Java をコンテナの中で動かすので、コンテナの中から別のコンテナを起動する仕組みを避けるためである。テスト用のデータベースは、開発用とは別の名前にする。
- バックアップは取らない。手元のデータは、消えてよいものとして扱う。

## 6. サービスの間のやり取り

- サービスは、相手を Kubernetes の中の名前で呼ぶ。例: `http://book-service:8080`
- サービスの間の呼び出しは、入口を通らない。`/internal` は、この道でだけ届く。
- 入口は、`/internal` で始まる要求に 404 を返す。Service は外に出ていないので、入口のほかに外から届く道はない。
- 名前空間の中の通信を、相手ごとに絞る設定(NetworkPolicy)は、開発の土台を作るときに、kind で働くことを確かめてから入れる(8 章)。

## 7. 受け入れ条件

kind の上で、ブラウザのテストか、HTTP を送るテストで確かめる。

| 識別子 | 条件 |
|---|---|
| `AC-RT-01` | 何もない状態から `up` を 1 回動かすと、`http://localhost:8080/` が 200 を返す |
| `AC-RT-02` | `GET /api/health` が、200 と `{"status":"ok"}` を返す |
| `AC-RT-03` | クッキーなしで `GET /api/books` を呼ぶと、401 と `UNAUTHENTICATED` が返る |
| `AC-RT-04` | 有効なクッキーと、偽の `Authorization` を付けて `GET /api/books` を呼ぶと、`book-service` に届いた `Authorization` が `auth-service` の発行したトークンで、`Cookie` が届いていない |
| `AC-RT-05` | `PUT /api/books/{bookId}/recipe-edits/{slug}` が `kitchen-service` に、`GET /api/books/{bookId}/members` が `book-service` に届く |
| `AC-RT-06` | 外から `GET /internal/auth/keys` と `GET /internal/books/b1/roles/u1` を呼ぶと、404 と `NOT_FOUND` が返り、サービスに届かない |
| `AC-RT-07` | 偽の `Authorization` を付けて `POST /api/auth/login` を呼ぶと、`auth-service` に `Authorization` が届かない |
| `AC-RT-08` | `auth-service` を止めて `GET /api/books` を呼ぶと、503 と `DEPENDENCY_UNAVAILABLE` が返る。`GET /` は 200 を返す |
| `AC-RT-09` | `book-service` を止めて `GET /api/books` を呼ぶと、503 と `DEPENDENCY_UNAVAILABLE` が返る。`GET /api/me` は 200 を返す |
| `AC-RT-10` | `X-Request-Id: abc` を付けて呼ぶと、サービスに届く `X-Request-Id` が `abc` でない |
| `AC-RT-11` | `AC-RT-02` から `AC-RT-07` が、Compose の入口でも同じ結果になる |
| `AC-RT-12` | `down` の後に `up` を動かすと、前のデータが残っておらず、起動に成功する |
| `AC-RT-13` | リポジトリのどのファイルにも、データベースのパスワードと署名の秘密の鍵が含まれない |

`AC-AUTHN-18` と `AC-AUTHN-21`(「共通設計: 認証」)は、`AC-RT-04` と `AC-RT-08` と同じ場面である。

## 8. 未決事項

- **Docker の方式**: この機械の Docker は cgroup v1 で、Kubernetes 1.35 以降のノードが起動しない。Docker Desktop を更新して cgroup v2 にすれば、新しい版を使える。ホスト側の変更なので、利用者が決める。それまでは 1.34 を使う。
- **入口が作る応答の `X-Request-Id`**: 入口が自分で返す 503 などに、識別子を付けられるかを確かめていない。開発の土台を作るときに確かめる。付けられなければ、画面は問い合わせ番号を出さない。
- **NetworkPolicy**: kind で働くかを確かめていない。開発の土台を作るときに確かめる。
- **Next.js が書き出すファイルの名前と、nginx の設定**: 開発の土台を作るときに確かめる。
- **入口の記録に残るパス**: 入口は、要求のパスを記録に出す。秘密の値をパスに入れない設計にする(招待の文字列は、本文で渡す)。それでも残るものがあれば、記録の書式から外す。
- **載せ直しの速さ**: イメージを作り直して載せ直すのに、何秒かかるかを測っていない。遅いときは、変更を見張って自動で載せ直す道具(Skaffold など)を足すかを決める。
- **入口の管理側の再起動**: 試作の間に 1 回、Kubernetes の応答が遅れて、入口の管理側が起動し直した。要求を運ぶ側は止まらなかった。ほかの作業が同じ機械で Docker を使っていた時間帯である。続くようなら、原因を調べる。
- **4.7 から 4.11 の細部**: 設計であり、まだ作っていない。開発の土台を作るときに、動かして確定する。
