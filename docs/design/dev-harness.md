# 開発の進め方: Claude Code のハーネス

対応する Issue: #15

## 1. 目的

実装の段階で、Claude Code が自分で作り、自分で確かめ、誤りに自分で気付ける状態を決める。
人が毎回見張らなくても、決まりを破る変更が途中で止まるようにする。

ハーネスは、Claude Code の周りに置く仕組みの総称である。
自動で走る検査、許す操作と拒む操作、手順書、CI がこれに当たる。

## 2. 範囲

やること:

- 編集の後と、作業を終える前に自動で走らせる検査
- 許可する操作、確認つきにする操作、拒む操作
- 作る Skill の一覧と中身
- 受け入れ条件の識別子と、テストを対応させる方法
- ブランチ、コミット、PR の進め方
- CI で走らせるもの
- 実装の段階の Issue の立て方

やらないこと:

- 設定ファイルと Skill の実物を作ること。開発の土台(段階 0)で作る。検査に使うコマンドが、そこで初めて決まるためである
- 配置の自動化。配置する場所が決まってから決める

### この文書で使う言葉

| 言葉 | 意味 |
|---|---|
| フック | Claude Code が決まった時点(ファイルを編集した後、作業を終える前など)で、自動で走らせるコマンド。結果を Claude Code に返し、作業を止めさせることもできる |
| Skill | ある種類の作業の手順書。Claude Code が、その作業のときに読み込む |
| 許可の設定 | Claude Code が、確認なしで実行してよいコマンド、確認が要るコマンド、実行できないコマンドを決める設定 |
| CI | PR を出すたびに、決まった検査を GitHub の上で自動で走らせる仕組み |
| 受け入れ条件 | 仕様書に書いた、合否を判定できる条件。`AC-EDIT-03` のような識別子を持つ |

## 8. 未決事項

- **検査のコマンド**: 9 章の表の「走らせるもの」は、役目を書いたものである。実際のコマンドは、段階 0 で作って確定し、`CLAUDE.md` に書く。
- **作業を終える前の検査にかかる時間**: 2 分以内を目安にした。測っていない。超えるときは、API のテストを外して PR の前の手順に移す。
- **CI で kind を動かすこと**: GitHub の実行環境で、kind と入口が動くかを確かめていない。段階 0 で確かめる。動かないか、遅すぎるときは、`main` へのマージの後だけに走らせる。
- **今ある `.claude/commands/` の扱い**: 5 つのコマンド(`implement`、`plan`、`pr`、`review-code`、`test-gen`)は、前のアプリ向けに書かれている。消して、11 章の Skill に置き換える案である。利用者が作ったものなので、消してよいかを利用者に確かめる。
- **並行の作業の数**: 設計の段階では、同時に 6 件を走らせて、利用枠の上限に当たった。実装の段階で、同時にいくつまで走らせるかは、段階 0 で試して決める。

## 9. 自動で走らせる検査

検査は、3 つの時点に分ける。
早い時点ほど、軽い検査だけを置く。
重い検査を編集のたびに走らせると、作業が進まなくなるためである。

| 時点 | 目的 | かけてよい時間 |
|---|---|---|
| ファイルを編集する前 | 触ってはいけないファイルと操作を、止める | 1 秒以内 |
| ファイルを編集した後 | そのファイルだけの、すぐ分かる誤りを返す | 5 秒以内 |
| 作業を終える前 | 変えた範囲の、型、lint、テストを通す | 2 分以内(見込み) |

### 9.1 編集する前に止めるもの

| 対象 | 理由 |
|---|---|
| `api/` の下のファイル | サービスのコードから出力するものである。手で直すと、コードと食い違う |
| `frontend/src/api/generated/` の下のファイル | `api/` の仕様から作るものである |
| `main` にすでにある Flyway のファイル | 適用済みのファイルを書き換えると、環境ごとにテーブルが食い違う(「共通設計: データベースの共通仕様」の 5.9) |
| `.env`、鍵のファイル | 秘密の値である。Claude Code は読まず、書かない |
| `data/foods.json` | 成分表から変換して作るものである。直すときは、変換のスクリプトを直す |

止めたときは、理由と、代わりにすること(例: 「入口のコードを直して、仕様を出力し直す」)を返す。

### 9.2 編集した後に走らせるもの

| 編集したファイル | 走らせるもの |
|---|---|
| `frontend/` の TypeScript | そのファイルだけの lint と整形 |
| `services/` の Java | そのファイルだけの整形 |
| `docs/` の Markdown | 文章の規約の検査(中黒、em ダッシュ、1 行に 2 文) |
| `data/recipes/` の JSON | そのファイルだけの形の検証 |

型検査とテストは、ここでは走らせない。
ファイルを 1 つ直すたびに全体を検査すると、直している途中の状態で必ず失敗するためである。

### 9.3 作業を終える前に走らせるもの

変えたファイルの場所から、走らせる検査を選ぶ。

| 変えた場所 | 走らせるもの |
|---|---|
| `frontend/` | 型検査、lint、単体のテスト |
| `services/service-common/` | 3 つのサービスすべての、下の行の検査 |
| `services/<サービス>/` | コンパイル、ドメインのテスト、層の検査(`AC-SVC-18` から `AC-SVC-20`) |
| `data/` | データの検証(`check:data`) |
| `docs/`、`docs-site/` | 仕様書のサイトの厳格なビルド |
| `deploy/` | マニフェストの形の検査 |

- 検査が失敗したら、作業を終えさせず、失敗の内容を Claude Code に返す。
- 同じ失敗で 2 回続けて止めたら、3 回目は止めずに、失敗していることを利用者への報告に書かせる。直せない失敗で、終われなくなるのを防ぐためである。
- データベースが要る API のテストと、kind の上のテストは、ここでは走らせない。PR を出す前に、Skill の手順で走らせる(11 章)。
- 検査は、すべて Docker のコンテナの中で走らせる。

## 10. 許可の設定

今の設定は、前のアプリ(Vite と Cloudflare Workers)のものである。
段階 0 で、次の内容に置き換える。

| 区分 | 操作 | 理由 |
|---|---|---|
| 確認なしで許す | `docker compose` での起動、検査、テスト。道具のコンテナでの `status` と `logs` と `deploy` | 作って確かめる流れを、止めないため |
| 確認なしで許す | `git status`、`git diff`、`git log`、`git switch`、`git add`、`git commit`、`main` 以外への `git push` | PR の流れに要る |
| 確認なしで許す | `gh pr create`、`gh pr view`、`gh pr edit`、`gh issue` の読み書き | 同上 |
| 確認つき | データを消す操作。`docker compose down -v`、クラスタを消す `down` | 手元のデータが消える |
| 確認つき | 履歴を書き換える操作。`git push --force`、`git reset --hard`、`git rebase` | 元に戻しにくい |
| 確認つき | ファイルをまとめて消す操作 | 同上 |
| 拒む | `gh pr merge` | マージは利用者が行う |
| 拒む | `main` への `git push`、`main` の上での `git commit` | 変更は PR で入れる |
| 拒む | 検査を飛ばす操作。`--no-verify` | 検査を通さない変更を入れないため |
| 拒む | `.env` と鍵のファイルを読むこと | 秘密の値を、会話とログに出さないため |
| 拒む | ホスト側で Node と Java を動かすこと。`npm`、`npx`、`mvn`、`java` | コンテナの中で動かす決まりである |

`git add` は、ファイルの名前を挙げて行う。
`git add -A` は、関係のないファイルを巻き込むことがある(13 章)。

## 11. Skill

| Skill | 使う時 | 中身 |
|---|---|---|
| `recipe` | レシピを足す、直す | 今あるものを直す。出力を HTML から `data/recipes/<slug>.json` に変える。食材マスタにない材料を足す手順、写真と出典、データの検証までを含む。直す点は「データ設計」の対照表に従う |
| `add-endpoint` | サービスに API を足す、変える | 仕様書の確認、ドメイン、ユースケース、基盤、入口の順に書く手順。5 通りの立場のテスト。`api/` の仕様の出力と、画面側の型の作り直し |
| `add-migration` | テーブルを足す、変える | Flyway のファイルの名前と番号、動かしたまま変えるときの 3 段階、`*JpaEntity` との突き合わせ |
| `verify-ui` | 画面を足す、変える | Playwright でその画面を開き、幅 360px と 1,080px でスクリーンショットを撮って見る手順。キーボードだけでの操作と、axe の検査 |
| `cluster` | kind に載せて確かめる | 起動、載せ直し、ログの見方。よくある失敗(イメージが古い、Pod が起動しない、入口が 503 を返す)の調べ方 |
| `ac-coverage` | PR を出す前 | 受け入れ条件とテストの対応を調べ、足りないものを一覧にする(12 章) |
| `pre-pr` | PR を出す前 | 変えた範囲に応じて、API のテスト、kind の上のテスト、`ac-coverage` を走らせ、PR の本文の「証跡」に入れる出力を集める |

- Skill は、`.claude/skills/<名前>/SKILL.md` に置く。
- 手順の中のコマンドは、段階 0 で確定したものを書く。
- うまくいかなかったことと、その直し方は、該当する Skill に書き足す。次に同じ作業をするときに、同じ失敗をしないためである。

文章の規約、仕様書の規約、PR の本文の規約は、今ある `.claude/rules/` をそのまま使う。

## 12. 受け入れ条件とテストの対応

**決まり**

- 受け入れ条件の識別子は、仕様書の表に 1 つずつ書いてある。形は `AC-<機能>-<連番2桁>` である。
- テストの名前に、対応する識別子を書く。1 つのテストが複数の条件を確かめるときは、すべて書く。
- 1 つの条件を、複数のテストで確かめてもよい。

**調べ方**

道具を 1 つ作る。
`docs/` の下のすべての文書から識別子を集め、テストのコード(画面の単体のテスト、ブラウザのテスト、サービスのテスト)の中を探す。

| 状態 | 意味 | CI |
|---|---|---|
| テストがある | 条件がテストされている | 通す |
| テストがなく、「まだ作らない」の一覧にある | まだ実装していない段階の条件である | 通す |
| テストがなく、一覧にもない | 実装したのに、テストを書き忘れた | 失敗させる |
| テストにあるが、仕様書にない | 識別子の書き間違いか、消した条件である | 失敗させる |

「まだ作らない」の一覧は、`docs/acceptance-pending.txt` に、識別子を 1 行に 1 つ書いて持つ。
設計の段階が終わった時点では、すべての識別子がこの一覧に入っている。
機能を実装する PR が、対応する識別子を一覧から消す。
一覧が空になったとき、すべての受け入れ条件にテストがある。

仕様書に条件を足したときは、同じ PR で、テストを書くか、一覧に足す。
どちらもしないと、CI が失敗する。

## 13. ブランチ、コミット、PR

`CLAUDE.md` の「作業の進め方」に書いてある決まりを、そのまま使う。
実装の段階のために、次を足す。

- 1 つの PR は、1 つの Issue に対応させる。差分は、作り直したファイル(`api/`、`generated/`)を除いて 400 行程度までを目安にする。超えるときは、Issue を分ける。
- サービスをまたぐ変更は、呼ばれる側、呼ぶ側、画面の順に、別々の PR にする。
- コミットの題は、Conventional Commits の形で、日本語で書く。種類は `feat`、`fix`、`docs`、`test`、`refactor`、`chore`、`build` を使う。
- 受け入れ条件のテストを、実装より先にコミットする。先に失敗するテストがあったことを、履歴に残すためである。
- PR の本文の「証跡」に、`pre-pr` が集めた出力を入れる。

**並行して作業するとき**

設計の段階で、複数の Issue を別々の作業場所で同時に進めた。
そこで起きたことから、次を決める。

- 並行の作業場所(`.claude/worktrees/`)は、`.gitignore` に入れておく。入れていなかったため、`git add -A` でコミットに巻き込んだ。
- どの PR も足す行があるファイル(仕様書のサイトの `nav`、`docs/index.md`、`README.md`)は、同時に直すと衝突する。並行する作業には、決定の記録の番号の範囲を先に割り当てる。衝突は、マージの順にまとめ役が解く。
- 前の PR がマージされる前に、その内容を前提にする作業を並行して始めるときは、前提の PR をまとめた作業用のブランチを作り、そこから切る。
- 互いの成果物を読めないまま書いた文書は、戻ってきた後に、境目を突き合わせる。

## 14. CI

PR を出すたびに、GitHub Actions で次を走らせる。
手元と同じコンテナ、同じコマンドを使う。
手元では通るのに CI では落ちる、ということを減らすためである。

| 検査 | 内容 | 走らせる条件 |
|---|---|---|
| 仕様書 | 仕様書のサイトの厳格なビルド。文章の規約の検査 | `docs/`、`docs-site/` を変えたとき |
| 画面 | 型検査、lint、単体のテスト、ビルド | `frontend/`、`data/`、`api/` を変えたとき |
| データ | データの検証(`check:data`) | `data/` を変えたとき |
| サービス | コンパイル、ドメインのテスト、層の検査、API のテスト(本物の PostgreSQL) | `services/` を変えたとき |
| API の約束 | コードから出力した仕様と、コミットされた `api/` を比べる(`AC-API-11`)。画面側の型を作り直して、差がないことを確かめる | `services/`、`api/`、`frontend/src/api/` を変えたとき |
| つないだ動き | kind に一式を載せ、ブラウザのテストを走らせる | `frontend/`、`services/`、`deploy/` を変えたとき |
| 受け入れ条件 | 12 章の対応の検査 | いつも |
| 秘密の値 | パスワード、鍵、トークンに見える文字列がないことを確かめる | いつも |

- どれか 1 つでも失敗した PR は、マージしない。
- 検査を通すために、テストを消したり、飛ばす印を付けたりしない。飛ばす必要があるときは、理由を PR の本文に書き、利用者の承認を得る。

## 15. 実装の段階の Issue の立て方

**立てる時**

要件定義の 11 章の段階ごとに立てる。
次の段階の Issue は、前の段階が終わってから立てる。
先の段階まで立てておくと、前の段階で分かったことで、中身が古くなるためである。

**1 つの Issue の大きさ**

1 つの PR で終わる大きさにする。
1 つのサービスの 1 つの機能か、1 つの画面である。

**書くこと**

| 節 | 中身 |
|---|---|
| 目的 | この Issue が終わると、何ができるようになるか |
| 対応する仕様書 | 文書と節の番号 |
| 満たす受け入れ条件 | 識別子の一覧。この PR で `docs/acceptance-pending.txt` から消すもの |
| 作るもの | ファイルやクラスの名前ではなく、役目で書く |
| 完了の条件 | 上の受け入れ条件のテストが通る。CI が通る。画面を変えたら、スクリーンショットを PR に付ける |
| 先に終えておくもの | Issue の番号 |

**段階 0 の Issue の案**

段階 0 は、開発の土台である。
終わりの条件は、登録してログインし、入口を通って `GET /api/me` が返るところまでが、kind の上でつながることである。

| 順 | 中身 | 主な受け入れ条件 |
|---|---|---|
| 0-1 | 道具のコンテナと、kind のクラスタの起動と削除 | `AC-RT-01` の前半、`AC-RT-12` |
| 0-2 | `services/` の親の構成、`service-common`(エラーの形、例外の変換、要求の識別子、ログ) | `AC-API-01` から `AC-API-06`、`AC-SVC-01` から `AC-SVC-08` |
| 0-3 | `auth-service` の骨組み。データベースへの接続、Flyway、稼働の確認、層の検査 | `AC-DB-01` から `AC-DB-03`、`AC-SVC-14` から `AC-SVC-16`、`AC-SVC-18` から `AC-SVC-20` |
| 0-4 | `auth-service` の登録、ログイン、ログアウト、`GET /api/me`、パスワードの変更 | `AC-AUTHN-01` から `AC-AUTHN-08`、`AC-AUTHN-22`、`AC-SVC-17`、「機能設計: 登録とログイン」の `AC-AUTH` のうち API の条件 |
| 0-5 | `auth-service` の `verify` と、トークン、公開の鍵 | `AC-AUTHN-09` から `AC-AUTHN-17`、`AC-AUTHN-19`、`AC-AUTHN-20` |
| 0-6 | `book-service` と `kitchen-service` の骨組み。トークンの確認まで | `AC-DB-04`、`AC-AUTHN-16`、`AC-AUTHN-17` |
| 0-7 | `frontend` の骨組み。テーマ、レイアウト、共通の部品、API のクライアント、ログインの状態 | 「画面の共通仕様」の `AC-UI` と、「画面の一覧と遷移」の `AC-NAV` のうち、土台に関わるもの |
| 0-7b | ログイン、登録、アカウントの画面と、ヘッダーの利用者のメニュー | 「機能設計: 登録とログイン」の `AC-AUTH` のうち画面の条件 |
