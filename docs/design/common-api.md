# 共通設計: API の共通仕様

対応する Issue: #1

## 1. 目的

`auth-service`、`book-service`、`kitchen-service` の API を、同じ決まりで作れるようにする。
画面側が、どのサービスの応答も同じ形で扱えるようにする。

## 2. 範囲

やること:

- パス、JSON、状態、エラー、識別子、日時、一覧、改訂番号の決まり
- OpenAPI の仕様の出し方と置き場

やらないこと:

- 個々の API の入力と出力。機能ごとの仕様書に書く
- ログインの確かめ方と、署名付きトークン。「共通設計: 認証」に書く
- ログと、要求を追うための識別子。「共通設計: サービスの共通構成」に書く

## 3. 画面

なし。
画面側での応答の扱いは「共通設計: 画面の共通仕様」に書く。

## 4. API

### 4.1 パス

- 外に出す API は `/api`、サービスの間だけで使う API は `/internal` の下に置く。
- 名詞の複数形を、英小文字とハイフンで書く。例: `/api/books/{bookId}/recipe-edits`
- 動詞は HTTP のメソッドで表す。メソッドで表せない操作だけ、末尾に動詞を置く。例: `POST /api/invitations/{token}/accept`
- パスの変数は、何の識別子かが分かる名前にする。`{id}` ではなく `{bookId}` と書く。
- 絞り込みと件数の指定は、クエリの変数で渡す。

### 4.2 メソッドと成功の状態

| メソッド | 使いどころ | 成功の状態 |
|---|---|---|
| `GET` | 取得。何度呼んでも状態を変えない | 200 |
| `POST` | 作成と、メソッドで表せない操作 | 作成は 201、操作は 200 か 204 |
| `PUT` | 全体の置き換え。同じ内容を何度送っても結果が同じ | 200 |
| `PATCH` | 一部の項目の変更 | 200 |
| `DELETE` | 削除 | 204 |

`GET /api/books` は例外で、自分のレシピ帳がなければ作る(要件定義の 4.4)。

201 と 200 は、作成か変更をした後の内容を本文で返す。
画面が、保存の後にもう一度取得しなくて済むようにするためである。

### 4.3 JSON

- 文字コードは UTF-8、`Content-Type` は `application/json` とする。
- 項目名は、小文字で始めて単語の境目を大文字にする(camelCase)。例: `baseVersion`
- 応答では、値がない項目を省かずに `null` で返す。応答の形が場合によって変わらないようにするためである。
- 入力では、項目を省いた場合と `null` を送った場合を同じに扱う。
- 入力に知らない項目があれば、400 で拒む。項目名の打ち間違いが黙って無視されるのを防ぐためである。
- 一覧は配列をそのまま返さず、`{ "items": [...], "nextCursor": ... }` の形で返す。分けて返す決まりは 4.6 に書く。
- 真偽の項目は `is`、`has`、`can` で始める。例: `isOwner`

### 4.4 識別子

- 利用者、レシピ帳、招待、セッションの識別子は UUID(バージョン 7)とし、文字列で受け渡す。
- バージョン 7 を使うのは、作った順に並ぶので、データベースの索引が散らばりにくいためである。
- 識別子は、作る側のサービスが発行する。画面からは受け取らない。
- レシピの識別子は、元のレシピのファイル名(`slug`)を使う。英小文字、数字、ハイフンで、64 文字までとする。

### 4.5 日時と日付

- 記録した瞬間は、協定世界時の ISO 8601 で、秒までを返す。例: `"2026-10-10T12:34:56Z"`
- 暦の上の一日は `"YYYY-MM-DD"` で受け渡す。例: `"2026-10-10"`
- 画面は、日時を表示するときに利用者の時間帯へ直す。日付は直さない。

### 4.6 件数の上限と、一覧の返し方

#### 件数に上限を設ける

増え続けるものには、件数の上限を設ける。

| 対象 | 上限 |
|---|---|
| 1 人が参加できるレシピ帳 | 20 |
| 1 つのレシピ帳のメンバー | 20 |
| 1 つのレシピ帳の、有効な招待 | 10 |
| 1 つのレシピ帳の、編集済みのレシピ | 1,000 |

上限に達しているときに、さらに作ろうとする要求は拒む。
状態は 409、`code` は `LIMIT_EXCEEDED` とし、`details.limit` に上限の数を入れる。

例: メンバーが 20 人いるレシピ帳の招待を、21 人目が受けようとする。
`book-service` はメンバーに加えず、409 と `LIMIT_EXCEEDED` を返す。
画面は `code` を見て「メンバーは 20 人までです」と案内する。

#### 一覧は分けて返す

一覧を返す API は、該当するものを一度に全部は返さず、決まった件数ずつに分けて返す。
この仕組みをページ分けと呼ぶ。
件数が増えても、1 回の応答の大きさとかかる時間が変わらないようにするためである。

分け方には、続きの位置を示す目印を使う。
この目印をカーソルと呼ぶ。

**要求**

| クエリの変数 | 内容 |
|---|---|
| `limit` | 1 回で返す件数。省くと 20。1 以上 100 以下 |
| `cursor` | 続きの位置。前の応答の `nextCursor` をそのまま渡す。最初の要求では付けない |

**応答**

```json
{
  "items": [ { "...": "..." } ],
  "nextCursor": "eyJpZCI6IjAxOTJhYmMuLi4ifQ"
}
```

| 項目 | 内容 |
|---|---|
| `items` | 今回の分。0 件のときは空の配列 |
| `nextCursor` | 続きがあるときは、次の要求に渡す文字列。続きがないときは `null` |

例: メンバーが 45 人いるレシピ帳の一覧を、20 件ずつ取る。

1. `GET /api/books/{bookId}/members?limit=20` を呼ぶ。20 人と `nextCursor` が返る。
2. `GET /api/books/{bookId}/members?limit=20&cursor=<1 の nextCursor>` を呼ぶ。次の 20 人と `nextCursor` が返る。
3. 同じように呼ぶ。残りの 5 人が返り、`nextCursor` は `null` である。ここで終わる。

決まりは次のとおりとする。

- 並び順は API ごとに固定し、機能ごとの仕様書に書く。画面から並び順を指定する仕組みは作らない。
- 並び順は、同じ順位のものが出ないように決める。順位が同じものがあると、続きの位置が一つに定まらないためである。作成日時で並べるときは、識別子も並び順に加える。
- カーソルの中身は、最後に返した 1 件の並び順の値である。画面はカーソルを作らず、中身を読まず、受け取った文字列をそのまま返す。
- カーソルに有効期限は設けない。
- 取得の途中でデータが増えたり減ったりしても、同じものを 2 回返さず、もともとあったものを抜かさない。
- `limit` が範囲の外のとき、`cursor` が読めないときは、400 と `VALIDATION_FAILED` を返す。`fields` の `path` にはクエリの変数の名前を入れる。
- 全部で何件あるかは返さない。数えるための問い合わせが毎回増えるためである。件数が要る画面が出てきたら、その API にだけ足す。
- 画面が全件を必要とするときは、`nextCursor` が `null` になるまで繰り返し呼ぶ。繰り返しは API を呼ぶクライアントにまとめ、画面ごとに書かない。

ページ分けの方式を選んだ理由は、決定の記録 0003 に書く。

### 4.7 入力の大きさ

- 要求の本文は 64KB までとする。
- レシピの編集内容(`PUT .../recipe-edits/{slug}`)だけは 256KB までとする。
- 超えた要求には 413 と `PAYLOAD_TOO_LARGE` を返す。
- 文字列と配列には、項目ごとに長さの上限を付ける。上限は機能ごとの仕様書に書く。

### 4.8 エラーの形

エラーは、どのサービスも次の形で返す。

```json
{
  "code": "VALIDATION_FAILED",
  "message": "入力に誤りがあります。",
  "details": {
    "fields": [
      { "path": "ingredientGroups[0].items[2].amount", "code": "MIN", "message": "0 より大きい数を入れてください。" }
    ]
  }
}
```

| 項目 | 内容 |
|---|---|
| `code` | エラーの種類。英大文字とアンダースコア。画面はこの値で動きを分ける |
| `message` | 利用者に見せてよい日本語の文。内部の事情(テーブル名、例外の名前、ほかのサービスの名前)を含めない |
| `details` | 種類ごとの追加の情報。ないときは `null` |

画面は `message` の文言で動きを分けない。
文言は後から直すことがあるためである。

### 4.9 エラーの種類

| `code` | 状態 | 起きる場面 | `details` |
|---|---|---|---|
| `VALIDATION_FAILED` | 400 | 入力が決まりに合わない。知らない項目がある。JSON として読めない | `fields` |
| `UNAUTHENTICATED` | 401 | ログインしていない。セッションが切れた | なし |
| `LOGIN_FAILED` | 401 | メールアドレスかパスワードが違う | なし |
| `FORBIDDEN` | 403 | メンバーだが役割が足りない | なし |
| `CROSS_SITE_REQUEST` | 403 | 状態を変える要求が、ほかのサイトの画面から送られた | なし |
| `NOT_FOUND` | 404 | 対象がない。メンバーでないレシピ帳を指定した | なし |
| `EMAIL_TAKEN` | 409 | 登録済みのメールアドレスで登録しようとした | なし |
| `REVISION_CONFLICT` | 409 | 改訂番号が合わない | `currentRevision` |
| `LIMIT_EXCEEDED` | 409 | 上限を超える作成 | `limit` |
| `INVITATION_INVALID` | 410 | 招待が期限切れ、使用済み、取り消し済み | なし |
| `PAYLOAD_TOO_LARGE` | 413 | 本文が大きすぎる | なし |
| `LOGIN_LOCKED` | 429 | ログインの失敗が続き、受け付けていない | `retryAfterSeconds` |
| `INTERNAL_ERROR` | 500 | 想定していない失敗 | なし |
| `DEPENDENCY_UNAVAILABLE` | 503 | ほかのサービスが応答せず、処理を進められない | なし |

決まりは次のとおりとする。

- 入力の検証で見つかった誤りは、最初の 1 件で止めず、すべてを `fields` に入れて返す。
- `fields` の `path` は、入力の JSON の中の位置を、項目名と添字で書く。
- `fields` の `code` は、`REQUIRED`、`MIN`、`MAX`、`TOO_LONG`、`TOO_MANY`、`INVALID_FORMAT`、`UNKNOWN_FIELD` のいずれかとする。
- `INVITATION_INVALID` は、期限切れ、使用済み、取り消し済みを区別しない。招待の状態を外から調べられないようにするためである。
- `INTERNAL_ERROR` の `message` は、いつも同じ文にする。原因はログに出し、応答には出さない。
- この表にない `code` を足すときは、先にこの仕様書に足す。
- 画面のクライアントは、応答を受け取れなかったときなどに、自分で `code` を付ける(`NETWORK_ERROR`、`TIMEOUT`、`UNEXPECTED_RESPONSE`)。これらは画面の中だけで使う値で、サービスは返さない。「共通設計: 画面の共通仕様」の 4.1 に書く。

### 4.10 改訂番号

レシピの編集内容と献立は、改訂番号(`revision`)を持つ。
同時に編集したときに、黙って上書きされるのを防ぐためである。

- 改訂番号は 1 から始まる整数で、保存のたびに 1 増える。
- 取得の応答に、今の改訂番号を入れる。まだ保存されていないものを取得したときは 404 を返す。
- 保存の要求の本文に、画面が持っている改訂番号を入れる。新しく作るときは `0` を入れる。
- バックエンドは、要求の改訂番号が今の番号と同じときだけ保存し、1 増やした番号を応答に入れる。
- 違うときは保存せず、409 と `REVISION_CONFLICT` を返す。`details.currentRevision` に今の番号を入れる。
- 上書きを選んだ画面は、最新の内容を取得し直し、その改訂番号で保存し直す。確かめずに上書きする入口は作らない。
- 削除も同じ決まりにする。改訂番号はクエリの変数 `revision` で渡す。

### 4.11 OpenAPI の仕様

- 仕様は、Quarkus のコードから SmallRye OpenAPI で出力する。手で書かない。
- 置き場は `api/<サービス名>.yaml` とし、リポジトリにコミットする。
- 外に出す API(`/api`)だけを仕様に含める。`/internal` は別の仕様 `api/<サービス名>-internal.yaml` に分ける。画面側の型に、使わない API が混ざらないようにするためである。
- 操作の名前(`operationId`)は、動詞と名詞を camelCase で書く。例: `saveRecipeEdit`。画面側の関数の名前になる。
- エラーの形は `ErrorResponse` という名前の型にし、3 つのサービスで同じ定義にする。
- 入力の制約(必須、長さ、範囲)は、Bean Validation の注釈から仕様に出す。
- 入口を足すか変えたら、同じ作業の中で仕様を出力し直してコミットする。
- CI は、コードから出力した仕様とコミットされた仕様を比べ、違っていれば失敗する。

### 4.12 API の版

パスに版の番号(`/v1`)を入れない。
画面とサービスを同じリポジトリから一緒に配置するので、古い画面が新しい API を呼ぶ期間がないためである。
項目を消すか意味を変えるときは、画面側の修正を同じ作業に含める。

## 5. データ

なし。
テーブルの決まりは「共通設計: データベースの共通仕様」に書く。
改訂番号の列だけは、4.10 に合わせて整数で持つ。

## 6. サービスの間のやり取り

`/internal` の API も、この仕様書の決まりに従う。
違いは次の 2 点である。

- 入口から届かない。届かなくする方法は「共通設計: 実行環境」に書く。
- 呼ぶ側は、相手の `message` を利用者へそのまま返さない。自分の `code` と `message` に置き換える。

相手が応答しないときは 503 と `DEPENDENCY_UNAVAILABLE` を返す。

## 7. 受け入れ条件

どのサービスにも当てはまる条件である。
サービスごとに、同じ内容のテストを持つ。

| 識別子 | 条件 |
|---|---|
| `AC-API-01` | ないパスを呼ぶと 404 が返り、本文が `{ code: "NOT_FOUND", message, details: null }` の形である |
| `AC-API-02` | JSON として読めない本文を送ると 400 と `VALIDATION_FAILED` が返る |
| `AC-API-03` | 入力に知らない項目を 1 つ足して送ると 400 が返り、`fields` にその項目の `path` と `UNKNOWN_FIELD` が入っている |
| `AC-API-04` | 必須の項目を 2 つ欠いた入力を送ると、`fields` に 2 件が入っている |
| `AC-API-05` | 65KB の本文を送ると 413 と `PAYLOAD_TOO_LARGE` が返る |
| `AC-API-06` | 処理の中で想定していない例外が起きると 500 と `INTERNAL_ERROR` が返り、本文に例外の名前とスタックトレースが含まれない |
| `AC-API-07` | 応答の日時が `YYYY-MM-DDThh:mm:ssZ` の形である |
| `AC-API-08` | 一覧の応答が `{ "items": [...], "nextCursor": ... }` の形である。0 件のときは `items` が空の配列で、`nextCursor` が `null` である |
| `AC-API-09` | 改訂番号 `0` で新しく保存すると、応答の改訂番号が `1` である |
| `AC-API-10` | 古い改訂番号で保存すると 409 と `REVISION_CONFLICT` が返り、`details.currentRevision` が今の番号で、保存されている内容が変わらない |
| `AC-API-11` | コードから出力した仕様が、コミットされた `api/<サービス名>.yaml` と一致する |
| `AC-API-12` | 45 件あるものを `limit=20` で取ると、20 件、20 件、5 件の順に返り、3 回目の `nextCursor` が `null` である。3 回の結果を合わせると 45 件で、重複がない |
| `AC-API-13` | `limit` を付けずに呼ぶと、20 件までが返る |
| `AC-API-14` | `limit=0`、`limit=101`、読めない `cursor` のそれぞれで、400 と `VALIDATION_FAILED` が返る |
| `AC-API-15` | 1 回目を取った後に、まだ返していない位置へ 1 件を足し、すでに返した 1 件を消す。続きを最後まで取ると、足した 1 件が含まれ、すでに返したものが 2 回出ない |
