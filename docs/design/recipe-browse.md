# 機能設計: レシピ一覧と詳細

対応する Issue: #9

## 1. 目的

利用者が、レシピを料理名や材料やジャンルから探し、選んだレシピの材料と手順を、作る人数に合わせた分量で読めるようにする。
ログインしていなくても使える。
ログインしている人には、今開いているレシピ帳の編集内容を重ねた結果を見せる。

## 2. 範囲

やること:

- レシピ一覧(`/`)とレシピ詳細(`/recipes/<slug>`)の、表示する項目、文言、操作、状態
- 検索の正規化の決まりと、検索の対象にする項目
- ジャンルの絞り込みと、検索の語と、URL の対応
- 一覧の並び順
- 人数の換算と、分量の表記の丸め方
- 材料のチェックと、手順の「済」の印
- 編集済みの印と、編集後と元のレシピの切り替えの、出す条件と置き場
- 栄養の値の枠、「編集する」、「献立に追加」の置き場
- 写真の大きさの作り分け
- 今の静的なレシピ集(`recipes/`)から引き継ぐ動きと、変える動き

やらないこと:

- 栄養の値の計算と、枠の中身(成分の並び、桁、「概算値」、除いた材料の一覧、出典表記)。「機能設計: 栄養計算」(#10)が決める。この文書は、枠を置く場所と、枠に渡すものを決める
- 編集内容を元のレシピに重ねる処理と、編集内容の形。「機能設計: レシピ帳とレシピの編集」(#12)が決める。この文書は、重ねた結果を、いつ、どこに表示するかを決める
- 「元のレシピが更新されています」の知らせの条件と文。#12 が決める。この文書は、置き場だけを決める
- 「献立に追加」の動きと文言、一覧の下に固定する献立の枠の中身。「機能設計: 今日の献立」(#13)が決める。この文書は、置き場だけを決める
- 元のレシピの JSON の形と、ブラウザへ渡す形。[データ設計](data-recipe.md) が決めている
- ヘッダー、フッター、色、部品、API が失敗したときの共通の動き。[画面の共通仕様](common-frontend.md) が決めている
- 印刷用の見た目(P1)

### この文書で使う言葉

| 言葉 | 意味 |
|---|---|
| 元のレシピ | Claude Code が作り、`data/recipes/` に置く 1 品分の JSON。ビルドのときにページへ組み込む |
| 編集内容 | 利用者がレシピ帳の中で元のレシピを直した内容。`kitchen-service` が持つ |
| 重ねる | 元のレシピに編集内容を当てはめて、表示する 1 つのレシピを作ること。ブラウザで行う |
| 表示するレシピ | 画面に今出しているレシピ。元のレシピか、編集内容を重ねた結果のどちらかである |
| レシピの要約 | 一覧のカードと検索に使う、1 品分の小さいデータ(データ設計の 5.7) |
| 検索用の文字列 | レシピ 1 品の、検索の対象にする項目をつなげて正規化した文字列。ビルドのときに作る |
| 正規化 | 表記のゆれをそろえる変換。カタカナとひらがな、全角と半角、大文字と小文字を同じ文字にする |
| 検索の語 | 検索の欄に入れた文字列を、空白で区切った 1 つずつ |
| 基本の人数 | レシピの分量が何人分で書かれているかの数(`servings`)。元のレシピでは 2 で、編集で変えられる |
| 表示の人数 | レシピ詳細で、利用者が切り替える人数。分量の表示だけを変える |
| 倍率 | 表示の人数 ÷ 基本の人数 |
| 換算する | 分量に倍率を掛けること。丸めない |
| 丸め方 | 換算した分量を、読みやすい数にする決まり。5 刻み(10 未満では 1 刻み)、分数、整数の 3 通りがある |
| ヒーローの写真 | レシピを代表する 1 枚(`role` が `hero`)。一覧のカードと、詳細の最初に出す |
| 小さい版 | 元の写真を、決まった幅に縮めて作ったファイル |
| 四捨五入 | 丸める桁の 1 つ下が 5 以上なら切り上げ、4 以下なら切り捨てる丸め方 |

## 3. 画面

どちらの画面も、ログインが要らない。
元のレシピは、ビルドのときにページへ組み込んであるので、API が 1 つも応答しなくても表示できる(要件定義の 5 章「サービスの独立」)。
ログインの状態を待たずに、本文を出す([画面の一覧と遷移](screens.md) の 3.1)。

骨組み(どこに何を置くか)は、画面の一覧と遷移の 3.8 が決めている。
この章は、それを詳しくする。

### 3.1 レシピ一覧(`/`)

#### 表示する項目

上から次の順に置く。

| 順 | 項目 | 内容 |
|---|---|---|
| 1 | 題 | `<h1>` で「おうちレシピ帖」。その下に「いつものごはん」 |
| 2 | 検索の欄 | 下の「検索の欄」のとおり |
| 3 | ジャンルの絞り込み | 下の「ジャンルの絞り込み」のとおり |
| 4 | 件数 | 下の「件数と、該当がないとき」のとおり |
| 5 | カードの並び | 条件に合うレシピのカード。並び順は 5.5 |
| 6 | 献立の枠 | 画面の下に固定する。中身と出す条件は #13 が決める |

今の静的なレシピ集の題の下にある「今日の献立を見る」のリンクは、置かない。
ヘッダーの「今日の献立」が引き継ぐ(画面の一覧と遷移の 3.8)。

#### カード

カード 1 枚は、レシピ 1 品を表す。
使うデータは、レシピの要約である。

| 項目 | 内容 | 例 |
|---|---|---|
| 写真 | ヒーローの写真。幅と高さの比を 3 対 2 にして、はみ出す分を切る。代替の説明は、写真の `alt` を使う | |
| 料理名 | `<h2>`。アレンジ版は、5.8 の形に組み立てた名前 | 「親子丼」「親子丼(鶏むね肉でさっぱり)」 |
| アレンジ版の印 | `arrangeLabel` があるレシピにだけ、料理名の後ろに `Badge`(緑)で「アレンジ」 | |
| 編集済みの印 | 下の「ログインしている人に足すもの」の条件で、`Badge`(朱)で「編集済み」 | |
| 分類 | `genres` の 2 件目 | 「丼もの」 |
| 調理時間 | `time` に「分」を付ける | 「20分」 |
| 「献立に追加」 | 置き場だけを決める。下の「ログインしている人に足すもの」のとおり | |

- 写真、料理名、印、分類、調理時間の全体を、レシピ詳細(`/recipes/<slug>`)への 1 つのリンクにする。リンクの名前(読み上げソフトが読む名前)は、料理名にする(画面の共通仕様の 3.6)。
- 「献立に追加」は、リンクの中に入れず、リンクの下に並べる。リンクの中にボタンを入れると、キーボードと読み上げソフトで、どちらを押したのかが分からなくなるためである。
- カードは、幅に入る数だけ横に並べる。1 枚の幅は 260px 以上とし、余った幅を等しく分ける。幅 360px で 1 列、内容の幅が 1,080px のときに 3 列になる。今の静的なレシピ集と同じ並べ方である。
- カードに触れたときは、影を一段濃くする。位置は動かさない(画面の共通仕様の 3.6)。今の静的なレシピ集は、カードを 4px 上へ動かしている。
- 今の静的なレシピ集は、調理時間の後ろに「2人分」を出している。これは出さない。要件定義の 4.1 が挙げる項目(写真、料理名、分類、調理時間)になく、レシピの要約にも基本の人数がないためである。
- 最後のカードが、画面の下の献立の枠に隠れないように、カードの並びの下に余白を取る。余白の大きさは、献立の枠の高さに合わせて #13 の実装のときに決める。

#### 検索の欄

| 項目 | 内容 |
|---|---|
| 見出し(`<label>`) | 「レシピを探す」 |
| 欄の中の薄い文字 | 「料理名や材料で探す(例: 鶏もも肉、丼、はんばーぐ)」 |
| 種類 | `type="search"`。`autocomplete="off"` |
| 長さ | 100 文字まで(`maxlength="100"`) |
| 形 | `rounded-full`(画面の共通仕様の 3.3) |

- 入力のたびに、待たずに絞り込む。送信のボタンは置かない。
- 検索の対象と、正規化の決まりは、5.1 から 5.3 に書く。
- 欄を空にすると、検索の条件がなくなる。空白だけの入力も、空と同じに扱う。

#### ジャンルの絞り込み

- `Chip`(絞り込みの印)を横に並べ、幅に入らない分は折り返す。全体を `<nav aria-label="ジャンルで絞り込む">` で包む。
- 最初に「すべて」を置き、その後ろに、レシピに付いているジャンルを 5.4 の順で並べる。
- 選べるのは 1 つだけである。選んである `Chip` には `aria-pressed="true"` を付け、地を `washi-deep` にして、枠を太くする。色だけで示さない。
- 「すべて」を選ぶと、ジャンルの条件がなくなる。
- 選んであるジャンルをもう一度押しても、何も変わらない。外すときは「すべて」を押す。今の静的なレシピ集と同じ動きである。

#### 検索とジャンルの組み合わせ

検索とジャンルは、両方を満たすレシピだけを残す(要件定義の 4.1)。
どちらかを変えても、もう片方の条件は残る。

例(5.3 のテスト用のデータで):

| ジャンル | 検索の欄 | 残るレシピ | 件数の表示 |
|---|---|---|---|
| すべて | 空 | 5 品すべて | 「5品」 |
| 和食 | 空 | 親子丼、親子丼(鶏むね肉でさっぱり)、ひじきの煮物 | 「5品中 3品」 |
| 和食 | 「卵」 | 親子丼、親子丼(鶏むね肉でさっぱり) | 「5品中 2品」 |
| 副菜 | 「卵」 | なし | 「条件に合うレシピがありません」 |
| すべて | 「カレー」 | なし | 「条件に合うレシピがありません」 |

#### 件数と、該当がないとき

件数は、ジャンルの絞り込みとカードの並びの間に、`role="status"` を付けて出す。
絞り込みの結果が変わったことを、読み上げソフトに伝えるためである(画面の共通仕様の 3.11)。

| 場合 | 表示 |
|---|---|
| 条件がない。または、条件があっても全部が残った | 「38品」 |
| 一部が残った | 「38品中 5品」 |
| 1 品も残らなかった | 件数の場所には何も出さず、カードの並びの場所に `EmptyState` を出す |

該当がないときの `EmptyState` は、次のとおりとする。

- 文は「条件に合うレシピがありません」とする。
- 「条件を消す」のボタンを 1 つ置く。押すと、検索の欄を空にし、ジャンルを「すべて」にする。
- `EmptyState` に `role="status"` を付ける。

今の静的なレシピ集は、該当がないときに、件数の場所に文だけを出している。
ボタンを足すのは、画面の共通仕様の 3.7 が、空の表示に、次にできる操作を置くと決めているためである。

元のレシピが 1 品もないとき(`data/recipes/` が空)は、検索の欄とジャンルの絞り込みを出さず、「レシピがまだありません」と出す。

#### URL との対応

選んだジャンルと、検索の語を、URL のクエリに残す。
再読み込みしても、レシピ詳細からブラウザの「戻る」で戻っても、同じ絞り込みで表示するためである。
ジャンルは、画面の一覧と遷移の 3.2 が決めている。
検索の語は、この文書で決めた。
理由は [決定の記録 0041](../decisions/0041-search-term-in-query.md) に書いた。

| 名前 | 値 | ないとき | 形が誤っているとき |
|---|---|---|---|
| `genre` | ジャンルの名前。例: `副菜` | 「すべて」を選んだ状態 | レシピに付いていないジャンルは、ないものとして扱う |
| `q` | 検索の欄に入れた文字列。正規化する前のもの。例: `鶏もも肉 卵` | 検索の欄は空 | 100 文字を超える分は、切り捨てて使う |

- 例: ジャンル「副菜」を選び、「にんじん」と入れると、URL は `/?genre=副菜&q=にんじん` になる。アドレスの欄には、日本語のまま見えるか、`%E5%89%AF...` の形に変換されて見える。どちらになるかは、ブラウザによる。
- クエリの並びは、`genre`、`q` の順にする。ないものは書かない。どちらもないときの URL は `/` である。
- URL を書き換えるときは、ブラウザの履歴に積まず、今の項目を置き換える(画面の一覧と遷移の 3.2)。絞り込みを何度変えても、「戻る」1 回で、一覧に来る前の画面に戻れるようにするためである。
- `genre` は、押したときにすぐ書き換える。`q` は、入力が止まって 0.3 秒たってから書き換える。1 文字ごとに書き換えると、ブラウザが、短い時間に多すぎる書き換えを拒むことがあるためである。0.3 秒は見込みで置いた(8 章)。カードの絞り込みは、URL を待たずに、入力のたびに行う。
- ページを開いたときと、ブラウザの「戻る」「進む」で URL が変わったときは、URL の `genre` と `q` を読み、絞り込みの印と検索の欄に入れる。
- 知らない `genre` で開いたときは、「すべて」を選んだ状態にする。URL は、利用者が次に操作するまで書き換えない。
- クエリの値は、利用者が書き換えられる。画面は、値を文字として検索の欄に入れ、絞り込みに使うだけで、HTML として解釈しない。

#### 最初の表示

ビルドで書き出す HTML には、すべてのレシピのカードを、5.5 の順で入れておく。
絞り込みの印は「すべて」を選んだ状態、件数は全品の数、検索の欄は空にしておく。

`/?genre=副菜` のように、クエリを付けて開いたときは、すべてのカードが一度見えてから、絞り込んだ結果に変わる。
この見え方を許す。
理由は次のとおりである。

- 静的な HTML は、クエリの値を知らずに作られる。絞り込みが決まるまでカードを隠すと、クエリを付けずに開いた人(いちばん多い開き方)にも、カードが出るのが遅れる。
- JavaScript を切っているブラウザでも、一覧を読めるようにしておく(画面の一覧と遷移の 3.7)。

JavaScript を切っているブラウザでは、検索の欄とジャンルの絞り込みは働かない。
検索の欄の下に、`<noscript>` で「検索と絞り込みには、JavaScript が必要です」と出す。

#### ログインしている人に足すもの

次の 3 つは、ログインしていて、今開いているレシピ帳と役割が分かってから出す。
出す条件は、画面の一覧と遷移の 3.4 の表が決めている。

| 足すもの | 出す人 | この文書が決めること |
|---|---|---|
| 編集済みの印 | 見るだけの人、編集できる人、持ち主 | 条件、置き場、失敗したときの動き |
| 「献立に追加」 | 編集できる人、持ち主、ログインしていない人 | 置き場だけ。カードのリンクの下に、カードの幅いっぱいのボタンを置く。文言、押したときの動き、状態は #13 が決める |
| 画面の下の献立の枠 | 見るだけの人、編集できる人、持ち主 | 置き場だけ。画面の下に固定する。中身と、出す条件の細部は #13 が決める |

編集済みの印の決まりは、次のとおりとする。

- 今開いているレシピ帳の、編集済みのレシピの一覧(`GET /api/books/{bookId}/recipe-edits`)を、全件取る(画面の共通仕様の 4.8)。
- 返ってきた `slug` と同じレシピのカードに、「編集済み」の印を出す。元のレシピにない `slug` は、無視する。元のレシピが消された後に、編集内容だけが残っている場合である。
- カードの料理名、写真、分類、調理時間は、編集内容があっても変わらない。これらは編集の対象でないためである(要件定義の 4.5)。
- **検索は、元のレシピの内容だけを対象にする。** 編集で足した材料の名前では、見つからない。編集内容で検索するには、すべての編集内容の本体を取る必要があり、一覧を開くたびの通信が増えるためである。例: 親子丼に、編集で「しめじ」を足しても、「しめじ」で検索して親子丼は出ない。
- レシピ帳を切り替えたら、新しいレシピ帳の一覧を取り直し、印を付け直す。
- ログアウトしたら、印を消す。

#### 状態

| 状態 | 入る条件 | 出すもの |
|---|---|---|
| 表示できた | いつも | カードの並び。元のレシピは読み込み中にならない |
| 空 | 条件に合うレシピがない | 上の「件数と、該当がないとき」の `EmptyState` |
| 印を読み込み中 | 編集済みのレシピの一覧を取っている | カードは、印のない形で出しておく。骨組みの表示は出さない。印は 1 行に収まる短い語で、後から足しても、カードの大きさが変わらないためである |
| 印を読み込めない | 一覧の取得が、やり直しても失敗した(画面の共通仕様の 4.6) | 件数の上に、`Notice`(注意)で「編集済みの印を読み込めませんでした」と「もう一度」のボタン。該当するときは問い合わせ番号。カード、検索、絞り込みは、そのまま働く |
| ログインが切れた | 一覧の取得が 401 と `UNAUTHENTICATED` を返した | ログインしていない人の表示に切り替える。エラーは出さない(画面の共通仕様の 4.4) |
| 保存中 | なし | この画面は、保存をしない |

### 3.2 レシピ詳細(`/recipes/<slug>`)

元のレシピにない `slug` のパスは、ビルドでファイルを作らないので、見つからないページになる(画面の一覧と遷移の 3.7)。

#### 表示する項目

上から次の順に置く。
「元」は、いつも元のレシピの値を出す項目である。
「表示」は、表示するレシピ(元のレシピか、編集内容を重ねた結果)の値を出す項目である。

| 順 | 項目 | 元か表示か | 内容 |
|---|---|---|---|
| 1 | 「レシピ一覧へ」 | | `/` へのリンク。いちばん下にも置く |
| 2 | ヒーロー | 元 | 下の「ヒーロー」のとおり |
| 3 | アレンジの内容 | 元 | アレンジ版にだけ出す。下の「アレンジ版」のとおり |
| 4 | 操作の並び | | 「編集する」、「献立に追加」、編集後と元のレシピの切り替え。下の「操作の並び」のとおり |
| 5 | 知らせ | | 編集内容に関わる知らせ。下の「編集内容の表示」のとおり |
| 6 | 基本情報 | 元 | 調理時間、難易度、道具 |
| 7 | 栄養の値の枠 | 表示 | 下の「栄養の値の枠」のとおり |
| 8 | 材料 | 表示 | 下の「材料と人数」のとおり |
| 9 | 作り方 | 表示 | 下の「作り方」のとおり |
| 10 | コツ | 表示 | 見出しは「おいしく作るコツ」。箇条書き。1 件もないときは、見出しごと出さない |
| 11 | 盛り付けの参考 | 元 | `role` が `gallery` の写真。下の「写真」のとおり |
| 12 | 写真の出典 | 元 | 下の「写真」のとおり |

#### アレンジ版

`arrangeLabel` があるレシピにだけ、ヒーローのすぐ下に、アレンジの内容の枠を出す。

#### 操作の並び

ヒーロー(アレンジ版では、アレンジの内容)のすぐ下に、次のものを横に並べる。
長い手順を読み終える前に、見つけられるようにするためである(画面の一覧と遷移の 3.8)。

ログインしていない人には、「編集する」と「献立に追加」を出す。押すと、ログインの画面へ移る(画面の一覧と遷移の 3.4)。

出すものが 1 つもないとき(見るだけの人で、編集内容がないレシピ)は、並びごと出さない。
役割で出し分けるものは、役割が分かるまで出さない(画面の一覧と遷移の 3.4)。

#### 編集内容の表示

ログインしていて、今開いているレシピ帳にこのレシピの編集内容があるときは、編集内容を重ねた結果を表示する(要件定義の 4.2)。
この文書は、いつ、どこに表示するかを決める。
重ねる処理は、#12 が決める。

流れは次のとおりである。

1. ページを開くと、ログインの状態を待たずに、元のレシピを表示する。
2. ログインしていて、今開いているレシピ帳が分かったら、編集内容を取る(`GET /api/books/{bookId}/recipe-edits/{slug}`)。
3. 404 が返ったら、編集内容はない。元のレシピを表示したままにし、切り替えを出さない。
4. 200 が返ったら、#12 の重ねる処理に、元のレシピと編集内容を渡し、返ってきたレシピを表示する。切り替えを、「編集後」を選んだ状態で出す。

元のレシピを先に表示するのは、ログインしていない人と、API が応答しないときに、待たせないためである。
その代わり、ログインしている人には、材料の分量が、開いた後に変わって見えることがある。
変わったことが分かるように、手順 4 のときに、切り替えの下に、次の文を `role="status"` で出す。

> 「<レシピ帳の名前>」の編集内容を表示しています

例: 「「わが家のレシピ帳」の編集内容を表示しています」

レシピ帳の名前を出すのは、幅 820px 未満では、レシピ帳の切り替えがヘッダーの「メニュー」の中に隠れ、どのレシピ帳の編集内容なのかが見えないためである。

切り替えの決まりは、次のとおりとする。

- `Chip` は「編集後」「元のレシピ」の順に並べ、全体を `role="group"` と `aria-label="表示する内容"` で包む。選んであるほうに `aria-pressed="true"` を付ける。
- 「元のレシピ」を選ぶと、材料、作り方、コツ、基本の人数、栄養の値を、元のレシピのものに替える。上の文は、「元のレシピを表示しています」に替える。
- 選んだ側は、URL にも、ブラウザの保存領域にも残さない。再読み込みすると、「編集後」に戻る。保存してある内容を見せるのが、この画面の基本だからである。
- 切り替えても、ページの上の位置(スクロール)を変えない。
- レシピ帳を切り替えたら、新しいレシピ帳の編集内容を取り直し、「編集後」を選んだ状態に戻す。新しいレシピ帳に編集内容がなければ、元のレシピを表示し、切り替えを消す。
- ログアウトしたら、元のレシピを表示し、切り替えを消す。

表示するレシピが替わったとき(編集内容が届いた、切り替えを押した、レシピ帳を切り替えた)の、ほかの状態の扱いは、次のとおりとする。

| 状態 | 扱い |
|---|---|
| 表示の人数 | 利用者が人数のボタンを一度も押していなければ、新しく表示するレシピの基本の人数にする。押していれば、選んだ人数のままにする |
| 材料のチェック | 材料の `id` で持つ。新しく表示するレシピに同じ `id` の材料があれば、チェックを残す |
| 手順の「済」 | 手順の `id` で持つ。新しく表示するレシピに同じ `id` の手順があれば、印を残す |

知らせの置き場には、次のものを出す。

| 知らせ | 条件と文 |
|---|---|
| 元のレシピが更新されています | #12 が決める。この文書は、操作の並びのすぐ下に `Notice` で出す、という置き場だけを決める |
| 編集内容を読み込めない | 下の「状態」のとおり |

#### 栄養の値の枠

栄養の値は、基本情報のすぐ下、材料の上に出す。
枠の部品(`NutritionSummary`)と、中身(成分の並び、桁、「概算値」の印、除いた材料の一覧、「栄養値は未算出」、出典表記)は、#10 が決める。
この文書は、置き場と、渡すものを決める。

| 項目 | 内容 |
|---|---|
| 見出し | 「栄養(1 人分)」 |

#### 材料と人数

見出し(`<h2>`)は「材料」とする。
その下に、人数の切り替え、材料のグループの順に置く。

人数の切り替えは、次のとおりとする。

| 項目 | 内容 |
|---|---|
| 並び | 「−」のボタン、「2人分」、「＋」のボタン |

| 人数の表示 | 数を太い文字で出し、「人分」を続ける。`aria-live="polite"` を付ける |
| 範囲 | 1 人から 6 人(要件定義の 4.2) |
| 最初の値 | 表示するレシピの基本の人数 |
| 端の動き | 1 人のときは「−」を、6 人のときは「＋」を、使えない状態にする |

材料のグループと材料は、次のとおりとする。

- グループごとに、名前(`ingredientGroups[].name`)を小見出しにし、その下に材料を並べる。例: 「具」「割下」
- 材料 1 件は、チェックの欄(`Checkbox`)、名前、分量を 1 行に並べる。名前を左、分量を右に寄せる。行の全体を `<label>` にして、どこを押してもチェックが付くようにする。
- 分量は、5.7 の決まりで作った文字列を出す。例: 「250g」「大さじ1と1/2」「1/2個」「適量」
- チェックを付けた材料は、名前と分量に取り消しの線を引き、文字を `ink-soft` にする。チェックの欄には「✓」が出る。色だけで示さない。
- チェックは、ページの中の状態としてだけ持つ。ページを閉じるか、再読み込みすると消える(要件定義の 4.2)。
- 表示の人数を変えても、チェックは残る。
- 材料の名前が長いときは、折り返す。分量は折り返さない。

見出し(`<h2>`)は「作り方」とする。
手順を、番号の付いた並び(`<ol>`)で出す。

| 項目 | 内容 | 例 |
|---|---|---|
| 番号 | 並び順の番号。1 から | |
| 見出し | `<h3>` で `title` | 「割下で玉ねぎを煮る」 |
| 本文 | `text` | |

「済」のボタンの決まりは、次のとおりとする。

- 手順ごとに、「済」と書いたボタンを置く。ボタンの名前は、`aria-label` で「手順 2 を済みにする」のように、番号を入れる。同じ名前のボタンが並んで、読み上げソフトで区別できなくなるのを防ぐためである。
- 押すと、その手順を済みにし、ボタンに `aria-pressed="true"` を付ける。もう一度押すと、戻る。
- 済みの手順は、番号を「✓」に替え、番号の地を `mitsuba` にし、見出しと本文の文字を `ink-soft` にする。
- 今の静的なレシピ集は、済みの手順の全体を、不透明度 45% で薄くしている。これは引き継がない。文字と地のコントラスト比が 4.5 を下回るためである(画面の共通仕様の 3.1)。`ink-soft` は、`paper` の地との比が 6.5 である。
- 印は、ページの中の状態としてだけ持つ。ページを閉じるか、再読み込みすると消える(要件定義の 4.2)。
- 手順の順に押す必要はない。どの手順も、いつでも済みにでき、戻せる。

#### 写真

盛り付けの参考(`role` が `gallery` の写真)は、次のとおりとする。

- 見出し(`<h2>`)は「盛り付けの参考」とする。
- 写真を、`photos` の並び順で出す。幅と高さの比を 3 対 2 にして、はみ出す分を切る。写真の下に、`caption` があれば出す。
- 幅 560px から 2 列にする。1 枚だけのときは、2 列の片側に寄せず、中央に置き、幅を 640px までにする。
- 1 枚もないときは、見出しごと出さない。今の 38 品に、1 品ある。
- 画面の外にある写真は、近づくまで読み込まない(画面の共通仕様の 3.6)。
- 今の静的なレシピ集は、写真を 1 度ずつ左右に傾けている。飾りなので、引き継ぐかどうかは、実装のときにスクリーンショットを見て決める(8 章)。

写真の出典は、次のとおりとする。

- 見出し(`<h2>`)は「写真の出典」とする。文字は `text-xs` にする。
- `photos` の並び順で、1 枚につき 1 行を出す。形は、データ設計の 5.9 が決めている。題名(出典のページへのリンク)、作者、ライセンス、取ってきた場所の順である。
- ライセンスに版(`licenseVersion`)があるときは、種類の後ろに、半角の空白をはさんで続ける。
- 例: 「Oyakodon 003(Ocdp 撮影、CC0、Wikimedia Commons)」
- 例: 「Niku jaga by yoppy(yoppy 撮影、CC BY 2.0、Wikimedia Commons)」
- 出典のページは、ほかのサイトである。リンクには `rel="noreferrer"` を付け、同じタブで開く。

「編集する」は、編集内容を読み込めないときも出す。
レシピの編集の画面は、自分で編集内容を取り直す。

JavaScript を切っているブラウザでは、元のレシピの材料(基本の人数の分量)、作り方、コツ、写真を読める。

### 3.3 写真の大きさ

元の写真は、長辺が 1280px の JPEG である(データ設計の 5.9)。
これをそのまま一覧のカードに使うと、38 枚で 9.3MB を読み込むことになる。
そこで、ビルドのときに、幅を縮めた小さい版を作る。
[画面の共通仕様](common-frontend.md) と [データ設計](data-recipe.md) が、この文書で決めるとしていた事柄である。
理由と却下した案は、[決定の記録 0042](../decisions/0042-resized-photos-at-build.md) に書いた。

| 項目 | 決まり |
|---|---|
| 作る時点 | 画面のビルドの前と、開発用のサーバーを起動する前 |
| 作る対象 | `frontend/public/photos/` にある、すべての写真 |
| 作る幅 | 480px と 960px の 2 つ。高さは、元の比のままにする |
| 形式 | JPEG。品質は 80 |
| 置き場 | `frontend/public/photos-resized/<slug>/<元の名前>-480.jpg` と `-960.jpg`。例: `photos-resized/oyakodon/hero-480.jpg` |
| Git | コミットしない。`.gitignore` に `frontend/public/photos-resized/` を書く |
| 元の写真 | 変えない。`frontend/public/photos/` のファイルは、1280px のまま配る |

- 置き場を `photos/` と分けるのは、データの検証(データ設計の CD-20)が、`photos/` に、どのレシピにもないファイルがあるとエラーにするためである。
- 元の写真の幅が、作る幅に満たないときは、拡大せず、元の幅のまま書き出す。今の 102 枚の幅は、945px から 1280px である。
- 元の写真が前に作ったときから変わっていなければ、作り直さない。開発用のサーバーを起動するたびに、102 枚を作り直さないためである。
- 作る処理は、`frontend/` の中のスクリプトとして置き、Docker のコンテナの中で動かす。ライブラリは sharp を使う見込みである(8 章)。

今の 102 枚を、この決まり(sharp 0.35.5、品質 80)で実際に縮めて、大きさを測った。

| 対象 | 元(1280px) | 幅 480px | 幅 960px |
|---|---|---|---|
| ヒーローの 38 枚 | 9.3MB | 1.2MB | 4.1MB |
| 全部の 102 枚 | 26MB | 3.2MB | 11MB |

画面は、写真を出す場所ごとに、次の版を使う。
ブラウザが、画面の幅と解像度に合う版を選べるように、`srcset` と `sizes` を書く。

| 場所 | 候補にする版 | 読み込み |
|---|---|---|
| 一覧のカード | 480px、960px | 画面の外にあるものは、近づくまで読み込まない |

### 5.1 検索の正規化

検索では、カタカナとひらがな、全角と半角、大文字と小文字を区別しない(要件定義の 4.1)。
そのために、検索用の文字列と、検索の欄に入れた文字列の両方を、同じ関数で正規化してから比べる。
片方だけを正規化したり、2 か所に別々の処理を書いたりすると、見つかるはずのレシピが見つからなくなるためである。

正規化は、次の 3 つを、この順で行う。

| 順 | 変換 | そろうもの | 例 |
|---|---|---|---|
| 1 | Unicode の正規化(NFKC) | 全角の英数字と半角の英数字。半角のカタカナと全角のカタカナ。全角の空白と半角の空白 | 「ＣＨＩＣＫＥＮ」は「CHICKEN」に、「ﾊﾝﾊﾞｰｸﾞ」は「ハンバーグ」になる |
| 2 | 英字を小文字にする | 大文字と小文字 | 「CHICKEN」は「chicken」になる |
| 3 | カタカナ(「ァ」から「ヶ」まで)を、同じ音のひらがなにする | カタカナとひらがな | 「ハンバーグ」は「はんばーぐ」になる |

入力と、正規化した結果の例は、次のとおりである。
コンテナの中の Node.js で、実際に変換して確かめた。

| 入力 | 結果 |
|---|---|
| 「ハンバーグ」 | 「はんばーぐ」 |
| 「はんばーぐ」 | 「はんばーぐ」 |
| 「ﾊﾝﾊﾞｰｸﾞ」(半角のカタカナ) | 「はんばーぐ」 |
| 「ＣＨＩＣＫＥＮ」(全角の英字) | 「chicken」 |
| 「Chicken」 | 「chicken」 |
| 「鶏モモ肉」 | 「鶏もも肉」 |
| 「鶏もも肉　丼」(間は全角の空白) | 「鶏もも肉 丼」(間は半角の空白) |
| 「ヴィネガー」 | 「ゔぃねがー」 |

- 長音の記号「ー」は、変えない。カタカナでもひらがなでも、同じ文字を使うためである。
- 変換は、端末の言語の設定に左右されない方法で行う。どの端末でも、同じ結果にするためである。

次のゆれは、そろえない。
そろえる決まりを足すと、関係のないレシピまで見つかるようになるためである。

| そろえないもの | 例 | 補う方法 |
|---|---|---|
| 漢字と、その読み | 「鶏」と「とり」 | 料理名は、読み(`reading`)が検索の対象に入っている。食材は、食材マスタの `aliases` に、ひらがなの別名を書く |
| 送り仮名と、漢字の使い方 | 「玉ねぎ」と「玉葱」と「たまねぎ」 | 食材マスタの `aliases` に書く |
| 濁点と半濁点の有無 | 「はんばーく」と「はんばーぐ」 | 補わない |
| 長音の書き方 | 「こーひー」と「こうひい」 | 補わない |

### 5.2 検索用の文字列

検索用の文字列は、レシピ 1 品につき 1 つ、ビルドのときに作る(データ設計の 5.7)。
ブラウザが、開くたびに作り直さなくて済むようにするためである。

次の項目を、この順に、半角の空白でつなげてから、5.1 の正規化をする。

| 順 | 項目 | 親子丼での値 |
|---|---|---|
| 1 | 料理名(`name`) | 親子丼 |
| 2 | アレンジ版の変更点の名前(`arrangeLabel`)。あるときだけ | なし |
| 3 | 読み(`reading`) | おやこどん |
| 4 | ジャンル(`genres`)の 2 件 | 和食、丼もの |
| 5 | すべての材料の、表示する名前(`name`) | 鶏もも肉、玉ねぎ、卵、三つ葉、温かいご飯、水、ほんだし、醤油、みりん、砂糖 |
| 6 | `ingredientId` がある材料について、食材マスタのその食材の `name` と `aliases` | 鶏もも肉、とりもも肉、鶏モモ肉、顆粒和風だし、ほんだし、ほか |

- 項目の間を空白でつなぐのは、2 つの項目にまたがって語が見つかるのを防ぐためである。検索の語は空白を含まないので、空白をまたいでは一致しない。例: 料理名の終わりの「丼」と、読みの初めの「お」をつなげた「丼お」では、見つからない。
- 食材マスタの `name` と `aliases` を入れるのは、レシピでの表示が商品名や略した名前でも、一般の名前で見つかるようにするためである。例: 材料の名前が「ほんだし」のレシピが、「顆粒和風だし」でも見つかる。
- `arrangeLabel` を入れるのは、今の静的なレシピ集が、アレンジ版を、変更点まで入れた名前で検索できるようにしているためである。データ設計の 5.7 の並びに、この項目を足した。
- 紹介(`description`)、リード文、道具、手順、コツは、対象にしない。要件定義の 4.1 が、対象を料理名、読み、材料名、ジャンルと決めているためである。
- 同じ語が何度入っていても、結果は変わらない。重なりを除くかどうかは、実装で決めてよい。

### 5.4 ジャンルの一覧

絞り込みの印に並べるジャンルは、レシピに付いている値から作る(要件定義の 4.1)。

- すべてのレシピの `genres` に 1 回以上出てくる値だけを並べる。どのレシピにも付いていないジャンルは、押しても 1 品も残らないので、出さない。
- 並び順は、データ設計の 5.2 の「ジャンルの値」の表の順とする。先に系統(和食、韓国風、中華、洋食)、次に種類(丼もの、ご飯もの、麺、煮物、汁物、炒め物、炒め煮、焼き物、揚げ物、卵料理、副菜)である。
- 今の静的なレシピ集は、目録に出てきた順に並べている。順を変えるのは、レシピを足すたびに、ボタンの並びが変わるのを防ぐためである。
- 例: 5.3 のテスト用のデータでは、「和食」「洋食」「丼もの」「焼き物」「揚げ物」「副菜」の順になる。その前に「すべて」が付く。

### 5.5 並び順

一覧のカードは、読み(`reading`)の順に並べる。
読みが同じレシピは、`slug` の順に並べる。

- 元のレシピは 1 品 1 ファイルで、並び順を持つ項目がない。そこで、データから決まる順にする。今の静的なレシピ集は、目録に書いた順(足した順)に並べている。
- 読みの順にすると、アレンジ版が、同じ読みを持つ元のレシピのすぐ後ろに並ぶ。
- 文字の比べ方は、文字コードの順とする。ひらがなは、文字コードの順が、ほぼ五十音の順になる。端末やビルドの環境の言語の設定で順が変わる比べ方(`localeCompare`)は、使わない。
- 並べ替えは、ビルドのときに行う。レシピの要約の一覧を、この順で作る。
- 例: 5.3 のテスト用のデータは、親子丼、親子丼(鶏むね肉でさっぱり)、チキン南蛮、ハンバーグ、ひじきの煮物の順になる。

- 表示の人数は、1 から 6 の整数である。
- 基本の人数は、元のレシピでは 2 である(データ設計の 5.2)。編集で変えられる(要件定義の 4.5)ので、関数は 2 と決めつけない。
- 基本の人数が 1 から 6 の範囲にあることを、前提にする。#12 が、編集での基本の人数の入力を、この範囲にすることを期待する(6 章)。範囲の外の値が来たときは、表示の人数の最初の値を基本の人数にし、切り替えの範囲を、基本の人数まで広げる。例: 基本の人数が 8 なら、1 から 8 人で切り替えられる。最初から換算した分量が出て、書いた値と違って見えるのを防ぐためである。

### 5.7 分量の表記

分量の表記の関数は、材料 1 件、基本の人数、表示の人数、その材料の食材(食材マスタの 1 件。ないこともある)を受け取り、画面に出す文字列を返す。

#### 全体の決まり

| 場合 | 表記 | 例 |
|---|---|---|
| `note` を持つ材料 | `note` をそのまま出す。人数を変えても変わらない | 「適量」「少々」「好みで」「ひとつまみ」 |
| 表示の人数が、基本の人数と同じ | 書いてある分量を、丸めずに出す。下の「基本の人数のとき」のとおり | 「250g」「大さじ1/3」 |
| 表示の人数が、基本の人数と違う | 換算した値を、丸め方に従って丸めて出す。下の「換算したとき」のとおり | 「375g」「大さじ1と1/2」 |

丸めるのは、換算したときだけにする。
理由は、書いてある値を丸めると、利用者が編集で入れた値と、詳細に出る値が食い違うためである。
例: 編集で塩を 3g にしたレシピを、基本の人数のまま開いたときに、5 刻みで丸めると「5g」と出る。
今の 38 品では、基本の人数での表記は、今の静的なレシピ集と同じになる。
理由と却下した案は、[決定の記録 0040](../decisions/0040-round-only-when-scaled.md) に書いた。

数と単位の並べ方は、データ設計の 5.3 の表の「表記の位置」に従う。

- `大さじ`、`小さじ`、`カップ` は、単位を数の前に書く。例: 「大さじ2」「カップ1/2」
- そのほかの単位は、数の後ろに書く。例: 「250g」「1/2個」「2切れ」
- 数と単位の間に、空白を入れない。
- 整数の部分が 4 桁以上のときは、3 桁ごとに半角のコンマを入れる(画面の共通仕様の 3.12)。例: 「1,200g」

#### 丸め方の決め方

丸め方は、単位と食材マスタから決まる(データ設計の 5.3、決定の記録 0027)。

| 順 | 条件 | 丸め方 |
|---|---|---|
| 1 | 単位が `g` か `ml` | 5 刻み。換算した値が 10 未満のときは 1 刻み |
| 2 | 単位が、その材料の食材の `wholeUnits` に入っている | 整数 |
| 3 | そのほか | 分数 |

- 食材マスタにない材料(`ingredientId` がない)と、食材マスタから消えた食材を指す材料は、2 に当たらないので、分数になる。
- 例: 卵(`wholeUnits` が `["個"]`)の「個」は整数、玉ねぎの「個」は分数、醤油の「大さじ」は分数、鶏もも肉の「g」は 5 刻みである。

#### 換算したとき

| 丸め方 | 決まり | 例(基本の人数は 2) |
|---|---|---|
| 5 刻み | 換算した値が 10 以上のときは、5 で割り、四捨五入して、5 を掛ける。10 未満のときは、1 刻みで四捨五入する。結果が 1 より小さいときは 1 にする | 250g を 4 人分で「500g」、3 人分で「375g」、1 人分で「125g」。15g を 1 人分で「8g」(7.5 を 1 刻みで丸める)。10g を 1 人分で「5g」。塩 2g を 1 人分で「1g」、3 人分で「3g」。19g を 1 人分で「10g」(9.5 を 1 刻みで丸める) |
| 整数 | 換算した値を四捨五入する。結果が 1 より小さいときは 1 にする | 卵 4 個を 3 人分で「6個」、1 人分で「2個」。卵 1 個を 3 人分で「2個」(1.5 を丸める)、1 人分で「1個」(0.5 を丸める) |
| 分数 | 下の「分数の決まり」のとおり | 大さじ 1 を 3 人分で「大さじ1と1/2」 |

どの丸め方も、0 にはしない。
材料がなくなったように見えるのを防ぐためである。

10 未満で 1 刻みにするのは、少ない分量を 5 刻みで丸めると、元の倍を超える値になるためである(決定の記録 0062)。
例: 塩 2g を 1 人分にすると、5 刻みでは「5g」になる。
どちらの刻みを使うかは、丸める前の値で決める。
10 以上の値は 5 刻みで 10 以上に、10 未満の値は 1 刻みで 10 以下になるので、人数を増やして値が減ることはない。

#### 分数の決まり

換算した値を、整数の部分と、端数(0 以上 1 未満)に分ける。
端数を、次の 7 つの候補のうち、いちばん近いものに丸める。

| 候補 | 0 | 1/4 | 1/3 | 1/2 | 2/3 | 3/4 | 1 |
|---|---|---|---|---|---|---|---|
| 値 | 0 | 0.25 | 0.3333… | 0.5 | 0.6666… | 0.75 | 1 |

- 2 つの候補との差が同じときは、大きいほうを選ぶ。例: 端数 0.125 は、0 と 1/4 の真ん中なので、1/4 にする。
- 候補が 0 のときは、整数の部分だけを書く。候補が 1 のときは、整数の部分に 1 を足して書く。
- 候補が分数で、整数の部分が 0 のときは、分数だけを書く。例: 「1/2」
- 候補が分数で、整数の部分が 1 以上のときは、「と」でつなぐ。例: 「1と1/2」「3と3/4」
- 全体が 0 になるとき(換算した値が 0.125 より小さい)は、「1/4」と書く。0 にはしない。
- 差が同じかどうかは、小数の計算の誤差を見込んで、100 万分の 1 の幅で比べる。`0.3333` のように、4 桁で切って書かれた分量(データ設計の 5.2)を、正しい分数に戻すためである。

例は次のとおりである。
基本の人数は、どれも 2 である。

| 書いてある分量 | 表示の人数 | 換算した値 | 表記 |
|---|---|---|---|
| 大さじ 1 | 3 | 1.5 | 「大さじ1と1/2」 |
| 大さじ 2.5 | 3 | 3.75 | 「大さじ3と3/4」 |
| 大さじ 1.5 | 1 | 0.75 | 「大さじ3/4」 |
| 大さじ 2 | 5 | 5 | 「大さじ5」 |
| 小さじ 0.5 | 1 | 0.25 | 「小さじ1/4」 |
| 小さじ 0.25 | 1 | 0.125 | 「小さじ1/4」 |
| 小さじ 0.25 | 3 | 0.375 | 「小さじ1/3」 |
| 小さじ 0.25 | 5 | 0.625 | 「小さじ2/3」 |
| 0.3333 個 | 1 | 0.16665 | 「1/4個」 |
| 0.3333 個 | 3 | 0.49995 | 「1/2個」 |
| 0.3333 個 | 5 | 0.83325 | 「3/4個」 |
| 0.3333 個 | 6 | 0.9999 | 「1個」 |
| 0.5 個 | 3 | 0.75 | 「3/4個」 |
| 0.5 個 | 6 | 1.5 | 「1と1/2個」 |
| 3 本 | 5 | 7.5 | 「7と1/2本」 |

小さじ 0.25 は、1 人分でも 2 人分でも「小さじ1/4」になる。
1/4 より小さい分数を、候補に持たないためである。
今の静的なレシピ集も、同じ表記である。

#### 基本の人数のとき

表示の人数が基本の人数と同じときは、書いてある分量を、丸めずに出す。

| 単位 | 決まり | 例 |
|---|---|---|
| `g`、`ml` | 数をそのまま書く | 250 は「250g」、3 は「3g」、12.5 は「12.5ml」 |
| そのほか | 端数が、上の候補のどれかと、1,000 分の 1 以内で一致すれば、分数で書く。一致しなければ、小数のまま書く | 0.5 は「1/2」、0.3333 は「1/3」、1.5 は「1と1/2」、0.6667 は「2/3」、0.2 は「0.2」、1.2 は「1.2」 |

- 小数は、書いてある桁のまま出し、末尾の 0 は付けない。分量は、小数 4 桁までである(データ設計の 5.2)。
- 1,000 分の 1 の幅は、`0.3333` と `0.6667` を、1/3 と 2/3 として読むためのものである。
- 丸め方が整数の材料も、基本の人数のときは、上の表に従う。例: 編集で卵を 1.5 個にしたレシピは、基本の人数で「1と1/2個」、4 人分(基本の人数が 2 のとき)で「3個」と出る。

#### 今の実装との違い

今の `QuantityFormatter` と、この節の決まりを、今の 38 品のすべての材料(数値で表せる 378 行)と、1 から 6 人のすべての組み合わせ(2,268 通り)で比べた。
コンテナの中の Node.js で両方を動かし、表記が食い違う組み合わせは 0 件だった。
この比べは、3 桁ごとの区切りを入れる前の文字列で行った。

この比べは、`g` と `ml` を 10 未満でも 5 刻みにしていたときの決まりで行った。
その後に、10 未満を 1 刻みにすると決めた(決定の記録 0062)。
この変更で表記が変わるのは、今の 38 品では 1 か所である。ひじきの煮物の 15g を 1 人分にしたときが、「10g」から「8g」になる。
`g` と `ml` の 76 行を、1 から 6 人分で計算して数えた。画面の実装で比べ直してはいない。

今の 38 品にない値では、上のほかに、次の 3 点が変わる。

| 場合 | 今の実装 | この仕様 | 変える理由 |
|---|---|---|---|
| 基本の人数のときの、5 の倍数でない `g` と `ml` | 5 刻みに丸める。3g は「5g」 | 丸めない。3g は「3g」 | 編集で入れた値と、表示が食い違うのを防ぐ |
| 分数で、端数が 0.08 以上 0.125 未満か、0.875 より大きく 0.92 以下 | 「1/2」になる。例: 0.1 は「1/2」、1.75 を半分にした 0.875 は「1/2」 | いちばん近い候補にする。0.1 は「1/4」、0.875 は「1」 | 今の動きは、候補を探す処理が何も見つけられず、最初の値の 1/2 が残るために起きている。意図した動きでない |
| 分数で、値が 0.08 より小さい | 「1」になる | 「1/4」になる | 少ない分量が、多く表示されるのを防ぐ |

### 5.8 料理名の組み立て

アレンジ版の、画面での名前は、`name` と `arrangeLabel` から組み立てる(データ設計の 5.2)。

| `arrangeLabel` | 名前 | 例 |
|---|---|---|
| ない | `name` | 「親子丼」 |
| ある | `name`、全角の開き括弧、`arrangeLabel`、全角の閉じ括弧の順につなぐ | 「親子丼(鶏むね肉でさっぱり)」 |

- 使う場所は、一覧のカードの料理名、カードのリンクの名前、詳細のタブの題である。
- 詳細の `<h1>` は、`name` だけを出す。変更点の名前は、すぐ下のアレンジの内容の見出しに出るためである。
- 献立など、ほかの画面でレシピの名前を出すときも、この関数を使う。画面ごとに組み立てると、括弧の種類が食い違うためである。

## 6. サービスの間のやり取り

なし。
この機能は、サービスを持たない。
画面は、入口を通して API を呼ぶだけで、サービスを直接呼ばない。

API が応答しないときの動きは、3.1 と 3.2 の「状態」に書いた。
どの API が応答しなくても、元のレシピの一覧、検索、絞り込み、詳細、人数の換算は働く。

ほかの機能設計に頼ること、頼られることは、次のとおりである。

| 相手 | 頼ること、渡すもの |

| #7 データ設計 | レシピの要約の一覧(検索用の文字列を含む)と、レシピの全体を受け取る。検索用の文字列を作る処理と、並べ替えは、ブラウザへ渡す形を作る場所から、5.2 と 5.5 の関数を呼んで行う |

### 確かめ方と、3 つの場合

`AC-LIST-01` から `AC-LIST-12`、`AC-DETAIL-01` から `AC-DETAIL-15` は、`frontend/src/domain/` の関数の単体テスト(Vitest)で確かめる。
`AC-DETAIL-42` から `AC-DETAIL-45` は、小さい版を作るスクリプトを、テスト用の写真に対して動かして確かめる。
ほかは Playwright で確かめる。
`AC-LIST-25` と `AC-DETAIL-24` は、今の 38 品にアレンジ版がないので、テスト用のレシピを組み込んだ画面で確かめる。
組み込み方は、段階 1 の実装のときに決める(8 章)。

| 場合 | 当たる条件 |
|---|---|
| 権限がない | ログインしていない人は `AC-LIST-28`、`AC-DETAIL-31`。見るだけの人は `AC-LIST-29`、`AC-DETAIL-36`。この機能は読むだけで、権限を判定する API を持たない。役割による入口の出し分けは、画面の一覧と遷移の `AC-NAV-17`、`AC-NAV-18`、`AC-NAV-20` が確かめる |
| 入力が不正 | `AC-LIST-07`、`AC-LIST-10`、`AC-LIST-20`、`AC-LIST-21`、`AC-LIST-22`。元のレシピにない `slug` は、画面の一覧と遷移の `AC-NAV-43` が確かめる |
| 相手のサービスが応答しない | `AC-LIST-32`、`AC-DETAIL-30`、`AC-DETAIL-38`、`AC-DETAIL-39` |

アクセシビリティの検査(axe)と、幅 360px での表示は、画面の共通仕様の `AC-UI-01` と `AC-UI-07` が、この 2 つの画面も対象にしている。
