# frontend(Next.js)

App Router、React、TypeScript、Tailwind CSS。
`output: "export"` で静的に書き出し、ブラウザから `/api` を呼ぶ。

## ディレクトリの役割

```
src/
├── app/           # ページ。データの取得と部品の組み立てだけを書く
├── components/    # 再利用する部品。業務の計算を書かない
│   ├── ui/        # 業務を知らない部品(ボタン、入力欄、ダイアログなど)
│   ├── layout/    # ヘッダー、フッター、レシピ帳の切り替え
│   └── <機能>/    # その機能だけで使う部品
├── hooks/         # 画面の状態(ログイン、今開いているレシピ帳、自動保存)と、API の取得をまとめる処理
├── domain/        # 業務ロジック。React、Next.js、ブラウザの API に依存させない
├── schema/        # Zod のスキーマ(元のレシピ、食材マスタ、入力欄)
└── api/           # API を呼ぶクライアント。generated/ は openapi.yaml から作る
e2e/               # Playwright
scripts/           # データの検証
```

## 決まり

- **計算は `src/domain/` に書く。** 栄養計算、分量の換算、検索の正規化、編集内容の重ね合わせ、献立の合計が対象である。部品やページの中に書かない。単体テストで固めるためである。
- **`src/domain/` から React、Next.js、`window`、`localStorage`、`fetch` を使わない。** 引数と戻り値だけで完結させる。
- **API は `src/api/` のクライアント経由で呼ぶ。** ページや部品から `fetch` を直接呼ばない。エラーの形(`{ code, message }`)の扱いを 1 か所にまとめるためである。
- **`src/api/` の関数は `src/hooks/` からだけ呼ぶ。** ページと部品は `src/hooks/` を通して取る。読み込み中とエラーの扱いを、画面ごとに書かないためである。
- **`localStorage` は `src/hooks/` からだけ読み書きする。** 保存してよいのは、今開いているレシピ帳の識別子だけである。
- **ログインが要る画面は `src/app/(member)/` に置く。** そこの `layout.tsx` が、ログインしていない人をログインの画面へ移す。これは表示の都合で、権限の判定にはならない。
- 見た目、部品、エラーの `code` ごとの動き、アクセシビリティの決まりは [docs/design/common-frontend.md](../docs/design/common-frontend.md) に従う。
- **`src/api/generated/` を手で編集しない。** `api/` の仕様から作り直す。
- **ビルド時に読むデータ(`data/`)は Zod で検証してから使う。** 検証に通らないときはビルドを止める。
- **ブラウザでしか動かない処理を持つ部品には `"use client"` を付ける。** 付ける範囲は、状態を持つ末端の部品に絞る。
- **動的なパス(`[slug]`)には `generateStaticParams` を書く。** 静的に書き出すので、ビルド時にすべてのパスが決まっている必要がある。
- `any` を使わない。型が定まらないときは `unknown` から絞り込む。
- 公開する関数には戻り値の型を書く。
- 入力欄の検証は Zod で行い、スキーマを `src/schema/` に置く。
- 色と書体は Tailwind のテーマの値を使う。部品に色の値を直接書かない。角括弧で値を書くクラス(`p-[13px]`)も使わない。
- 写真には代替の説明を付ける。操作できる要素はキーボードで届くようにする。

## テスト

- `src/domain/` の関数には Vitest の単体テストを書く。テストは同じディレクトリに `*.test.ts` で置く。
- 受け入れ条件(要件定義の 4 章)のうち、画面の動きに関わるものは Playwright で書く。
- 栄養計算のテストには、手で計算した期待値を書く。実装の出力を写して期待値にしない。
